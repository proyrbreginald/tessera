# 门禁手册

> 每条门禁回答三个问题：**它拦什么**、**它真的拦住过什么**（没有实例的检查往往是摆设）、**失败之后怎么办**。
>
> 唯一全量入口是 `cargo xtask verify`；只想看整体健康度用 `cargo xtask gates`（不因第一个失败而中断）。
> 常量类数字（成员/纯逻辑 crate 数、静态门禁条数、unsafe 预算、缺口数）由
> `cargo xtask check-docs` 强制与代码一致 —— **数字变了就改文档，不要改代码来迁就文档**。

## 1. 静态门禁（`cargo xtask gates` 一次跑完全部 18 项）

| 门禁 | 拦什么 | 真实事件 | 失败后怎么办 |
|---|---|---|---|
| `check-layering` | 18 个纯逻辑 crate 的依赖闭包（**含 dev-dependencies**）里出现 `imxrt-*`/`cortex-m*`/`rtic`；名单唯一来源是 `PURE_CRATES` | 2026-10-10：Makefile 与 CI 各自硬编码 crate 名单，纯逻辑层长大之后 `make test` 仍只跑 144 个用例、CI 漏 5 个 crate 的 lint；审计还抓到过 `imxrt-hal.workspace = true` 这种用"依赖名后缀"绕过精确匹配的写法 | 把硬件相关部分放到 `board-support`，纯逻辑侧只留 trait（见 [`ports`](../../crates/ports/src/lib.rs)） |
| `check-capsules` | `sdk` 不再是纯逻辑、或依赖了 `sdk` 的插件 crate 直接依赖 `board-support`/`firmware`/`rtic`/`imxrt-*`。**只扫仓库内 `crates/`**：`firmware`/`board-support` 作为组合根被排除 | 该门禁**早于 S1 引入**（基线 `e1c69e4` 的 `xtask` 已有 dispatch/COMMANDS/verify 三处），S1 只把 `product` 纳入 `PURE_CRATES`，因此它自动覆盖 `product`。仓库外业务工作区**不在覆盖范围**（S3 才补） | 插件只能依赖 `sdk`（稳定门面）与纯逻辑层；需要硬件能力走 `sdk` 将来提供的能力句柄（S2），不要直接 `use board_support` |
| `check-interrupt-priorities` | `#[task(binds = …, priority = N)]` 的优先级字面量与期望表不一致；出现未登记的中断任务 | RTIC 的 `priority` 只接受整数字面量，编译器无法把它绑定到 `primitives::budget::prio`；`console_rx` 与 `deadline_tick` 同为 1 是刻意配置，而 `SERIAL_RX=2` 属于尚未落地的串行总线任务（易被误读） | 新增/调整中断任务时，同时改 `main.rs` 的 `priority`、`xtask` 的期望表与 `docs/02-架构/中断与idle轮询分析.md`；改优先级后重新做字节间隔/时基余量论证 |
| `check-lint-headers` | 纯逻辑 crate 的 `lib.rs` 缺 `forbid(unsafe_code)` 或两条 clippy 拒绝项（`unwrap_used`/`indexing_slicing`） | lint 头被"顺手删掉"是静默降低标准最常见的形态 | 补齐 lint 头（照抄 [`mpu-regions`](../../crates/mpu-regions/src/lib.rs) 的开头） |
| `check-unsafe` | `unsafe {}` 与 `// SAFETY:` 不配平、`unsafe fn` 缺 `# Safety` 段、超出 [`unsafe.budget`](../../unsafe.budget)（预算 81，实测 80，以 `check-unsafe` 为准） | 预算一路从 22 增到 56，**每一次增长都必须在 `unsafe.budget` 里写下**"为什么无法避免、为什么不会引入 UB"；`alloc_pool`/`flexcan`/`cache`/`rom_flash` 的每一处都有逐条理由 | 补 SAFETY 说明；确实必需就**同时**更新 `unsafe.budget` 里的理由，否则门禁会拒 |
| `check-gaps` | **刻意不失败**：清点全部 `GAP(Px)` 并给 `文件:行` 指针（当前 3 项：P2 CAN 接收路径 / P4 A/B 升级 / P5 看门狗） | 未实现项是事实而不是错误；它需要被看见、被计划 | 不需要修，但**不许把 `GAP` 标记删掉了事**（那等于假装完成）。接线之后把标记与清单一起更新 |
| `check-fault-handlers` | 四个故障向量（槽 3–6）指向空桩或共用处理器 | 2026-10-12 审计从**链接产物**读出：槽 3（`HardFault`）反汇编是 `push {r7,lr}; mov r7,sp; b .` —— 空死循环；槽 4/5/6 指向 `DefaultHandler_`。这类缺陷**编译得过、测试也全绿**，只有看产物才发现 | 要么写出真实处理器（`#[exception] unsafe fn HardFault(frame) -> !`，能拿到 PC/LR/SP），要么**刻意**让三类可配置故障升级（本项目当前选择，理由：cortex-m-rt 只允许 HardFault 拿帧）；**混合**状态会失败 |
| `check-critical` | 裸的 `critical_section::with` / `interrupt::free` / `interrupt::disable` 出现在允许清单之外（只有 [`board-support/src/rt.rs`](../../crates/board-support/src/rt.rs) 这一处测量入口与测试文件可以） | 2026-10-12：终端 `fs` 命令第一版在 `with_fs`（**关中断**）里调用会全盘扫描的 `stats()`，主机实测读 28.3 MB 介质、真机折算 **0.5–2 s** 关中断 —— 而当时构建、测试、门禁**全都照样通过**。「一个没被测量的临界区」就是「没人知道有多长的关中断窗口」 | 改用 `board_support::rt::measured_cs(|cs| { … })`：它读 DWT 周期计数器并记入 `irq-off` 统计，超预算时由 `realtime` 判定；若确实是长活，正确修法是把活挪出临界区 |
| `check-api-usage` | 清点**整仓只出现一次**的 `pub fn`（即只有定义、没有调用者） | 2026-10-10 用手工办法（数引用次数）一次就找出 `fs::stats()`/`rescan()`、`FileSystem::block_erase_count()` 等**有行为却没人接线**的公开项 —— 其中"磨损统计没人接"是评审里挂了很久的一条。手工排查有效但会忘，这条让它每次可重跑 | **刻意不失败**（与 `check-gaps` 同一取舍）：没有调用者可能是给上层留的扩展点，也可能是忘了接线。看输出里的 `文件:行` 去判断，真缺口就接上或按 `GAP` 留痕 |
| `check-style` | 代码里出现 `todo!()`/`unimplemented!()`；crate 缺 `//!` 模块文档；workspace lints 被放宽（`missing_docs`/`unsafe_code` 不见了） | 铁律"禁止 `todo!()`"此前**只有文档、没有门禁**；`no_std` 固件里一个 `todo!()` 等于 ISR 静默挂死 | 改成返回明确错误变体（`NotImplemented`/`Rejected`）+ 留 `GAP(Px)`；模块文档补 `lib.rs` 开头 |
| `check-docs` | 三类：① 常量类数字与代码不一致（成员/纯逻辑 crate 数、静态门禁条数、unsafe 预算、缺口数）；② **孤儿文档** —— 每篇 `docs/**/*.md` 都必须被某处链接；③ **命令存在性** —— 文档里出现的每条 `cargo xtask <子命令>` / `make <目标>` 都必须真实存在 | 2026-10-10 的人工审计一次查出 **27 处**漂移（映像大小、SP、unsafe 数、crate 数…）；文档可达性抓出过 5 篇孤儿文档；命令存在性针对"照着文档敲、报 command not found"这类最伤信任的错误 | 改文档（断言消息里写了是哪一句、应该是多少）。**会变的测量值不要写进文档**，用 `cargo xtask context` 取 |
| `check-memory` | `.text` 不在 ITCM 或超出 64 KiB 预算；`.stack` 大小与声明值不符；`.vector_table` 不在 DTCM | 这些此前只是链接脚本与文档里的约定，段被挪走或 ITCM 被挤爆**没有任何检查会失败** | 看是哪个段跑偏；预算常量在 [`memory-layout`](../../crates/memory-layout/src/lib.rs)，要改预算得连同理由一起改 |
| `check-code-placement` | `.xip` 段里的符号不在批准名单（`XIP_ALLOWED`），或 `.xip` 地址不在 Flash 窗口内 | `.xip` 是 Flash **原地执行**区：里面的代码在擦/写期间取指停等（真机：擦 64 KiB ≈ 557 ms）。负例验证史很说明问题：第一版"按名字查驱动符号"在 `lto = "fat"` 下**无效**（模块被整体内联，`nm` 里根本没有那个名字）；第二版"扫机器码里的寄存器地址字面量"也无效（Thumb-2 把地址拆进 `movw`/`movt` 的指令字段）⇒ 改成**正向白名单**：里面只允许批准过的东西 | ① 确实该放这里 → 在 `XIP_ALLOWED` 里加一条并写明理由；② 否则去掉函数上的 `#[unsafe(link_section = ".xip")]`。⚠️ 静态门禁**看不见内联**，充分判据是真机上从 `idle` 发起一次擦除+编程 |
| `check-image` | 链接产物里的 FCB tag/版本/容量、LUT **三个序列的 4 字节地址相位**（读 `0xEC`/擦 `0x21`/写 `0x34`，相位 `0x20`）、IVT 魔数、初始 SP 落在 DTCM | LUT 退回 3 字节地址时，越过 16 MiB 的访问**不报错**，会静默别名到低 16 MiB（"擦日志区"擦掉启动头） | 看 `board-support::flash` 里的路线对照表；**时钟与 dummy 必须一起改** |
| `check-size` | 映像 ≥ 1 MiB | 单槽升级要放得下；同板既有 C 固件的 960 KiB 槽位曾被 1,062,020 B 的映像撑爆 | 看是什么把映像撑大的（`size -A`），别直接抬阈值 |
| `check-flash-map` | 分区表不自洽 / 映像放不下分区 / **文档里的分区表格与代码不一致** | 分区表是三处（BSP、门禁、文档）共用的事实来源，最容易"文档写一套、代码跑另一套" | 以 [`flash-layout`](../../crates/flash-layout/src/lib.rs) 为准，同时改文档表格 |
| `check-compile-fail` | `tests/compile-fail` 下的负例**居然编译过了**，或错误码与 `EXPECTED` 不符 | 现有负例证明的是"**`Cycles` 非零**在类型上不可绕过"（`record(span, 0)` 必须编译不过）—— 起因是真机上 DWT 被清后拿到 0 周期样本，`count > 0` 而 `max == 0`，"没被观测"被显示成"快得测不出来" | 说明约束被削弱了 —— 通常是有人加了 `From`/`Deref`/默认值，或把不变式从类型挪回了注释 |
| `trace` | 需求追溯矩阵里出现无代码/测试引用的需求（当前 **30 条**平台需求：RT/PF/MT/EV/DB/SF/TS） | 手写追溯矩阵必然漂移；这份是**工具生成**的（勿手改） | 给该需求补实现与测试引用，或删掉这条需求 |

> 另外两个不算"检查"但同属静态门禁体系的命令：`cargo xtask verify`（全量入口）与
> `cargo xtask gates`（汇总表，不因第一个失败而中断）。`cargo xtask check-*` 单跑用于排查。

**为什么不设工具链门禁**：仓库策略是**永远跟随最新 stable**，`rust-toolchain.toml` 只写
`channel = "stable"`，没有 `toolchain.lock`、也没有逐字比对 rustc 版本的门禁
（原 `check-toolchain` 已删除）。可复现性由入库的 `Cargo.lock` / `xtask/Cargo.lock`
保证；新 stable 的新 lint 按"修代码"处理，不放宽 lint。细节见
[`构建与工具链`](构建与工具链.md)。

## 2. 非静态门禁（按需跑，因为慢或需要台架）

| 门禁 | 拦什么 | 什么时候跑 |
|---|---|---|
| `cargo xtask coverage` | 主机侧**行覆盖率低于 90%**（阈值；当前值以命令输出为准） | 改动纯逻辑后；它只统计**能在主机上跑**的 18 个纯逻辑 crate —— BSP/固件的正确性由 `check-memory`/`check-code-placement` 与真机自报事实承担 |
| `cargo xtask bench` | 真机指标退化（**百分比与绝对量同时超限**才算回归）；另有三条与基线无关的**硬判据**：栈余量 ≥ **30%**、实时预算成立 `rt=ok`、控制台零丢弃 `txdrop=0` | 动过时钟/缓存/内存布局/发送路径之后；`--record` 重采基线（[`bench/baseline.json`](../../bench/baseline.json)），`--from-file <抓包>` 可离线验证解析逻辑本身 |
| `make bytecheck` | 控制台输出**丢字节/错位**（肉眼不可靠：丢字节常只出现在长输出的后半段） | 动过控制台、时钟、中断优先级之后 |
| `make monitor` | 时基漂移超出 ±2%（判据是设备自报 `uptime` vs 主机时间；脚本会自动发 `beat on`） | 动过时钟树/波特率之后 |
| `make check-bench` | 探针、SWD 节点、pyocd 不可用 | 每次烧录之前 |

## 2.5 capsule 化后的门禁缺口（S1 后仍存在的部分）

当前 18 项静态门禁只覆盖“本仓库 20 个成员 crate”。业务 capsule 建在仓库之外，
因此以下能力**只覆盖仓库内**或**还不存在**：

| 目标门禁 | 要拦什么 | 现状 |
|---|---|---|
| 业务 crate 依赖检查 | 只允许依赖 capsule SDK/端口；禁止 `board-support`/`firmware`/`imxrt-*`/`rtic` | `check-capsules` 已覆盖**仓库内**依赖 `sdk` 的插件；`check-layering` 覆盖仓库内 18 个纯逻辑 crate；**仓库外无检查** |
| 业务 crate unsafe 检查 | 禁止 `unsafe`/寄存器访问 | 仅靠仓库内 `forbid(unsafe_code)`；**无仓库外检查** |
| capsule 契约检查 | `Capsule` 生命周期、事件/预算签名、主机可重放 | `sdk::Capsule<C>`（name/phase/init/step）已有单测；`on_event` 事件分发**未实现**，无预算签名检查 |
| 每 capsule 预算/健康 | 单个 capsule 不能顶爆全局 span | **部分**：有 per-capsule 失败计数与**累计** 3 次即隔离；没有独立实时预算/配额 |
| 整包组合检查 | 组合根只选择已登记 capsule；业务不修改底座源码 | **S1 已提供通路**：`product` 组合根 + 业务槽；仓库外产品注册业务 capsule 尚无门禁 |

在这些门禁落地之前，仓库外业务只能靠代码评审与 `simulator` 测试约束；
不能宣称“capsule 已经被门禁保护”。方向见 [ADR-0008](../adr/0008-静态capsule化内核.md)
与 [`产品组合根外提设计`](../02-架构/产品组合根外提设计.md)。

## 3. 三条"门禁本身"的纪律

1. **门禁必须能失败**：每条新门禁都要有**负例验证**（故意改坏 → 必须失败）。
   本项目已有的负例证据：`check-docs`（改错成员数）、`check-style`（插入 `todo!()`）、
   `check-memory`（预算常量改小即 `error[E0080]`）、`check-code-placement`（把未批准的函数
   标进 `.xip`）、`bench`（吞吐改小 61% 即判回归）、`mpu-regions`/`memory-layout` 的编译期断言。
2. **门禁失败信息要给出"怎么修"**，而不只是"哪里错"。
3. **同一件事只允许有一份定义**：纯逻辑 crate 列表来自 `PURE_CRATES`（`make test`/CI 都委托它）、
   分区表来自 `flash-layout`、内存布局来自 `memory-layout`、命令清单来自 `COMMANDS`
   （`help` 由它生成，不会再漏项）。历史上"同一件事写两遍"已经造成过：
   `make test` 只跑 144 个用例、CI 漏掉 5 个 crate 的 lint、MPU 区域表与内存布局各写一份 64 KiB。
