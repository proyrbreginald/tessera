# 台架准备与排障

## 一次性准备

```bash
make setup                  # 建 .venv 并装 pyocd/pyserial
sudo usermod -aG dialout "$USER"    # ⚠️ 之后必须**重新登录**（或 newgrp dialout）
make check-bench            # 台架就绪检查
```

udev 别名由台架**统一维护**，源文件与安装步骤在相邻项目的 `tools/udev/` 下
（本仓库**不自带副本**：两份规则漂移比没有规则更糟）。

| 别名 | 用途 |
|------|------|
| `/dev/pudu-debugger-16p-uart` | 本板调试串口（`J7` 的 TX1/RX1） |
| `/dev/pudu-debugger-swd` | SWD 探针（`c251:f001`） |

> 这两个名字就是 `scripts/tool-paths.sh` 里的 `UART_ALIAS` / `SWD_ALIAS` 默认值；
> `make check-bench` 按它们检查。改别名请改脚本与 udev 规则，不要只改文档。
> `cargo xtask bench` 抓包用的串口节点可用 `BASE_SERIAL=<节点>` 覆盖；
> 脚本要显式指定解释器时用 `BASE_PYTHON`。

⚠️ **务必用别名，不要用 `ttyUSBn`**：内核按枚举顺序分配编号，换 USB 口、插拔顺序、
重启都会换号（既有工程实测控制台从 `ttyUSB1` 变成 `ttyUSB0`）。

## 为什么烧录成功本身就是证据

探针不能隔着 SWD 直接写 QSPI Flash。真实流程是：探针把一小段 **flash 算法**下进
片上 RAM → 让 M7 跳过去执行 → 算法**自己初始化 FlexSPI 控制器**，产生真正打到
W25Q256 上的 SPI 时序。

因此**烧录成功本身就说明 FCB 的读命令、dummy 周期与时钟配置是对的** ——
flash 算法与 Boot ROM 共用同一套参数。

## 排障清单（现象 → 根因 → 处置）

| 现象 | 根因 | 处置 |
|------|------|------|
| 完全无输出，核心像卡死 | 核心被摁在**复位态**（复位没走到 Boot ROM） | 查供电轨（12 V、`MAIN_3V3`、`VCC_1V1`）、复位按键是否卡住、`POR_B` 电平。判据：`DHCSR.S_RESET_ST=1` 且**外设总线全读回 0**（调试域可读说明调试链路是好的，问题在复位/供电） |
| 读 `0x6000_0000` 得 0，以为 Flash 是空的 | FlexSPI 未初始化时该地址**无人应答**，本来就只能读到 0 | 不要据此判断 Flash 内容 |
| 看门狗闩锁 | `SGM706`（`U5`）的 `WDG_CTR` **需要高电平才禁用**；不为高时 `MR` 被拉低 → 经 `POR_B` 复位 | 归入"完全无输出"排查；烧录/调试期间必须确保看门狗被禁用 |
| 烧录成功但起不来 | 镜像没写在 QSPI 的**偏移 0**（FCB 在最前），或器件没擦干净 | `make image` 断言布局；objcopy 产物不要裁掉或补齐开头 |
| FCB 与实装器件不匹配 | 三处必须一致：链接脚本的 FLASH 长度、FCB 的 `sflashA1Size`、读序列的 dummy/时钟 | `build.rs` 生成 `const` 断言绑死前两者；`make image` 断言镜像里的实际值 |
| 启动即崩溃 | **dummy 周期与串行时钟绑定**：只改时钟不重算 dummy 会读到垃圾数据 | 两者要么一起改，要么都别动 |
| 有输出但乱码 | 时钟或波特率不对 | 确认 115200 8N1；确认控制台的 `CLOCK_HZ` 与所选时钟源一致；确认板上是 24 MHz 晶振 |
| 文字正常但 `uptime` 漂移 | 时间基准不对（时基取自晶振，指向晶振本身而非串口） | `make monitor` 报告漂移；必要时用示波器/频率计标定 |
| 输出中途停住 | 线缆/连接器机械问题（`J7` 的 11/12 脚、22 Ω 串阻） | 先排除机械问题再查固件 |
| `pyocd list` 报没有探针 | **四种互不相同的原因**：探针不在、`/dev` 节点权限不足、被别的进程占用、跑在重建了 `/dev` 的沙箱里 | ⚠️ `lsusb` 能列出探针**完全不能说明可用**（libusb 与 lsusb 都靠 sysfs 枚举）。逐条查：`/dev/bus/usb/BBB/NNN` 是否存在且可读写 → 是否被占用（`pgrep -a -f 'pyocd\|openocd'`）→ `ls /dev/bus/usb` 是否存在 |
| 串口打开报 `Device or resource busy` | ModemManager 把 CDC-ACM/CH34x 口当"可能的调制解调器"探测 | `sudo systemctl stop ModemManager && sudo systemctl mask ModemManager` |
| 别名存在、`ls -l` 看不出异常，但打开报 `Permission denied` | 规则是 `GROUP="dialout" MODE="0660"`，改组成员后**必须重新登录** | `newgrp dialout` 或重新登录；Arch 系组名是 `uucp` |
| 补装 udev 规则后别名仍不生效 | `udevadm trigger` 默认发 **change** 事件，不会重建别名 | 加 `--action=add`，或直接拔插一次 |
| 别名指向错的设备 | 台架有多个同型号适配器 | `udevadm info -q property -n /dev/ttyUSBn \| grep '^ID_PATH='`，再用 `ENV{ID_PATH}` 钉死物理口（代价：换口后别名会静默消失） |
| panic 后串口没消息但调试器看到 `udf` | 写串口时控制台正被占用；`with_console` 用 `try_borrow` 失败即返回、**不阻塞** | 看故障寄存器（`SCB::CFSR`/`HFSR`、压栈的 PC/LR），不要等日志。panic 路径本身走 `write_bytes_blocking`（绕开被占用的队列），因此"完全没消息"要先怀疑核没在跑 |

## 关于 `make check-bench` 的取舍

- **探针不存在 = 硬失败**：这是一条无法绕过的前置条件。
- **串口别名缺失 = 只警告**：别让固件工作卡在与固件无关的环境问题上。

因此 **别名缺失不能当作环境 OK 的证明**。这是刻意取舍，不是疏漏。

## `make bytecheck` 的期望文本

判据是"复位 → 抓包 → **剥离 ANSI 后逐条比对**"（见 `scripts/console-bytecheck.py`）。
两类期望，来源不同：

- **横幅图形**：来自仓库根 [`banner.txt`](../../banner.txt)，当前字体为 **ANSI Shadow**（figlet 字体）；`build.rs` 构建期注入，
  改文件即改横幅；banner.txt 不允许空行，否则每行之间会多出空白）。脚本**不写死**图形文本，而是直接读该文件的第一行 ——
  于是你替换图形时脚本自动跟随，不会留下过时的期望。
- **启动报告**：`build.rs` 注入的身份行（`tessera <版本> · MIMXRT1021CAG4A · Cortex-M7 @396 MHz`）
  与五个分节 `[启动]/[平台]/[安全]/[实时]/[设备]` 的关键行：
  `sdram post :`、`flash 4B`、`fs`、`mpu`、`stack`、`dwt`、`flash rd`、`id`、`can`。
  这些行由固件打印，**不随图形变化**。

改**图形**只需改 `banner.txt`；改**报告行**则要同时改期望清单。但不要为了"让门禁过"
把期望改宽 —— 逐字节校验的价值恰恰在于期望是**具体文本**（丢字节常只出现在长输出的后半段）。

需要原始寄存器细节（`pit regs`、`region0..7`、FlexSPI/FlexCAN 探针、DWT 分段回读）时，
进入终端后敲 `diag`；它们**刻意不放进启动报告**（报告要一眼能读完）。

## 实测签名：如何判断"核心被摁在复位态"（2026-10-09）

台架上遇到过一次**板子完全不出字**的情形。以下判据可以**从调试器侧**确诊，
不需要示波器 —— 顺序照做即可，因为每一条都排除了一个不同的原因：

| # | 观察 | 实测值 | 排除/确认了什么 |
|---|------|--------|------------------|
| 1 | 串口能打开但**零字节** | 无输出 | 不是权限/占用（能打开就说明节点可用） |
| 2 | **完全不连调试器**再听串口 | 仍无输出 | 排除"探针把目标按住/占用了它" |
| 3 | `pyocd` 能连上、能读 CPUID | `0x410fc241`（Cortex-M7 r1p1） | 调试域是活的；问题不在 SWD 链路 |
| 4 | 读 Flash 映射 / OCRAM / IOMUXC / OCOTP | **全部 FAULT ACK** | 系统总线与外围域没起来 |
| 5 | 读 `SRC_SRSR`（`0x400F8058`） | `0x00000000` | **Boot ROM 压根没跑过**（POR 位应为 1） |
| 6 | 往 ITCM 写一小段代码再回读 | **写入不落地**（回读是别的数据） | 存储器写入被丢弃 |
| 7 | 设 PC/SP 后 resume 再 halt | PC **冻结**在 `0x0000139F4`（未映射区） | 核心没有在执行指令 |
| 8 | `pyocd erase --chip` | `flash init timed out` | 连 flash 算法都跑不起来（算法要在核上执行） |
| 9 | 逐个试 `reset_type`（hw/sw/hw_srst/sw_srst） | 全部"成功"但现象不变 | 不是复位类型选错 |
| 10 | `valid_aps` / 读 AP#1（MDM-AP） | `valid_aps=[0]`，AP#1 读数 == AP#0 | 该 CMSIS-DAP 只暴露一个 AP，**够不到 MDM-AP** |

**结论**：这是硬件层状态（核心被摁在复位 / 系统域未供电），软件无法恢复。
**处置：断电重新上电**。这与本板既有记录一致（`SGM706` 看门狗闩锁：`WDG_CTR`
需要**高电平才禁用**，不为高时 `MR` 被拉低 → 经 `POR_B` 把核心按在复位）。

⚠️ 注意第 6/7 条的价值：它们把"核心不执行"与"总线不通"区分开了。
只看第 4 条会误以为是 FlexSPI/Flash 的问题（进而怀疑 FCB），
而第 8 条 `flash init timed out` 才是决定性的 —— flash 算法在核上跑，
算法都起不来就说明问题在核，而不在 Flash。

⚠️ 另有一条容易误判：`pyocd reset` 与 `reset_and_halt` 在这块板子上都返回"成功"，
状态也会显示 RUNNING/HALTED 的切换。**不要用 pyocd 的返回状态判断板子是否真的在跑**，
要用第 5~8 条这类**可验证的副作用**（复位原因、写入是否落地、算法能否初始化）。

## 调试范式：以固件自报为准，调试器只做旁证

2026-10-09 的教训值得单独写下来。

**现象**：通过 SWD 读 PIT 寄存器得到彼此矛盾的结论 —— ch0 像是 24 MHz、ch2 像是
8 MHz、中断频率换算又像 40 MHz；同一地址连续两次读出不同值（甚至出现整片地址恒返回
同一常数 `0x2483`）。若以这些读数为依据，会把根因定到"PERCLK 配置错误"上去。

**事实**：固件自己的串口输出完全自洽 —— 心跳行（`beat on` 后）的 `uptime` 每秒精确 +1 s、原始刻度每秒
+24,000,000（= PERCLK 24 MHz 正确）、ISR 996.5 Hz。**根因不在时钟配置。**

**结论与做法**：

1. **让固件把它看到的寄存器读出来打印**，而不是用调试器去读。
   横幅里的 `pit regs : ch0 LD=... TCTRL=...` 就是这么来的，一次就把问题定死。
2. 需要区分"真事件"与"伪事件"时，把**两个计数都放进固件**（例如"ISR 进入次数"
   与"进入时标志确实置位的次数"），而不是用调试器反复采样。
3. 调试器的读**可以**作为旁证（CPU、状态、写是否生效），但凡与固件自报冲突，
   以固件自报为准，除非能解释差异。
4. 出现"整片地址返回同一常数"时，先怀疑链路（本次是**同时插了两个探针**：
   读到的 CPUID 是 `0x410FC241` = Cortex-**M4**，与 RT1021 的 `0x411FC271` 不符）。
   开始任何调试前的第一件事：**核对 CPUID 与目标芯片一致**。
5. 时基类问题的最快判据：`uptime` 是否跟得上墙上时钟。本次先用它排除了"时钟树"
   方向，才把注意力转到"计数器方向与中断竞态"。
