# 测试策略

## 核心问题：CI 与真机之间那道鸿沟

i.MX RT1021 在 QEMU/Renode 中支持并不完整（FlexSPI 外部 Flash、Boot ROM、SEMC 基本缺失），
而 Boot ROM/FCB 握手、真实中断时序、电气特性**无法**在主机上复现。如果不主动压缩这道
鸿沟，就会退化成"一个破坏启动流程的改动要等到夜间 HIL 才发现"。

本策略的目标：**让"必须靠真机才能发现的问题"只剩电气与真实时序两类。**

## 七层，各自负责证明什么

| 层 | 范围 | 手段 | 判据 |
|----|------|------|------|
| **L0 编译期** | 类型与常量 | newtype、类型状态机、`const_assert`、`#![forbid(unsafe_code)]` | 编译不过就是不合格 |
| **L1 单元** | 纯逻辑（**18 个 crate**：core/proto/ports/sim/sdk/product/semc/shell/flashmap/fs/mpu/memory/rt/fault/pool/log/gzip/flash） | `cargo test --target <host>`（= `cargo xtask test-host`） | **450 个用例**全绿（2026-10-23；会变，以命令输出为准） |
| **L2 属性/穷举** | 编解码（Modbus-RTU/CRC）、存储策略（双份 + 序号 + CRC）、FS 掉电原子性、时序 | 自研确定性 PRNG + 穷举小域 + 掉电注入 | 反例带种子可复现 |
| **L3 编译失败** | 类型约束的**负例** | `cargo xtask check-compile-fail`（自跑 cargo，断言错误码） | 负例确实编译失败（`Cycles` 非零：`record(span, 0)` 必须编译不过） |
| **L4 场景（端到端）** | 跨 crate 的数据流 + 可注入的时间与介质 | `simulator`：脚本化总线 + 手动时钟 + 可注入掉电的介质 + 捕获日志 | 主机上可完整重放（代表：`simulator/tests/power_cut_atomicity.rs`） |
| **L5 产物级** | 链接后的 ELF | `cargo xtask check-image` / `check-size` / `check-memory` / `check-code-placement`（真 ELF 解析） | FCB/IVT/向量表/体积/段放置 |
| **L6 目标端（HIL）** | 电气、真实时序、掉电 | 真机 + 探针 + 串口（**已接线**，2026-10-09 起多次上机） | 见下方"真机在环" |

再加一条贯穿各层的**追溯**：需求编号内嵌在源码/测试里，`cargo xtask trace` 生成矩阵
并对未覆盖项报错（当前 **30 条**平台需求，唯一真源是
[`需求规格`](../01-需求/需求规格.md)）。

静态门禁共 **18 项**（`cargo xtask gates` 一次列出全部 PASS/FAIL，不因第一个失败而中断；
逐条的拦什么/真实事件/失败处置见 [`门禁手册`](门禁手册.md)）。

当前 `cargo xtask check-gaps` 报 **3 项**未实现（P2 CAN 接收路径、
P4 A/B 升级、P5 看门狗）—— 未实现是**事实**而不是错误，清单与里程碑归属见
[`模块分解`](../02-架构/模块分解.md)。

## capsule 化后的测试边界（目标形态）

capsule 化把“业务 crate 不在本仓库”变成架构事实，但也把测试责任切得更清楚：

| 责任 | 由谁证明 | 手段 |
|---|---|---|
| capsule 的领域逻辑 | 业务 crate | 主机单测 + `simulator` 重放 |
| capsule 与端口契约的兼容 | 组合根/契约测试 | 编译期类型 + `simulator` 场景 |
| capsule 的耗时/阻塞 | core kernel | `realtime` 每 capsule 预算（目标） |
| capsule 的 panic/资源耗尽 | 全机 | 目前只能靠健康位/看门狗/配额；**不是隔离** |
| 整包集成 | 产品组合根 | `cargo xtask verify` + 真机 HIL |

两条当前边界：

- `sdk` 与产品组合根（`product`，S1）已落地，`Capsule<C>` 的契约（阶段顺序、容量、重名、
  失败隔离）已有主机单测；但**事件分发 `on_event` 未实现**，也没有 per-capsule 预算承载点，
  仓库外业务仍按 [`业务接入指南`](../02-架构/业务接入指南.md) 的方式测试。
- 目标形态下，业务 capsule 必须能在主机上完整重放；不能重放的逻辑说明它把硬件/时序
  漏进了业务层。

安全边界要单独说清：`forbid(unsafe_code)` 只排除 UB，不证明 capsule 不会 panic、
死循环或耗尽资源。测试策略不能把“编译过 + 主机测试过”当成“不可信隔离”。
见 [ADR-0008](../adr/0008-静态capsule化内核.md)。

## 各层里最值得说明的三个设计

### 1. L2/L4：把"不可类型化的契约"变成可穷举的策略

`Store::write_atomic` 的契约（掉电时"要么旧值、要么新值"）**无法用类型表达** ——
一个只写一半扇区的实现照样能编译。早期设计因此把它列为"只能靠真机断电测试验证"的
薄弱点，而真机断电测试慢、不可复现、一天跑不了几次。

拆开之后：

```text
DoubleBankStore（双份 + 序号 + CRC 的策略）  ←── 纯逻辑，主机可**穷举**
        │ 依赖
RawMedium（读/擦/写三个动作）                ←── 唯一的不可测部分，已被压到最薄
```

`crates/simulator/tests/power_cut_atomicity.rs` 对**每一个可能的掉电字节位置**
各跑一次（`for cut in 0..=total_written`），断言读回要么是完整旧值、要么是完整新值。

**这组测试在设计阶段就抓到了真实缺陷**：早期实现"先按序号挑出最新的、再校验它"，
于是一旦最新那份是半写状态，读路径会报错并**丢掉仍然完好的旧值**。
正确顺序是"先全部校验，再在有效的那些里挑最新"（`a_torn_newest_record_does_not_mask_the_intact_older_one`）。

### 1.5 文件系统：同一套"把不可测压到最薄"的思路

平台数据（配置、标定、复位台账、黑匣子、出厂信息等；词汇表见
`board-support::config::files`）都住在一个**日志结构文件系统**里
（[`filesystem`](../../crates/filesystem/src/lib.rs)）。
它的掉电安全同样不靠真机断电验证：

```text
FileSystem（记录 CRC + 版本完整 + 垃圾回收 + 磨损分散）  ←── 纯逻辑，主机可**穷举掉电点**
        │ 依赖
BlockDevice（读/擦块/写三个动作）                        ←── 唯一的不可测部分
```

测试用可注入故障的 Mock 介质，对**每一个可能的掉电点**各跑一次，
断言重新挂载后每个文件读到的是**完整旧版本或完整新版本**，绝不出现半新半旧。
这与 `DoubleBankStore` 的做法是同一条纪律：把"策略"留在能穷举的一侧，
把"三个动作"留给真机。

**为什么用文件而不是为每类数据切一个分区**：那些差异（整体覆盖 / 只追加 / 写一次）
是文件语义，不是物理布局；分区越多，"偏移/对齐/擦除策略"要论证的组合越多，
而每一处算错都可能擦掉别人的数据。


### 1.6 栈余量：数字必须来自测量，不能来自估计

这个项目的栈被真机打穿过**三次**，症状都是"串口一行都不出"：

| 日期 | 栈大小 | 现场证据 | 根因 |
|---|---|---|---|
| 2026-10-09 | 8 KiB | `SP=0x1FFFE7F0`（越过 DTCM 下界） | `init` 同时放装载缓冲（~4 KiB）与启动工作区（~3.5 KiB） |
| 2026-10-10 | 16 KiB | `CFSR=0x400`(STKERR)、`SP=0x1FFFF838` | `fs::mount()` 的 ~7 KiB 实例 + 搬进静态的副本同时在栈上 |
| 2026-10-10 | 32 KiB | 串口全哑 + SWD 连不上（lockup） | 文件系统扩到 446 块后常驻索引 7 → 12 KiB，"临时量 + 静态副本"同时在栈上 |

三次的教训是同一条：**当时只有一个"估计的"数字，而没有测量**。因此现在启动时做一次
栈涂抹（`board_support::stacks`）：在最早的时机把未使用的栈区涂成固定指纹，
启动完成后从栈底往上找第一处被动过的位置 —— 那就是**最坏情况**的用量。

历史读数（2026-10-10，含文件系统挂载；48 KiB 栈）：

```text
stack    : 峰值 28812 B / 48 KiB，余量 41%
```

**最后一次上机镜像的启动横幅**（同一块板，48 KiB 栈）：

```text
stack    : 峰值 29860 B / 48 KiB，余量 39%
```

> ✅ 当前源码版本 `0.1.1.0` 已于 **2026-10-27** 上机校准（见
> [`板级事实` §6](../03-硬件/板级事实.md)）；上面是两个更早镜像的读数，
> 引用时以"最后一条真机记录"的日期为准。

`cargo xtask bench` 另有一条与基线比对的口径（[`bench/baseline.json`](../../bench/baseline.json)，
2026-10-12 记录：栈余量 **34%**，硬下限 **30%** = `memory_layout::MIN_STACK_HEADROOM_PERCENT`）。
三条口径取数时机不同，都以命令/横幅输出为准。

三条纪律：

1. **数字随启动打印**，因此栈余量一旦异常，现场第一眼就能看到，而不是等 HardFault；
2. **改栈大小要有依据**：要么是这条测量变小了，要么是新增了一条深调用链；
3. **栈测量模块与链接脚本的大小由编译期断言绑死**（`build.rs` 生成的
   `consistency.rs` 里断言 `stacks::STACK_SIZE == STACK_BYTES`）——
   否则"余量"会被算在一个根本不存在的区间上。

### 2. L3：负例才是类型约束的证据

"类型约束存在"如果只有正例（"我这样用是对的"），根本无法证明约束**拦得住错**。
`tests/compile-fail/` 下每个用例是一个独立小 crate，附 `EXPECTED` 文件写明期望的
错误码；`cargo xtask check-compile-fail` 会真的编译它并断言失败原因：

| 负例 | 期望 | 证明的约束 |
|------|------|-----------|
| `span-record-zero-is-a-type-error` | `E0308` | `record(span, 0)` 必须编译不过 —— **`Cycles` 非零**是类型层面的要求，零周期采样不允许存在（它会让实时统计悄悄失真） |

**为什么不用 `trybuild`**：本机离线依赖集里没有它，而自己跑 cargo 只需 30 行。
更重要的是少一个依赖就少一份需要论证的工具面。

### 3. L4：测试能推进"被依赖方"的时间

端口层**拥有**它的时钟（时间从边界注入，这是分层要求）。但如果手动时钟自己持有值，
测试把时钟交给被测对象后就再也推不动时间 —— 而推进时间恰恰是所有超时场景的前提。

因此 `ManualClock` 内部是 `&Cell<Timepoint>`：

```rust
let cell = Cell::new(Timepoint::ZERO);
let clock = ManualClock::new(&cell);
let handed_to_driver = clock;                 // 驱动持有时钟
clock.advance(Duration::from_millis(3));      // 测试仍能推进时间
assert_eq!(handed_to_driver.now(), clock.now());
```

同一份时间被两边共享：驱动通过 `Clock::now()` 读，测试通过 `advance`/`set` 写 ——
"超时/抖动/回绕"于是变成确定性的、可复现的输入。

## 需求 → 测试的映射

`cargo xtask trace` 扫描 [`需求规格.md`](../01-需求/需求规格.md) 的编号（RT/PF/MT/EV/DB/SF/TS），
在源码中查找引用（测试名用下划线形式，如 `rt_1_...`；注释里写出原文如 `// 平台需求 RT-2` 也算），
生成 [`需求追溯矩阵.md`](../01-需求/需求追溯矩阵.md)，并对**没有任何引用的需求报错**。
当前 **30 条**平台需求全部有引用；每条需求的"可执行判据在哪"写在需求规格表里，例如：

- `RT-4`（回绕安全、可自证漂移）→ `primitives::time` 的回绕单测 + `make monitor` 的 ±2% 漂移判据；
- `TS-5`（类型约束必须有负例）→ `tests/compile-fail/span-record-zero-is-a-type-error`；
- `SF-2`（栈余量 ≥30%）→ `memory-layout` 的涂抹测量 + 启动横幅 `stack :` 行 + `cargo xtask bench` 硬判据；
- `PF-1`（真机基准与基线回归）→ `cargo xtask bench` 与 [`bench/baseline.json`](../../bench/baseline.json)（Flash 读吞吐基线 **48,701 KiB/s**，2026-10-12 记录）。

**为什么不手写追溯矩阵**：手写的表一定会与代码漂移，而漂移的追溯表比没有更糟 ——
它会给出虚假的安全感。

## 覆盖率

主机侧**行覆盖率**是一条**门禁**：阈值 **90%**，低于即失败（平台需求 **TS-3**）。
取数一律以 `cargo xtask coverage` 的输出为准（`-C instrument-coverage` + 工具链自带
`llvm-cov`，**不新增依赖**；只统计能在主机上跑的 **18 个纯逻辑 crate** —— BSP/固件的
正确性由产物级门禁（`check-memory`/`check-code-placement`/`check-image`）与真机自报事实承担）。

当前值**不写死在文档里**：它会变，写进来必然漂移。用命令输出或
`cargo xtask context` 的 `measured.coverage` 取。

⚠️ **诚实说明**：MC/DC 级覆盖需要合格工具链，属功能安全的未解问题
（见 [`工具链鉴定策略`](../05-安全/工具链鉴定策略.md)）；行覆盖率达标**不等于** MC/DC 达标。

## 反模式（明确不采用）

| 反模式 | 为什么不用 |
|--------|-----------|
| 用"跑一会儿看看"代替时序测试 | 不可复现、且只在特定对齐下暴露 |
| 只写正例不写负例 | 无法证明约束存在 |
| 手写追溯矩阵 | 必然漂移，且给出虚假安全感 |
| 断言"未实现的功能" | 会把未实现固化成"看起来已实现" |
| 用 `todo!()` 标记未实现 | 未实现变成运行期 panic；在 ISR 里可能表现为静默挂死 |
