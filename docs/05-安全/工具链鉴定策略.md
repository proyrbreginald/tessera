# 工具链鉴定策略

## 问题

功能安全认证通常要求编译器与运行时库经过鉴定（例如 TÜV 认证的 C 编译器）。
**`rustc` 没有这类鉴定**。这是本项目在安全语境下最大的单点不确定性，而且它
**不在工程团队的控制范围内** —— 能否被接受取决于认证方。

## 三条路径

| 路径 | 做法 | 代价 | 适用 |
|------|------|------|------|
| **A. 安全相关部分用已鉴定的 C 工具链** | 安全相关的关键路径（例如缓存维护、介质写入闸门）用经鉴定的 C 实现，Rust 只承载非安全部分 | 破坏"纯 Rust"目标 | 认证方强硬时 |
| **B. 工具链鉴定论证（Tool Qualification）** | 对 rustc 做使用域限定 + 大量测试 + 失效模式分析，形成鉴定证据包 | 工作量大，需认证方接受 | 作为辅助 |
| **C. 提高验证强度替代工具鉴定** | 安全相关代码高覆盖（门禁：主机行覆盖率 ≥90%，`cargo xtask coverage`）+ 穷举/属性测试 + 编译失败负例 + 编译期断言 + 独立评审，论证"工具缺陷会被下游测试捕获" | 测试成本高，但保留纯 Rust | **推荐主路径** |

**推荐 C 为主、B 为辅，A 作为谈判失败时的退路。** 这一点必须尽早与认证机构沟通。

## 另一个选项：Ferrocene

Ferrocene 是已获 ISO 26262 / IEC 61508 鉴定的 Rust 工具链。若接受引入（商业授权），
工具链缺口直接消失。**代价**：采购周期、版本受限、以及生态兼容性约束
（当前依赖 `imxrt-hal` 0.6 等 crate 是否能与 Ferrocene 的 rustc 版本共存需验证）。

🟡 **待确认**：是否接受 Ferrocene（Q-B）。若不接受，路径 C 的工作量与风险都要上调。

## 本项目已经做出的、降低工具鉴定压力的选择

| 选择 | 效果 |
|------|------|
| **减少依赖数量** | 固件依赖闭包只有 imxrt 全家桶 + rtic + cortex-m + heapless，无第三方工具链 crate（文本日志已接入；旧二进制日志资产已删除） |
| **不用 `defmt`** | 少一整条依赖链进入固件（且现场本来就没有调试器） |
| **不用 `proptest`/`trybuild`** | 验证工具不进"被验证代码"的构建闭包；用自研 PRNG 与自跑 cargo 替代 |
| **`xtask` 独立工作区** | 构建工具（`object` 等）不进入固件依赖闭包 |
| **unsafe 集中 + 预算** | 需人工论证的面积从"整个项目"缩到 **实测 80 处、两个 crate**（`board-support`/`firmware`；预算 81，以 `check-unsafe` 为准；其余 **18 个纯逻辑 crate** 由 `forbid(unsafe_code)` 编译期保证） |
| **安全相关机制面积小** | 集中在少数纯逻辑 crate（`mpu-regions`/`memory-layout`/`realtime`/`fault-decode`/`nor-flash`/`block-pool`），BSP 只留"把算好的值写进寄存器"的薄适配层 |

最后一条尤其重要：**把安全相关逻辑收敛到尽量小的模块**，这样即使最终被迫走路径 A
（用 C 实现安全部分），改动面也可控。
