> 而不是声称已经满足任何标准。
>

## 4. 编码标准与静态门禁

Rust 没有 MISRA 那样的行业标准，因此本项目自定并**全部由门禁强制**
（17 项静态门禁由 `cargo xtask gates` 汇总，不因第一个失败而中断）：

| 规则 | 强制方式 |
|------|----------|
| 纯逻辑层无 `unsafe`（18 个 crate） | `#![forbid(unsafe_code)]` + `cargo xtask check-lint-headers` |
| unsafe 必须逐处举证 | `// SAFETY:` 与 `# Safety` 配平 + `unsafe.budget` 只减不增（预算 81，实测 80，以 `check-unsafe` 为准） |
| 无 panic / unwrap / expect | crate 级 clippy deny（`-D warnings` 进 CI） |
| 无越界下标 | `clippy::indexing_slicing` deny |
| 无静默截断 | `clippy::as_conversions` + `cast_possible_truncation` deny |
| 无浮点（避免不确定性与 FPU 依赖） | `clippy::float_arithmetic` deny |
| 整数溢出显式暴露 | `overflow-checks = true`（release 也开） |
| 分层不可破坏 | `cargo xtask check-layering` |
| 未实现不可伪装 | `NotImplemented`/`Rejected` + `cargo xtask check-gaps` |
| 文档数字不漂移 | `cargo xtask check-docs`（常量类数字与代码强制一致） |

## 5. Rust 在安全论证中的优势与**缺口**（诚实版）

### 可以写进安全案例的优势

| 机制 | 消除的失效模式 | 论证方式 |
|------|----------------|----------|
| 所有权/借用 | use-after-free、数据竞争 | 类型系统（可静态论证） |
| `forbid(unsafe_code)`（**18 个纯逻辑 crate**） | 该层不存在 UB 类缺陷 | 编译期（`cargo xtask pure-crates` / `check-lint-headers`） |
| newtype 与不透明类型（`Timepoint` 不实现 `PartialOrd`、`Cycles` 非零） | 混用与回绕比较类缺陷 | 编译期 + 编译失败负例（`cargo xtask check-compile-fail`） |
| 控制路径无堆分配 | 内存耗尽、碎片导致的非确定性 | 固定块静态池 + `block-pool` 单测（失败是一个值） |
| 无 panic 路径 | 意外中止 | clippy deny + 错误类型化 |

### 必须诚实面对的缺口

| 缺口 | 影响 | 缓解 |
|------|------|------|
| **工具链未鉴定** | 认证方常要求编译器经鉴定 | 见 [工具链鉴定策略](工具链鉴定策略.md) |
| `unsafe` 的 BSP 层 | 该层仍可能有 UB | 预算门禁 + 逐处举证 + 人工评审（**79 处 / 预算 79**，集中在 `board-support` 与 `firmware`；`cargo xtask check-unsafe` 复测） |
| `core` 无安全手册 | 论证缺一环 | 列出用到的 `core` 子集并人工评审（未做） |
| RTIC 未经认证 | 调度器是"需被论证的可信基础" | 用其**设计**（静态优先级、编译期无锁）论证，而非其证书 |
| 覆盖率证据 | MC/DC 需合格工具链 | 门禁目前是**行覆盖率 ≥90%**（`cargo xtask coverage`，当前值以命令输出为准）；MC/DC 未做 |
| 无 IV&V 人员 | 认证硬性要求 | ❌ 缺（Q-F） |

## 5.5 capsule 化对安全论证的影响

capsule 化的目标是**可组合与可演进**，不是安全隔离。必须区分：

| 问题 | 本架构的回答 |
|---|---|
| safe capsule 会有 UB 吗？ | `forbid(unsafe_code)` + 依赖分层 + clippy 能显著降低，但不等于零缺陷证明 |
| capsule 会不会破坏别的 capsule？ | **会**。capsule 与 kernel 共享地址空间，一个 panic/死循环/越权 API 调用可影响整机 |
| 能不能把 capsule 当不可信第三方代码？ | **不能**。本架构只承诺“可信业务插件”；不可信代码需要 userspace/MPU 进程模型，明确不在范围内 |
| capsule 化会削弱现有安全机制吗？ | 不会直接削弱；但需要新增每 capsule 预算/健康/资源配额，否则“业务增多”会削弱实时性论证 |
| 更新是热替换吗？ | **不是**。业务与底座一起编译成整包固件；A/B 整包更新仍属 P4 |

因此安全案例里必须把“capsule 代码”列为**可信计算基（TCB）的一部分**，而不是隔离域。
如果未来业务来自第三方，必须先改变架构（进程/MPU），不能只靠 `forbid(unsafe_code)`
和代码评审。

更多边界见 [ADR-0008](../adr/0008-静态capsule化内核.md) 与
[`微内核与capsule架构`](../02-架构/微内核与capsule架构.md)。

## 8. 最高优先级的三个动作

1. **确认适用标准与目标等级**（Q-A）—— 它决定后面全部工作量。
2. **确认工具链路径**（Q-B）并与认证机构预沟通：这是唯一"卡脖子"且不在工程控制
   范围内的项。
3. **确认外部看门狗 `WDG_CTR` 由谁驱动**（Q-I）—— 在它确认之前，看门狗既不敢启用
   （`GAP(P5)`），也无法保证触发后是否只能断电恢复。
