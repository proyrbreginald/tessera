# 危害分析与安全需求

> ⚠️ **初步分析**，不是合格的 HAZOP/FMEA。它的作用是给出"危害 → 安全需求 →
> 机制 → 测试"这条链，并暴露还缺哪些安全分析输入。
>
> 范围：**平台级**。底座与应用场景无关，因此下面只覆盖平台能力自身的失效模式
> （内存、缓存、栈、故障可解释性、看门狗、升级、实时性）；接入方整机的危害分析
> 在其自己的仓库里做。

## 1. 危害清单（初步）

| # | 危害 | 触发场景 | 后果 | 严重度 |
|---|------|----------|------|--------|
| H1 | 内存被破坏（跨区域读写、DMA 看到旧数据） | 越界写；MPU 区域属性没生效；缓存属性错 | 静默数据损坏 / 不可解释的异常 | 高 |
| H2 | 脏缓存行回写 Flash —— 器件内容被"陈旧内容"覆盖 | 写入后未失效 D-Cache；"读-改-写"读到缓存里的旧行 | 数据损坏，且写入者以为写对了 | 高 |
| H3 | 栈溢出 | 深调用链 / 大对象进栈；栈大小靠"估一个够大的" | 串口全哑、HardFault、行为不可预期 | 高 |
| H4 | 故障不可解释（空死循环、无复位台账） | 故障处理器是空循环；不读 `SRC_SRSR`；无崩溃记录 | 现场只剩"串口安静"，同类故障反复发生 | 中（但影响改进闭环） |
| H5 | 看门狗失控：触发后只能断电恢复 | `WDG_CTR` 驱动源未确认就贸然启用；或故障后无自愈路径 | 设备停止服务且无法远程/现场恢复 | 高 |
| H6 | 升级失败不可恢复 | 覆盖唯一映像；掉电落在擦写中途 | 设备变砖（只能靠下载器救） | 中 |
| H7 | 关中断窗口超预算导致丢字节 | 长操作进关中断；ISR 超预算 | 串行字节丢失、实时性论证失效 | 高 |
| H8 | 业务 capsule 越权/失控 | capsule 共享内核地址空间；panic、死循环、资源耗尽、API 滥用 | 整机复位/停服/数据泄露；**没有内存隔离兜底** | 高 |

## 2. 危害 → 安全需求 → 机制

| 危害 | 平台需求 | 机制 | 可执行证据 |
|------|----------|------|-----------|
| H1 | **SF-1** 内存分区与缓存属性必须生效且可回读 | `mpu-regions` 区域表 + 编译期断言；BSP 写后回读打印；非缓存 DMA 池的属性自证 | 单测 `rbar_region_index_stays_in_low_nibble` 等（`cargo test`）；启动横幅 `region*:` / `ram dma :`；`cargo xtask check-memory` |
| H2 | **SF-1 + SF-6** 缓存里不得有 Flash 脏行；写入 fail-closed | Flash 区只读（AP=6，缓存里不可能出现 Flash 脏行）；擦写后按范围失效 D-Cache + ROM 清控制器缓冲；`check_erase`/`check_program` 闸门与 4 字节别名自检 | `board-support/src/cache.rs`；真机对照（D-Cache 开/关两种状态下自证）；`nor-flash` 单测（相位/对齐/只读拒绝） |
| H3 | **SF-2** 栈余量必须实测且不低于硬下限（≥30%） | 栈涂抹 + 启动打印 + `bench` 硬判据 | 启动横幅 `stack :`（实测峰值 29,860 B / 48 KiB，余量 39%）；`cargo xtask bench`；`memory-layout` 单测（含"涂抹漏栈底字"的回归） |
| H4 | **DB-1** 复位原因与故障现场必须可解释 | 槽 3 真实 `HardFault`（能拿 PC/LR/SP）+ 槽 4/5/6 刻意升级；`fault-decode` 解码；崩溃记录写 `.uninit`（跨暖复位存活） | `cargo xtask check-fault-handlers`（从链接产物断言）；启动横幅 `reset :` / `上次故障:`；`fault-decode` 单测 |
| H5 | **SF-4 + SF-5** 喂狗必须由健康门控决定；连续复位进安全状态 | `all_healthy` 判定 + 必需健康位原子聚合；`SafetySupervisor::on_boot` 连续复位闭环 | 单测 `sf_4_all_healthy_requires_every_required_bit`、`sf_5_repeated_resets_eventually_force_safe_state`；**固件已接线 SF-5（2026-10-19）**：启动时按 `.uninit` 复位计数判定 `Safe`，心跳上报 `safe=`/`wdg_ok`。⚠️ **看门狗未启用（`GAP(P5)`）、喂狗执行器未接线** |
| H6 | **EV-1 + SF-6** 升级必须可切换、可回滚；写入 fail-closed | 分区表预留 `bootloader`/`slot_run`/`slot_backup`/`boot_meta`；A/B 元数据双份 + 序号 + CRC；映像体积门禁；LUT 4 字节相位断言 | `cargo xtask check-flash-map` / `check-image`（LUT 相位、IVT、初始 SP）；`flash-layout` 单测。⚠️ **切换与回滚未实现（`GAP(P4)`），当前为单槽阶段** |
| H8 | **不在本架构范围** | 当前只承诺“可信业务 capsule”；capsule 代码计入 TCB。若需不可信第三方隔离，必须改用 userspace/MPU 进程模型（见 [ADR-0008](../adr/0008-静态capsule化内核.md)） | 代码评审 + 每 capsule 预算/健康/配额（目标）+ 看门狗（P5）；**不能**用 `forbid(unsafe_code)` 当成隔离证据 |
| H7 | **RT-1..RT-3 + DB-2** 关中断必须有预算且只能经测量入口；长操作不得进关中断；输出不得静默丢 | `realtime::BUDGET_IRQ_OFF_MICROS` 与字节间隔的编译期断言；`measured_cs` 唯一入口；写队列由 `idle` 属主执行；控制台队满分流 + 丢弃计数 | `cargo xtask check-critical`；心跳 `rt=ok`；`cargo xtask bench` 硬判据（`rt=ok`、`txdrop=0`）；`make bytecheck` |

## 3. 安全状态（Safe State）

🟡 **定义待确认**（Q-E）。当前实现采用的**假设**：

```text
Safe 状态 = 撤除有风险的输出（安全相关输出）+ 保持可观测性
```

`SafetySupervisor::outputs_permitted_with_link(link_alive)` 的判定是**与**关系，
且失联优先：只要外部链路不可信，就不允许驱动安全相关输出。`Safe` **不参与自动恢复**
—— 只有重新上电或显式维护动作才离开。理由是"安全状态被自动解除"本身就是一类危险失效：
现场必须能解释为什么会进去。

## 4. 状态迁移

```text
Normal ──degrade(原因)──▶ Degraded ──enter_safe(原因)──▶ Safe
   ▲                         │                            │
   └── on_selfcheck(true) ×3 ─┘                            └─ 不自动恢复
```

| 迁移 | 触发 | 实现 |
|------|------|------|
| `Normal → Degraded` | 链路错误率超阈值 / 存储校验失败可回退 / 错过截止时刻 / ISR 超预算 / 协议异常 | `SafetySupervisor::degrade` |
| `Degraded → Normal` | **连续 3 次**自检通过 | `on_selfcheck` + `RECOVERY_STREAK` |
| `任意 → Safe` | 失联超时 / 存储双份均损坏 / 连续 3 次复位 | `enter_safe` + `on_boot` |

## 5. 危害的反向覆盖检查（诚实结论）

| 危害 | 分析输入是否充分 |
|------|------------------|
| H1 | ⚠️ 区域表有单测、属性有回读；但"任意越界立即陷入"没有被逐场景验证，且**没有独立栈守卫**（那是 H3 的领域） |
| H2 | ⚠️ 缓存维护有真机对照证据；**介质侧写入路径的真机证据仍未闭合** —— `config::FLASH_SELFTEST_AT_BOOT` 的文档记录了尚未查明的失败用例（该开关默认关闭） |
| H3 | ✅ 有余量测量与硬判据；⚠️ **独立栈守卫区域未加** —— 溢出仍依赖 MPU 兜底 |
| H4 | ⚠️ 现场可读、跨暖复位存活；**掉电即失**（落盘未接），冷启动后的记录能力还不完整 |
| H5 | ❌ 看门狗未启用、喂狗未接线（`GAP(P5)`）—— 健康门控只有判据、没有执行器 |
| H6 | ❌ 基本未覆盖（当前单槽；A/B 切换与回滚未实现，`GAP(P4)`） |
| H7 | ⚠️ 运行期有实测台账与机器判据；⚠️ **启动期** `boot-init` 刻意设成"必然红灯"（结构性盲区的可见化），在 `init` 瘦下来之前不算达标 |

## 6. 还缺的安全分析输入

- 接入方整机 FMEA 与现场失效记录 —— 平台只覆盖平台级危害；整机层面需要接入场景。
- 安全状态（Safe State）的准确定义与"撤除输出"的物理路径（Q-E）。
- 外部看门狗 `WDG_CTR` 的驱动源与上电默认电平（Q-I，见 [`板级事实`](../03-硬件/板级事实.md) §2.5）。
- CAN 接收路径未通的根因与总线电气数据（Q-J）—— 需要第二块板/示波器，不靠改序列去猜。
- 目标安全等级（Q-A）与工具链路径（Q-B）—— 见 [`工具链鉴定策略`](工具链鉴定策略.md)。
