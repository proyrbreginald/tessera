# 架构与实现

> 运行时、中断、调度、capsule 边界与关键子系统的**核心事实**。历史 ADR 的内容已合并到本文。

## 1. 运行时：RTIC v2（静态任务）

- `no_std`、零 `async`、零通用堆；`alloc` 仅限固定块静态池（终端/诊断/压缩器状态）。
- 只有 **两个硬件中断**（RTIC 任务，均优先级 1）：

| 中断 | 任务 | 职责 | 为什么 1 |
|---|---|---|---|
| `LPUART1` | `console_rx` | 只读一个字节推入 RX 队列，其余全留 idle | 余量 4×（下一级已用尽） |
| `PIT` | `deadline_tick` | 32 位低半部溢出时抬 64 位时基 | 余量 50×，1 ms 周期 |

- RTIC 优先级是**字面量、编译器绑不到常量**，因此有门禁 `check-interrupt-priorities`：
  新增中断任务必须登记，PIT 的期望值从 `primitives::budget::prio::DEADLINE_TICK` 解析。
- **不再把可阻塞工作放 ISR**：ISR 只做 O(1) 搬运，长活在 idle 或维护作业里分片执行。

## 2. idle 协作循环（公平性设计）

每个 idle 轮次按相位推进，每步有上限，避免一个相位饿死其它相位：

```text
Input(终端 64 B/步) → Maintenance(FS / 日志 / 轮转 / 维护作业)
→ Health(健康位) → 1 Hz 内务 → wfi
```

- `FsService` 每轮最多推进 **1 条**常驻写请求（`step_at_most(1)`），剩余留到下一轮；
- 归档/轮转这类需要"同步完成再校验"的路径**逐笔提交后立即推进**（曾因改成纯排队导致
  FS 写失败并耗尽空闲块，A/B 证据在旧分析文档，已收敛为当前实现）；
- 归档分片 512 B；自动轮转检查最多 1 次/秒，且只在写队列空闲时投递维护作业；
- **已知残余**：一次归档里仍有个别同步 Flash 块操作（擦除/页编程不可再分），
  `idle-step` 实测约 60 ms 量级，达不到 1 ms；用 2 KiB RX 队列保证长步期间输入不丢
  （归档+1,600 B 输入突发实测 `rxdrop=0`）。

## 3. 实时预算与关中断

- 关中断只能走测量入口 `board_support::rt::measured_cs`；绕过它的临界区会被
  `check-critical` 拒绝 —— 没被测量的临界区等于没人知道窗口多长。
- 心跳（`beat on`）给出 `rt=ok|VIOLATION|none`（三态）、`dwt=ok|DEAD`、`txdrop=`、`rxdrop=`；
  `rt=none` 不等于合格，表示"一次都没测过"。
- DWT 会被启动期大范围内存测试清掉（根因未解释）：每次心跳检查并按需重装，`rearm=` 计数。
- 预算常量在 `primitives::budget`；实际值用 `cargo xtask context` / 心跳读取。

## 4. capsule 架构（编译期静态组合）

- **core kernel**：`board-support` + `firmware`，独占硬件/中断/调度；
- **基础 capsule**：纯逻辑层按能力划分（FS/日志/终端/实时仪表等）；
- **业务 capsule**：仓库外的 crate，依赖 `sdk`/`ports`，编译期静态组合；
- 不是运行期热替换/ELF 动态加载：`sdk` 是稳定门面（`Capsule<C>`/`CapsuleSet`/`Product`），
  组合根已外提为 `product`（只依赖 `sdk`），`firmware` 通过 `platform.rs` 注入实现。
- 未实现：S2 上下文能力对象化、S3 基础 capsule 外提与仓库外插件门禁（见 [安全与约束](安全与约束.md)）。
- safe capsule **不是安全隔离**：共享地址空间，不能防 panic/死循环/资源耗尽；不可信第三方
  代码需要 userspace/MPU 进程模型，本架构不做。

## 5. 关键子系统

| 子系统 | 核心事实 |
|---|---|
| 启动链 | `imxrt-rt` 构建期生成 FCB+IVT+boot data；运行期启动头只读；启动横幅回读时钟/PIT/FCB/MPU/栈/DWT/器件 ID |
| 控制台 | 中断只入队；TX 8 KiB 环形队列；队满按 `PRIMASK` 分流（开中断自旋、关中断丢弃并计入 `txdrop`）；**全系统只有一个 `DATA` 写入者** |
| 文件系统 | 日志结构 + 记录级 CRC + 版本完整性 + GC + 磨损分散；写队列由 idle 属主执行；掉电点穷举测试 |
| 日志 | 16 B 定长记录 + CRC-16 环形缓冲；默认不打终端；gzip generation 归档，索引在 FS 中 |
| 故障/复位 | 四个故障向量各有真实实现或刻意升级（`check-fault-handlers`）；`fault-decode` 解码 SRSR/CFSR/HFSR/入栈帧，跨暖复位记录 |
| 时基 | PIT 32 位链式 64 位微秒；`Timepoint` 不实现 `PartialOrd`，防跨回绕比较 |
| 安全门控 | 健康位全集才允许喂狗；失联优先"与"判据；安全状态不自动恢复（看门狗驱动源待确认，P5） |

## 6. 为什么不用 async / 通用堆 / defmt

- **async**：单执行器无抢占，硬实时不可论证；RTIC 静态任务的可预测性更适合本平台。
- **通用堆**：变长块+合并会破坏"无碎片、内存静态可知"的论证；固定块池失败返回空值。
- **defmt**：现场故障没有调试器；文本日志可读回、可落盘、可压缩归档。
