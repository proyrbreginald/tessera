# 并发与实时预算

> 一句话结论：RTIC v2 的**静态优先级**把"抖动上界可论证"变成编译期事实；
> DWT 仪表把"实际有没有超"变成每秒都在上报的实测判据。两者缺一不可 ——
> 纸面预算最危险的失效方式不是"算错了"，而是**没人知道它已经错了**
> （2026-10-12 真机上就抓到过一次：DWT 被清导致所有测量被跳过，心跳却仍在打 `rt=ok`）。

## 结论（先说结果）

- **并发模型**：RTIC v2 静态优先级，单核 Cortex-M7 @396 MHz，零 `async`
  （见 [ADR-0001](../adr/0001-运行时选型rtic-v2.md)）。
- **当前固件只有 2 个硬件任务**：`console_rx`（控制台接收）与 `deadline_tick`
  （1 ms 时基），**同为优先级 1**；其余全部在 `idle`（优先级 0）
  （`crates/firmware/src/main.rs` 的任务声明）。
- **总线任务的优先级已在 `primitives::budget::prio` 排好并断言**（`SERIAL_RX=2`、
  `CAN_TX=3`、`CAN_RX=4`），但任务本身尚未落地（**P2 缺口**，见
  [模块分解](模块分解.md) 与 `cargo xtask check-gaps`）。
- **最紧的硬约束**：115200 8N1 串行总线的字节间隔 **86.8 µs**；关中断预算 **80 µs**
  必须小于它 —— 这条关系由 `const_assert!` 钉住，改坏即**构建失败**
  （`primitives::budget` 与 `realtime` 各钉一半）。

> 中断绑定的逐项清单、优先级接线现状与 idle 轮询任务的公平性分析见
> [`中断与idle轮询分析`](中断与idle轮询分析.md)。

## 任务与优先级

**已落地**（代码事实）：

| 优先级 | 任务 | 触发 | 预算（最坏执行） | 理由 |
|--------|------|------|------------------|------|
| **1** | `console_rx` | `LPUART1` RX 中断 | < **20 µs** | 这块 LPUART 的接收 FIFO **只有 1 字节深**，必须在下一个字节到达（≈86.8 µs）前搬走 |
| **1** | `deadline_tick` | `PIT` 比较中断（1 ms） | < **20 µs** | 推进时基与健康计数；必须远小于 1 ms 周期，否则中断自我堆叠 |
| **0** | `idle` | 循环 | 一轮 < **1 ms** | 终端、健康聚合、**文件系统写队列属主**、诊断输出与喂狗决策 |

**已排好、尚未落地**（`primitives::budget::prio` 的编译期断言在等它们；串行/CAN 的
端口驱动属于 P2 缺口）：

| 优先级 | 任务 | 触发 | 预算 | 理由 |
|--------|------|------|------|------|
| 2 | `serial_rx` | 串行总线 RX 中断 | < 15 µs | 高优先级任务的最坏执行之和必须让字节间隔留有余量 |
| 3 | `can_tx_done` | CAN TX 中断 | < 10 µs | 释放邮箱 |
| 4 | `can_rx` | CAN RX FIFO 中断 | < 15 µs | 硬件 FIFO 有限，溢出即丢帧，必须最先清 |

表中的 ISR 数值是**预算**（设计上限）；真机上的实测由 DWT 仪表逐条统计
（见下文"DWT 实测体系"）。预算与实测都成立，实时性论证才算完整。

时基本身是 **PIT0+PIT1 链成的 64 位自由计数器**（24 MHz，1/24 µs ≈ 41.7 ns 分辨率），
1 ms 心跳挂 PIT2；回绕安全由 `primitives::time::Timepoint` **不实现 `PartialOrd`**
在类型上保证（**平台需求 RT-4**），漂移判据是 `make monitor` 的 uptime 对照（±2%）。

## 最紧的硬约束：串行总线的字节间隔

```text
86.8 µs = 10 bit ÷ 115200（8N1），常量取整到纳秒为 86 806 ns
```

115200 8N1 是本平台的**默认**串行总线配置（`primitives::budget::SERIAL_BAUD`，
接入方可调整 —— 改了之后下面的断言会重新校验可行性，这正是把它们放在代码里的目的）。
任何优先级高于串行接收的任务，其最坏执行时间之和若超过这个间隔，就会**丢字节**。
`budget.rs` 里的断言把它钉死（下面是节选；真实代码为满足 const 上下文的溢出检查
写成 `wrapping_*` 形式，逐字见源码）：

```rust
// 高优先级 ISR 预算之和必须小于半个字节时间（≥2 倍余量）
const_assert!(
    (ISR_CAN_RX_MICROS + ISR_CAN_TX_MICROS) * 1_000 * 2 < SERIAL_BYTE_INTERVAL_NANOS
);
// 单条最高优先级 ISR 也不得超过半个字节时间
const_assert!(ISR_CAN_RX_MICROS * 1_000 * 2 < SERIAL_BYTE_INTERVAL_NANOS);
// 15 µs @396 MHz = 5940 周期（同时验证换算函数本身）
const_assert_eq!(cycles_for_micros(15), 5_940);
// 优先级顺序本身也是设计：CAN 接收最高（FIFO 有限），其次是串行接收，再是心跳
const_assert!(prio::CAN_RX > prio::CAN_TX);
const_assert!(prio::CAN_TX > prio::SERIAL_RX);
```

**为什么放在代码里**：实时性论证最危险的失效不是"算错了"，而是"数字被改了而没人
重算"。把波特率调低、把某条 ISR 预算放宽，可行性结论可能翻转，但代码照样编译、
测试照样通过。现在任何一处改动只要破坏"留有余量"这个关系，**构建就失败**。

## DWT 实测体系（把"应该够快"变成每秒可判的数字）

预算只是设计上限；**实测**由 DWT 周期计数器 + [`realtime`](../../crates/realtime/src/lib.rs)
的 span 统计完成（**平台需求 RT-1 / RT-2**）：

- **测量入口唯一**：所有关中断都走 `board_support::rt::measured_cs`；`cargo xtask check-critical`
  拒绝旁路 —— "一个没被测量的临界区，就是没人知道有多长的关中断窗口"。
- **8 个 span**（`realtime::Span`）：`irq-off`（预算 80 µs）、`isr-pit`（20）、
  `isr-lpuart1`（20）、`shell-input`（1 ms）、`storage-crit`（80）、`boot-init`（故意宽松，
  见下）、`idle-step`（1 ms）、`boot-post`（4 s）。
- **分布**：`realtime` 对每个 span 维护 `floor(log2(cycles))` 直方图，`rt` 表新增 **p99 上界**列（桶上界，保守值；零分配的代价是粒度是 2 的幂）。

**入口抖动**：`diag` 额外输出 `tick jitter`（PIT 节拍到 ISR 入口的周期偏差，运行期清零启动期样本）；它是软件侧代理指标，不是 GPIO 边沿到 ISR 的精确延迟。

**三态结论**：心跳（`beat on` 开启；默认不打印）打 `rt=ok|VIOLATION|none` —— `none` 表示**一次都没测过**，
  它**不等于合格**：`cargo xtask bench` 把 `none` 判为失败而非通过。
- **启动期与运行期分开判**：`boot-init`（RTIC 用 `interrupt::disable()` 把整个
  `#[init]` 夹住，2026-10-19 实测约 8 ms；SDRAM 自检已搬到 `idle`）与 `boot-post`（SDRAM 暖复位快速自检 ≈143 ms；全片自检 ≈3.3 s（仅上电/故障复位））是分开判的启动期项
  启动期项。这样"一条已知会红的判据"不会污染运行期结论、也不会被现场无视。
- **DWT 自身要被监督**：心跳（`beat on` 后可见）里的 `dwt=ok|DEAD` 直接说明"上面那张 rt 表的数字还可信吗"；
  每秒维护检查 `DWT_CTRL`/`DEMCR`（与是否打印心跳无关），被清则**自动重装**并计数 `rearm=`。2026-10-12 真机
  实测确认：启动期 `memtest::pattern_test` 那一次 32 MiB 写遍+读遍期间它会被清成 0
  （根因未解释，处置与排查纪律见 `AGENTS.md` §5），重装后心跳继续 —— "运行期会不会
  再被清"因此是一个**实测数字**而不是推测。
- **`Cycles` 这个类型值得单说**：DWT 没在走时每次测量都拿到"0 周期"，而统计会把它
  记成"快得测不出来"。修法不是靠调用点记得判断，而是**零周期构造不出 `Cycles`**
  （`Cycles::new` 返回 `None`），于是"没测到"在类型上就不可能被记成"测到 0"。
- **`cargo xtask bench` 的硬判据**（与基线无关，违反即失败）：`rt=ok`、
  控制台 `txdrop=0`、栈余量 ≥ 30%。

最近一次真机抓包（2026-10-13）的读法：`rt=ok`、`txdrop=0`、`dwt=ok rearm=1`
（`rearm=1` 对应上文启动期已定位的清除 + 自动重装）。

## 还停留在预算的假设（🟡 不得当事实）

| 量 | 当前取值 | 状态 |
|----|----------|------|
| 串行总线波特率 | 115200 8N1 | **平台默认**（接入方可调整；改动会让编译期断言重新校验） |
| CAN 波特率 | 1 Mbps | ✅ 本板实测（PE 时钟 12 MHz，按官方公式反解位时序） |
| 各 ISR 最坏执行时间 | 上表数值 | 🟡 **预算值**；串行/CAN 任务的实测要等 P2 落地后才能给出 |
| 串行端口驱动 / CAN 接收路径 | 未落地 | **P2 缺口**（`cargo xtask check-gaps`；内部 loopback 已 PASS，外部总线接收未接） |

未确认项一经确认，**必须**改这些常量并让断言重新成立；实测值应写回注释。
这就是"先测后写"的可执行形式：假设被写在一个地方，且有门禁盯着它。

## capsule 的调度位置（目标形态）

capsule 化不允许业务自己创建 RTIC 任务或注册中断；否则优先级与关中断预算会被业务切碎，
实时性论证就不再成立。目标形态下：

| 执行位置 | 谁调用 | 约束 |
|---|---|---|
| `init` | 组合根在启动期调用 | 不得做长活；不得注册 ISR |
| `on_event` | core kernel 从 ISR 搬运后的事件分发 | 有界、非阻塞 |
| `step` | `idle`（默认）或固定周期钩子 | 必须可被打断；每 capsule 独立计量 |
| 硬实时控制 | core kernel 提供的固定优先级周期钩子 | 业务只实现钩子，不决定优先级 |

`Capsule` trait（name/phase/init/step）与组合根（`product`，S1）已落地，但**还没有**每 capsule
预算，只有全局 span（`shell-input`/`idle-step` 等）；因此“业务变多后实时性仍可论证”是目标，
不是现状。实现时必须先有每 capsule 预算/健康判据，再允许业务 capsule 接入（S2/S3）。

当前文件系统的**读**已经走属主上下文（`with_fs_read`，不关中断）；**写**仍只允许投递到
`write_queue`，由 `idle` 属主执行。这两条在 capsule 化后保持不变。

## 共享资源与同步策略

RTIC 的资源是 `&mut` 独占转移，**不使用全局锁**。跨上下文数据一律走消息/队列/原子：

| 资源 | 保护方式 | 理由 |
|------|----------|------|
| PIT / USART 外设 | RTIC `#[local]`（任务独占） | 无需同步 |
| 控制台 TX 队列 | 中断排空；**发送路径只能有一个 `DATA` 写入者** | 真机定位过"直写与中断排空互相覆盖 ⇒ 整行整行地丢"，详见 `AGENTS.md` §5 |
| 文件系统实例 | `critical_section::Mutex<RefCell<Option<..>>>`；**读**走 `with_fs_read`（属主上下文，不关中断） | **写绝不在关中断里**：擦一个 64 KiB 块真机量级 **几十毫秒** |
| 文件系统写请求 | `filesystem::write_queue`：生产者投递、`idle` 属主执行；**满则拒绝**（返回 `false`，不覆盖、不静默丢弃） | 投递本身只拷贝 ≤192 B，关中断窗口短且可测量（**平台需求 RT-3**） |
| 日志环 | SDRAM 固定区、`TextLog` 独占借用；级别过滤与 `.uninit` 尾部镜像 | ✅ 已接线；默认不输出终端 |
| 健康位 | 原子 `fetch_or`（ISR）→ `swap`（idle）→ 纯函数判定 | 见下 |

**健康门控的所有权划分**（"分层换来了什么"最直白的一处）：

```text
ISR（P1）         : HEALTH.fetch_or(DEADLINE_TICK, Relaxed)   ← 一次原子置位，有界
空闲任务           : HEALTH.swap(0) | IDLE → all_healthy(reported, REQUIRED)
（纯逻辑 primitives）: all_healthy 是纯函数                        ← 主机可穷举验证
```

策略是纯函数（可在主机上穷举"任一必需任务漏报即不喂狗"，**平台需求 SF-4**），
目标端只剩一次 `swap`。看门狗本身**尚未启用**（P5 缺口），`wdg_ok=` 目前是该项决策的
如实上报，而不是已经驱动物理看门狗。

## 为什么不用 Embassy（async）

`embedded-hal-async` + Embassy 是很好的技术，但它**不提供抢占式优先级**：单个执行器
按优先级顺序轮询任务，任一任务不让出（`.await` 不返回）就会阻塞其后所有任务。
在有硬实时接收任务的场景下，这意味着"串行总线的阻塞写"能直接推迟 CAN 的响应 ——
实时性从**结构保证**退化为**每个任务的让出纪律**。

在功能安全语境下更严重：认证要求"干扰自由"**可论证**，而"所有开发者永远记得及时
让出"无法论证。RTIC 把这一点变成编译期事实。

**重新评估的触发条件**：只有当所有总线的实时要求都放宽到"软实时"，且 IO 并发路数
≥ 4 时，async 的收益才可能超过其代价。

## 已知的未偿债务

- **DMA 与缓存一致性**。MPU + I-cache/D-cache 已于 2026-10-10 启用（Flash XIP =
  只读 + 可缓存，SDRAM = 写回 + 写分配 + 共享；真机实测 Flash 读吞吐
  46.6 → **51.8 MiB/s**，见 [资源利用与优化评审 §2](资源利用与优化评审.md)）。
  Flash 写入路径已在 2026-10-13 落地：编程/擦除后必须**失效对应范围的 D-cache 行**
  （`SCB.DCIMVAC`；ROM 的 `clear_cache` 清的是控制器侧预取缓冲，**不是** L1 D-Cache
  —— 两者都做过对照实验）。任何**新增**的 DMA 代码同样必须复查：缓冲区放非缓存区
  （OCRAM 顶部 64 KiB 的 `memory_layout::DMA_POOL`，MPU 上落在非缓存兜底区）或传输前后
  显式维护。**建议先配好 MPU 再引 DMA** —— 顺序反了会引入一类极难复现的数据损坏。
- **P2 未落地**：串行端口驱动与 CAN 接收路径都还没有任务本体；上表的串行/CAN 预算
  因此尚未被真机实测覆盖。
- **`boot-init` 仍然超标**（设计使然）。下一步是把 `#[init]` 里的长活继续外移；
  在搬完之前，这条红是正确的信号，不是要"调宽预算"的对象。
