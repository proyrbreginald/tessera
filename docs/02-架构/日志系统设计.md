# 日志系统设计（现场取证优先）

> capsule 视角：日志是**基础 capsule / 系统服务**；业务只通过端口/日志 API 写事件，
> 不直接拥有环、压缩器或文件句柄。见 [`微内核与capsule架构`](微内核与capsule架构.md)。
>
> 设计前提：**现场故障没有调试器**（[ADR-0004](../adr/0004-日志方案不使用defmt.md)）。
> 目标不是“把日志打出来”，而是“设备挂掉之后还能知道它死前经历了什么”。

## 1. 当前收敛结果（本仓库起点已包含）

- **只保留文本日志链路**：`/log/blackbox.log` + gzip generation 归档 + 64 B 索引。
- 早期二进制资产（16 B 记录、Ring、StringArena、LZ4、转置批次、`persist`）已**全部删除**。
- 日志 crate 只保留纯逻辑的 [`TextLog`](../../crates/log/src/text_log.rs) 与
  [`archive`](../../crates/log/src/archive.rs)，以及级别枚举 `level`。
- 旧的 `GAP(P3)` 随二进制资产删除而关闭；`check-gaps` 只剩 P2/P4/P5。

## 2. 生产链路

```text
log_event(level, tag, body)
  │  1. 级别过滤（LOG_LEVEL，默认 Info）
  │  2. 格式化到 ≤1 KiB 行缓冲
  ├──► TextLog：64 KiB SDRAM 文本环，按行 FIFO，满则丢最旧
  ├──► .uninit 崩溃尾部镜像（4 KiB 环形区，跨暖复位保留）
  └──► 终端通道（默认关闭；`log on` 显式开启）

idle / 命令上下文
  └──► log_try_flush()
         ├─ 环内 ≥512 B（或 `log flush` 强制）才刷
         ├─ 每次最多 1 KiB → FS 写队列 Append
         └─ idle 属主任务写 /log/blackbox.log

30 s / 8 KiB
  └──► gzip → /log/archive.<gen>.gz
         + /log/archive.idx（最多 3 个窗口）
```

## 3. 为什么这样分工

| 约束 | 设计后果 |
|---|---|
| 控制台 115200，86.8 µs/字节 | 热路径绝不直接打印；默认静默，`log on` 才输出 |
| 关中断预算 80 µs | 日志入环只在 `measured_cs` 内拷贝；不做 I/O/压缩 |
| 现场无调试器 | 日志先落 SDRAM 环，再由 idle 刷盘；崩溃时 `.uninit` 尾部兜底 |
| 零堆 | `TextLog` 只持有状态，缓冲区是固定 SDRAM 静态区 |
| Flash 擦写慢 | 落盘只走写队列，由 idle 属主执行；绝不进 ISR |

## 4. 级别过滤

`log::level::Level` 定义 `Error / Warn / Info / Debug`，`rank` 越小越紧急。

- 默认阈值 **Info**：`E/W/I` 落盘，`D` 默认过滤；
- `log level e|w|i|d` 设置阈值，非法值明确报用法，不猜默认；
- 被过滤的行计入 `LOG_FILTERED`，在 `log stats` 与 `log level` 中可见；
- `log on/off` 只控制终端镜像，不改变落盘；`log level` 同时影响两者。

## 5. 落盘写放大优化

旧行为 `LOG_FLUSH_BYTES = 1`：环里有一行就刷，每 192 B 形成一条独立 FS 记录
（记录头 + 路径 + 日志偏移 + CRC），导致记录数多、块分散、挂载扫描变慢。

现在：

- 环内累计 **512 B** 才自动刷；`log flush` 可强制推进；
- FS 写请求单条数据上限从 **192 B 提升到 1 KiB**；
- 一次 append 可带走约 1 KiB，记录数显著下降；
- 崩溃尾部由 `.uninit` 镜像兜底，因此不必为了“怕丢最后一行”而 1 字节就刷。

## 6. 崩溃尾部快照

`log_event` 在写入文本环后，同步把同一行写入 `.uninit` 的 4 KiB 环形区：

- `.uninit` 不被启动代码初始化，暖复位/看门狗复位后内容仍在；
- 每次写入后 `clean_dcache_range`，复位后读到的是 SRAM 最新内容；
- 启动时 `crash_log_init` 用 magic/长度校验，冷启动随机值直接丢弃；
- `log prev` 输出上一轮保留的尾部；`log clear` 会同时清空它。

这不是“HardFault 里碰文件系统”的危险路径：fault 发生时最后一行**已经在 RAM 里**，
文件系统写入仍只发生在 idle/命令上下文。

## 7. 终端命令

| 命令 | 行为 |
|---|---|
| `log` / `log stats` | 环、持久化计数、级别、终端开关、崩溃尾部、归档窗口 |
| `log on` / `log off` | 打开/关闭终端日志镜像（默认关闭） |
| `log level [e\|w\|i\|d]` | 查询/设置级别阈值 |
| `log dump` | 输出活动日志全部行（走流式读取 + 着色） |
| `log grep <子串>` | 过滤活动日志 |
| `log prev` | 输出 `.uninit` 中上一轮崩溃/复位前的尾部 |
| `log flush` | 强制推进写队列 |
| `log rotate` | 手动 gzip 归档并清空活动日志 |
| `log verify` | 逐窗口 gzip 解压 + 索引 CRC 校验 |
| `log restore [n]` | 恢复最近 n 个归档窗口到 `/log/restored.log` |
| `log clear` | 删除活动日志文件并跑 GC 回收其死记录（归档保留） |

## 8. `log clear` 的真实语义

旧实现只是覆盖写 `[log cleared]`，旧字节仍在 Flash，属于“逻辑清空”。

现在：

1. 在属主上下文 `fs.remove("/log/blackbox.log")` 落墓碑；
2. 调用 `fs.gc()` 回收该文件留下的死记录；
3. 清空 SDRAM 文本环、崩溃镜像与持久化计数；
4. 归档窗口**保留**（需要清归档请显式删除对应 generation 文件）。

它不会擦除含其它活数据的块；`gc` 只擦确认没有活记录的块。因此这是“文件级真实清空”，
不是整片 Flash 的安全擦除。

## 9. 归档

- 每个窗口一个 `/log/archive.<8 位十六进制>.gz`，不再整文件复制；
- `/log/archive.idx` 固定 64 B，最多 3 个窗口；索引是缓存，窗口文件是事实来源；
- 轮转前先 `log_try_flush(true)`，避免最后一段还留在环里；
- gzip 压缩在 SDRAM 备用栈执行；解压走零分配路径；
- 已知债务：索引更新与旧窗口删除之间掉电可能留下孤儿窗口，不会自动删除。

## 10. 已知边界

- 文本日志无结构化字段；需要机器解析时应在行格式上增加稳定标签；
- 活动窗口 8 KiB、归档 3 个，保留量有限；
- `log clear` 只清活动文件，不清归档；
- 崩溃镜像只有 4 KiB，超出后覆盖最旧文本；
- 文件系统层面的挂载/读路径扫描与 GC 稀疏块问题另见
  [`当前进展`](../00-索引/当前进展.md) 与 [资源利用评审](资源利用与优化评审.md)。
