# 分层与依赖规则

> 规则不是靠人记的：`cargo xtask check-layering` 从 **Cargo 依赖闭包**逐 crate 强制
> （连 `dev-dependencies` 也查，且做双向比对：未登记的纯逻辑 crate 也会让它失败）。

## 1. 依赖表（20 个成员 crate）

下表的顺序即"从下到上"：每一行只允许依赖它**下方**的行。
前 18 行 = `cargo xtask pure-crates` 的输出（纯逻辑层，可在主机上测试）；
最后两行是硬件相关层。

| crate | 允许依赖 | 说明 |
|---|---|---|
| `primitives` | `heapless`、`static_assertions` | 平台原语：时间（回绕安全的 `Timepoint`）、实时预算（`const_assert`）、健康门控/安全状态机、零分配格式化、PRNG、CRC-16/CRC-32 |
| `wire-format` | `primitives` | 线路编解码：Modbus-RTU 帧结构与结构校验；功能码是**不透明 newtype**，不解释设备语义 |
| `ports` | `primitives` | 端口契约（`Bus`/`Clock`/`Store`/`LogSink`/`RawMedium`）、半双工类型状态机、双份存储策略 |
| `simulator` | `primitives`、`ports`、`wire-format` | 主机替身：脚本化总线、手动时钟、可注入掉电的介质、捕获日志（仅测试/自检，绝不进固件目标） |
| `sdram-timing` | `primitives` | SDRAM 规格、SEMC 时序换算、内存测试算法（纯算术；写寄存器在 BSP） |
| `shell` | `primitives`、`realtime` | 串口终端：行编辑、ANSI、命令分发（命令表是唯一来源） |
| `flash-layout` | 无 | Flash 用途划分：分区表是 BSP / 门禁 / 文档的**共同事实来源** |
| `filesystem` | `primitives` | 日志结构文件系统：记录级 CRC、版本完整性、GC、磨损分散、写队列（介质只认 4 个方法） |
| `mpu-regions` | `primitives` | MPU 区域表与 `RBAR`/`RASR` 编解码（写寄存器在 BSP；回读也走同一解码函数） |
| `memory-layout` | `primitives` | 片内内存布局事实 + 栈涂抹测量算法 + 预算常量（不依赖任何其它 crate：布局是底部事实） |
| `realtime` | `primitives`、`static_assertions` | 实时性仪表：span 注册表、预算判据、关中断最外层语义（一个寄存器都不读） |
| `fault-decode` | `primitives` | 复位原因（`SRC_SRSR`）与故障现场（`CFSR`/`HFSR`/入栈帧/跨暖复位记录）的解码 |
| `block-pool` | `primitives`、`static_assertions` | 固定块静态池的分配**策略**（内存本身在 BSP；失败是一个值） |
| `log` | `primitives` | 日志核心：定长记录 + 环 + 三层字符串 + LZ4 + 转置布局 |
| `gzip` | `primitives`、`miniz_oxide` | gzip 容器 + DEFLATE（压缩侧的状态落 BSP 的大块静态池） |
| `nor-flash` | `primitives`、`static_assertions` | QSPI NOR 的纪律：几何、对齐/范围校验、命令相位一致性、自证目标、FlexSPI 寄存器常量 |
| `sdk` | 无 | 业务 capsule 契约：`Capsule<C>`（name/phase/init/step）、固定容量 `CapsuleSet`、`Product` 模板与 `prelude`；不依赖硬件 |
| `product` | `sdk` | 产品组合根：声明 capsule 集合/顺序/容量（默认 6 个基础服务 + 2 个业务槽），通过 `Platform` 注入服务；**只依赖 `sdk`** |
| `board-support` | 纯逻辑层 + `imxrt-hal`/`imxrt-ral`/`imxrt-rt`/`imxrt-boot-gen`/`cortex-m*` | **唯一**允许接触寄存器的库 crate；每一处 `unsafe` 带 `SAFETY` 并计入 `unsafe.budget` |
| `firmware` | `board-support` + 纯逻辑层 + `rtic` | RTIC 应用与平台注入（bin）：只做接线、任务划分、健康位原子聚合；产品组合策略在 `product`；`unsafe` 仅故障处理器与一次性板级初始化 |

**接入方的业务 crate 不在本仓库**：它应当只依赖纯逻辑层（`ports`/`primitives` 等），
在主机上用 `simulator` 测试；目标侧由 `firmware` 或接入方自己的组合根接线。
见 [`业务接入指南`](业务接入指南.md)。

### 1.1 capsule 视角下的三层

| 层 | 当前 crate（或来源） | 依赖规则 |
|---|---|---|
| core kernel | `board-support`、`firmware` | 可依赖硬件 crate，可使用 unsafe；中断/调度/内存/Flash 原语归它 |
| 基础 capsule / kernel-support | 18 个纯逻辑 crate | 禁止 unsafe、禁止硬件依赖；只通过端口/纯逻辑 API 交互 |
| 业务 capsule | 仓库外 crate | 只依赖 capsule SDK（目标形态）或 `ports`/`primitives`（当前）；禁止 `board-support`/`firmware`/RTIC/unsafe |

“基础 capsule”目前没有物理拆分：它们仍在同一个工作区、同一个依赖表里。
`sdk` 门面与产品组合根（`product`，S1）已落地；S2 上下文能力对象化与 S3 基础 capsule 外提尚未实现。
`cargo xtask check-capsules` 检查 `sdk` 保持纯逻辑、插件 crate 不直接依赖硬件/组合根（**只扫仓库内**）。
见 [`微内核与capsule架构`](微内核与capsule架构.md)、[`产品组合根外提设计`](产品组合根外提设计.md)、
[ADR-0008](../adr/0008-静态capsule化内核.md) 与 [ADR-0010](../adr/0010-产品组合根外提.md)。

## 2. 为什么"层"是编译期事实

真实的寄存器写入、中断时序与电气连接**无法**用主机测试替代。既然如此，就让不可测的
部分尽可能薄，并让"纯逻辑层不依赖任何硬件"成为 **Cargo 依赖图上的事实**：

- 纯逻辑 crate 的 `Cargo.toml` 里**没有** `imxrt-*`/`cortex-m*`/`rtic`，
  所以"上层意外引入硬件依赖"会在**构建期**失败，而不是靠代码评审；
- `check-layering` 另外解析依赖闭包，防止"通过中间人偷偷继承"（例如
  `ports` → 某个引入 `cortex-m` 的 crate 也会被抓住）；
- 新增一个纯逻辑 crate 时要把它加进 `xtask` 的 `PURE_CRATES`，否则门禁会因
  "未登记的纯逻辑 crate"失败（双向比对）。

## 3. unsafe 边界

- 每个纯逻辑 crate 以 `#![forbid(unsafe_code)]` 开头（`check-lint-headers` 强制该行存在）；
- `board-support` 与 `firmware` 允许 `unsafe`，但**每一处**必须：
  1. 紧邻一条 `// SAFETY:` 说明（`check-unsafe` 强制配平）；
  2. 计入 [`unsafe.budget`](../../unsafe.budget)（只减不增；预算 81，实测 80，以 `check-unsafe` 为准）。
- 规则的口径：**`unsafe` 不是被禁止的，而是被隔离且有预算的**。当一段逻辑可以
  被主机穷举测试时，它就不应该出现在 `unsafe` 附近 —— 这类搬运（例如
  `RBAR` 编解码、栈余量算术）已经发生过多次。
- **`forbid(unsafe_code)` 不等于安全隔离**：它只排除 UB；同地址空间内的 capsule
  仍可能 panic、死循环或耗尽资源。可信插件模型与“不可信第三方隔离”是两件事，
  见 [ADR-0008](../adr/0008-静态capsule化内核.md)。

## 4. 类型状态机（为什么在 `ports`）

半双工总线最常见的一类现场故障是"**方向切换顺序错**"：还没发完就切到接收、
或者在应答没到之前又发一帧。这类 bug 只在特定时序下复现，运行时报错等于把问题
推到现场。

[`bus::Link`](../../crates/ports/src/bus.rs) 把顺序抬进类型：只有 `Idle` 状态能发，
只有 `AwaitingResponse` 状态能收。写错顺序是**编译错误**。它依赖 `Bus` trait，
所以契约与状态机必须在同一个 crate 里 —— 否则会形成 core ↔ ports 的循环依赖。

同样的思路还用在：

- 时间：`Timepoint` **不实现 `PartialOrd`**（"用 `<` 判到期"在计数器回绕后失效）；
- 记录：`Cycles` 是 `NonZeroU32`，`record(span, 0)` 是编译错误（`check-compile-fail` 的负例）；
- 存储：`Store::write_atomic` 的原子性无法用类型表达，于是靠"双份 + 序号 + CRC"的
  策略实现 + 掉电穷举注入测试（见 [`测试策略`](../04-开发/测试策略.md)）。
