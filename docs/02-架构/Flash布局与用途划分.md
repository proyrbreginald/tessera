# Flash 用途划分

> capsule 视角：文件系统是**基础 capsule / 系统服务**，业务 capsule 只拿 `Store`/capability
> 句柄，不直接算分区偏移；Flash 驱动与分区表属于 core kernel 的事实。
> 见 [`微内核与capsule架构`](微内核与capsule架构.md)。
>
> 分区表的**唯一事实来源**是 [`crates/flash-layout`](../../crates/flash-layout/src/lib.rs)：
> BSP 引用它、`cargo xtask check-flash-map` 遍历它、本文的表格由同一门禁逐行核对
> （分区名 + 偏移必须与代码一致）。三者不可能漂移。

## 寻址：整片 32 MiB 可用（靠专用 4 字节操作码，不靠模式切换）

`W25Q256` 上电是 **3 字节地址模式**，上限 16 MiB。要打开整片有两条路：

| 路线 | 做法 | 代价 |
|---|---|---|
| A. 全局 `EN4B` 模式切换 | FCB 的 device mode 序列发 `0xB7`，器件整体切到 4 字节地址模式 | 器件被留在**非上电默认**状态：序列没生效而 LUT 已是 4 字节 → Boot ROM 读不到映像 → 变砖，只能靠 BOOT_MODE 引脚 + 串口下载器恢复 |
| **B. 专用 4 字节操作码（本项目采用）** | 读 `0xEC`、页编程 `0x34`、扇区擦除 `0x21`、块擦除 `0xDC`，地址相位一律 32 位（`0x20`） | 什么都不留在器件里：器件始终是上电默认状态，而每条命令**自带** 4 字节地址；启动路径的风险不增加 |

选 B 的依据是**本板既有 C 固件参考实现的已知正确配置**
（`winshare/.../imx_nor_flash/nor/flexspi_romapi.c`，那份固件在这块板上跑过现场），
读/写/擦序列逐项照抄。

**这条前提被两道机制锁住**（否则后果是静默别名：越过 16 MiB 的读写落到低 16 MiB 上，
"擦日志区"可能擦掉启动头）：

1. **构建期**：`cargo xtask check-image` 从链接好的 ELF 里按 FCB 偏移 `0x80` 读出 LUT，
   断言**三个序列**（读 `0xEC` / 擦 `0x21` / 写 `0x34`）的命令字节与地址相位 = `0x20`；
2. **运行期**：每次启动跑一次别名自检 —— IVT 魔数 `0x402000D1` 固定在偏移 `0x1000`，
   若读 `16 MiB + 0x1000` 也得到这个魔数，就说明高位地址被丢掉了。启动横幅会打印
   `flash 4B : 4 字节寻址自检 PASS/FAIL`。

## 设计取向：分区只留启动与升级必需的，应用数据全部进文件系统

第一版方案把每类应用数据各切一个物理分区（共 15 个分区）。**那是过度设计**：

1. 每多一个分区，就多一套"偏移 / 大小 / 对齐 / 掉电策略 / 磨损预算"要论证与维护；
2. 而这些差异本质上是**文件语义**的差异，不是物理布局的差异：

   | 数据的写法 | 语义 | 用文件怎么表达 |
   |---|---|---|
   | 整体覆盖 | 内容整体替换 | 整文件重写 |
   | 长期有效、偶尔更新 | 标定型 | 整文件重写 |
   | 只追加 | 台账/日志型 | 追加写 + 回绕 |
   | 写入一次 / 整块替换 | 出厂信息、整包数据 | 整文件重写 |

3. 分区表越大，`check-flash-map` 要维护的不变量越多，越容易退化成"两处事实"。

因此最终收敛为 **6 个功能分区**：启动头、引导程序、应用槽 A/B、A/B 元数据、
以及**一整块文件系统**。应用数据不再各占一个分区。

## 1. 事实基础

| 事实 | 数值 | 来源 / 证据 |
|---|---|---|
| Flash 器件 | Winbond **W25Q256JVEQ**，32 MiB，4 KiB 扇区 / 64 KiB 块 / 256 B 页 | 原理图 p13 |
| 启动头位置 | FCB 在偏移 `0`（512 B），IVT 在 `0x1000`，boot data 紧随 | `imxrt-rt` 链接脚本 + `check-image` 断言 |
| **寻址宽度** | FCB 的 LUT 用**专用 4 字节地址操作码**（读 `0xEC`，地址相位 `0x20`） | [`flash.rs`](../../crates/board-support/src/flash.rs)；`check-image` 从镜像断言 |
| ⇒ 可用窗口 | **整片 32 MiB** | 4 字节操作码自带上限；启动时另有一次别名自检 |
| 擦除粒度 | 4 KiB（扇区）；块擦除 64 KiB | 器件手册 |
| 当前映像 | **205,648 B**（2026-10-22 本机链接产物） | `cargo xtask check-size` |

**同板既有固件的分区表**（`winshare/test/master-control-board-a-06`，已现场验证）：
bootloader 0x00000..0x10000（64 KiB）/ app 0x10000..0x100000（960 KiB）/
upgrade 0x100000..0x300000（2 MiB）/ filesystem 0x300000..0x2000000（29 MiB）。
两条可直接复用的结论：**引导程序区 64 KiB**、**应用槽必须 ≥2 MiB**
（他们的 960 KiB 槽位已被实测 1,062,020 B 的映像撑爆）。

## 2. 分区表

全部 4 KiB 对齐；`SECTOR=4 KiB`、`BLOCK=64 KiB`、`XIP_WINDOW=32 MiB`（= `FLASH_SIZE`，
即**整片可用**，因为 LUT 用的是专用 4 字节地址操作码）。

| 分区 | 偏移 | 大小 | 用途 | 掉电策略 |
|---|---:|---:|---|---|
| `boot_header` | `0x000000` | 8 KiB | FCB + IVT + boot data | 运行期只读 |
| `bootloader` | `0x002000` | 248 KiB（256 KiB 区域含启动头） | 引导程序：选槽、校验、回滚（**未实现，P4**） | 整区（仅升级时） |
| `slot_run` | `0x040000` | 2 MiB | 实际运行槽 | 整槽（仅升级时） |
| `slot_backup` | `0x240000` | 2 MiB | 备份槽（新固件先写这里） | 整槽（仅升级时） |
| `boot_meta` | `0x440000` | 64 KiB | A/B 元数据：当前槽、试启计数、已确认 | 双份 + 序号 + CRC |
| `filesystem` | `0x450000` | **约 27.69 MiB** | **全部应用数据** | 由文件系统保证 |

### 阶段 1 的已知过渡状态

Bootloader 尚未实现。当前阶段 1 映像仍从 Flash 偏移 0 起，映像大小约 191 KiB，
会**临时占用 `bootloader` 预留区**（`0x2000..0x40000`）的一部分；它不会进入
`slot_run`（`0x40000`）及之后的分区。

这是显式登记的过渡状态，`check-flash-map` 会：

- 允许映像覆盖 `bootloader` 区，并打印“阶段 1 临时占用”的说明；
- 但拒绝映像进入 `slot_run` 或更后面的分区。

Bootloader 接入后，应用映像必须迁到 `slot_run`，这个临时覆盖状态随之结束。

两条"必须独立成区"的论证：

- `boot_meta` **不能放进文件系统**：引导程序要在**没有文件系统**的情况下读它
  （文件系统跑起来之前必须已经知道启动哪个槽）；
- `boot_header` **绝对不能运行期写**：写坏它 = Boot ROM 不启动 = 只能靠 BOOT_MODE
  引脚 + 串口下载器恢复（这是"绝不在运行期写启动头"的原因）。

## 3. 应用数据 = 文件

文件系统分区由 [`filesystem`](../../crates/filesystem/src/lib.rs) 管理（日志结构、
记录级 CRC、版本完整性、垃圾回收、磨损分散）。平台约定文件在
[`board_support::config::files`](../../crates/board-support/src/config.rs)：

| 路径 | 语义 |
|---|---|
| `/config/config.bin` | 应用参数（整体覆盖） |
| `/config/calib.bin` | 现场标定（长期有效） |
| `/log/reset.log` | 复位台账（只追加） |
| `/log/blackbox.log` | 事件黑匣子（只追加文本日志） |
| `/log/spool.log` | 遥测/事件缓冲（只追加） |
| `/factory/factory.bin` | 出厂信息（写一次） |

### 3.1 路径语义：Linux 风格**绝对路径**，但不是完整 VFS

`filesystem::path` 提供绝对路径与目录合成，**没有独立目录 inode**：

- 文件记录里存**完整绝对路径**（如 `/log/blackbox.log`），目录由路径前缀隐含；
- `list_dir("/")` / `list_dir("/log")` 从现有文件路径**合成**直接子项（文件给大小，
  子目录给 `None`），不额外占介质/RAM；
- 路径规则：以 `/` 开头、总长 ≤31 B、可打印 ASCII、不允许 `//`/`.`/`..`/尾 `/`；
- 旧的**无 `/` 名字**仍可读（迁移兼容），但新代码一律用绝对路径；
- 终端命令：`ls [path]`、`cat <path>`、`fstat <path>`、`rm <path>`、`cd [dir]`、`pwd`（`stat` 已作为 `status` 别名占用）；路径参数支持相对当前目录、`.` 与 `..`。

**取舍**：没有 `mkdir`/`rename`/硬链接/空目录/权限位——这些需要目录对象与额外
掉电恢复逻辑。对“现场日志/配置/标定”这类用途，换来的是**零新增介质格式、零新增
RAM、掉电语义与现有记录完全一致**。`list_dir` 的去重是 O(n²)，但平台文件数上限是 16，
实际代价可忽略。

**为什么必须"先比较再写"**：同一个内容被反复写入时，若不比较就擦写，双份区域的
寿命会从"几十年"掉到"数月" —— 这条纪律对"外界反复推送同一份数据"的接入场景尤其重要。

**单一属主**：文件系统是持久化的唯一写入者。过渡期曾出现过"三张原始偏移表与文件系统
块 0 物理重叠"的双属主事故（其中一方不知道自己会被另一方擦掉），现在这条由
`check-flash-map` 的几何判据变成**不可能重新引入**：除文件系统外，任何分区与文件系统
区间相交即失败。

## 4. 启动与升级

### 阶段 1（当前）

```text
Boot ROM → FCB(0x0) → IVT(0x1000) → 应用（映像从偏移 0 起，单槽）
```

`check-flash-map` 在这里检查"映像不得越过第一个数据分区（`boot_meta`，`0x410000`）"：
当前 205,648 B 的映像离红线还有约 **22 倍**余量（4,259,840 ÷ 205,648）。
`bootloader` / `slot_run` / `slot_backup` / `boot_meta` 四个分区**已预留且由门禁保护**，
但"选槽、校验、回滚"的代码**尚不存在** —— 这是 **P4 缺口**
（`cargo xtask check-gaps` 会把它连 `文件:行` 一起列出来）。

### 阶段 2（A/B 双槽，属 P4 缺口，尚未开始）

```text
Boot ROM → FCB → IVT → bootloader(0x2000)
                          ├─ 读 boot_meta（双份 + 序号 → 取新且 CRC 正确的一份）
                          ├─ 选中槽位 → 校验映像头（magic/长度/CRC/版本）
                          ├─ 试启计数 +1（仅在"未确认"窗口内写）
                          └─ 跳转到该槽
                                   ↓
                              应用启动
                                   ├─ 自检通过 → 写"已确认"
                                   └─ 自检失败 → 不确认 → 计数达阈值后自动回滚
```

升级**只写非活动槽**，全程不碰在跑的映像。**不做搬运式升级**（既有固件的
app/upgrade 两分区做法）：搬运要先把活动映像擦掉再拷入，中途掉电就没有可启动映像。

## 5. 对文件系统的要求

| 要求 | 为什么 |
|---|---|
| 记录级 CRC + 序号 | 唯一能同时对付"写了一半"与"擦了一半"的手段 |
| 日志结构 | 掉电时不必维护"就地更新"的原子性；顺带把擦除摊到全片（磨损分散） |
| 垃圾回收 | 日志结构必须回绕，否则空间会用尽 |
| 先比较再写 | 内容未变就不该擦写，否则双份区域的寿命从"几十年"掉到"数月" |
| 无分配、定长上限 | 固件零通用堆；文件名 ≤31 字节、文件数 ≤64 这些上限写进契约并用测试钉住 |
| 长操作不在关中断里 | 擦一块真机量级几十毫秒（见 §8.3），而串行总线字节间隔只有 86.8 µs —— 写入一律经 `filesystem::write_queue` 由 `idle` 属主执行（**平台需求 RT-3**） |

## 6. 与门禁的联动

`cargo xtask check-flash-map` 每次 `make verify` 都检查（基于同一份分区表数据）：

1. 分区**首尾相接**：不允许重叠，也不允许留未声明的缝隙；
2. 每个分区 4 KiB 对齐、大小为 4 KiB 整数倍；
3. 全部落在 32 MiB 的 XIP 窗口内（`XIP_WINDOW == FLASH_SIZE`，与器件容量一致）；
4. **单一属主**：除文件系统外，任何分区不得与文件系统区间相交；
5. `slot_run.size == slot_backup.size`（复制恢复的论证前提）；
6. 启动头位于偏移 0 且标记为运行期只读；
7. 当前映像放得进 `slot_run`，且在阶段 1 不越过第一个数据分区（`boot_meta`，`0x440000`）；
8. **文档的分区表**（本文 §2）逐行与代码一致（分区名 + 偏移，机器核对）。

另有 crate 内主机测试（`cargo test -p flash-layout` 口径），其中一条**刻意钉住
"分区数量保持精简"**：想再切一个专用分区，就必须先改掉那个数字，从而被迫回答
"为什么不能用文件表达"。

## 8. 擦写能力：已实现（寄存器级 + ROM 驱动）

### 8.1 现状

- **擦除与页编程的驱动面已落地**：`nor-flash` 提供几何与判据（扇区对齐、不跨页、
  不碰启动头、命令相位），`board-support` 的 `flexspi_ip` 走**寄存器级 IP 命令**，
  `rom_flash` 复用 ROM 驱动；介质层（`store.rs`）把两者接在"读-改-写"的整页语义上。
- **页编程最终确认必须走寄存器级**：真机对照实验中 ROM 的 `program` 在本板
  **报成功但不写**（器件读回全 `0xFF`），而同一时刻寄存器级路径写后回读逐字节一致。
  ⇒ `rom_flash::program_page` 已转调 `flexspi_ip::program_page`，两条路径共用同一套
  分块逻辑（分叉的判据比没有判据更危险）。
- **真机自证曾全部通过**（2026-10-13 深夜，修复后的运行）：
  `自证(跨页+非对齐) PASS 擦写三例=ok bad=0 擦回=ok sector=0x1fff000` ——
  用例从 `sector+200` 写 300 字节，**同时覆盖"非页对齐起始（第 1 页走读-改-写）"与
  "跨页拆分"**，且断言写入范围之外仍是擦除态；同日 `reg 写路径自证 PASS detail=0`
  （整页 + XIP 回读 + 擦回空白）。此前扩展成"四用例"（含 64 KiB 块擦除）的自证报过
  FAIL（2026-10-12），已定位并修复 —— 两个独立根因见 §8.2；修复后的整组用例复测
  应在上机时重跑。
- 启动开关 [`FLASH_SELFTEST_AT_BOOT`](../../crates/board-support/src/config.rs) 默认**关闭**
  （它每次启动都写一次器件，只适合一次性验证）。

### 8.2 沿路修掉的三条硬事实（都在代码注释里留了现场记录）

1. **`IPCR1.IDATSZ` 必须等于"这一个 IP 命令真正送进 FIFO 的字节数"** ——
   声明整页 256 B 却只灌 32 B 会让写相位停摆；分块单位是 `flexspi_ip::ip_burst_bytes()`。
2. **写后必须维护内核 D-Cache**（`SCB.DCIMVAC` 按范围失效）：决定性对照是
   "把 D-Cache 关掉后两条自证全部 PASS"。ROM 的 `clear_cache` 清的是控制器侧
   预取缓冲，**不是** L1 D-Cache，不能替代。
3. **控制器复位（`clear_cache`）绝不能放进内层循环**：它是 FlexSPI 软件复位，
   会清掉 AHB 预取缓冲 —— 真机实测同一基准因此从 3,401,993 KiB/s 掉到 48,473 KiB/s
   （**70 倍**量级），而后者才是诚实的器件带宽。现行做法：内层只做廉价的 D-Cache
   失效，控制器复位每次编程/擦除只做一次。

### 8.3 实测的擦写耗时（此前一直是空的数字）

| 操作 | 真机实测（2026-10-12/13） | 含义 |
|---|---|---|
| 擦 4 KiB 扇区 | ≈ **33.4 ms**（2026-10-19 基准：32.2–33.8 ms） | 直接印证"擦写绝不能进关中断"（预算 80 µs） |
| 擦 64 KiB 块 | ≈ **557 ms** | 文件系统 GC 的最坏单步 |
| 页编程一页（256 B） | ≈ **542 µs**（2026-10-19 基准：539–544 µs） | **器件页编程本身**（W25Q256 典型 0.4 ms、最大 3 ms）；早期批写实验无收益，已撤销 |

### 8.4 启用 4 字节寻址带来的新不变量

"整片 32 MiB 可用"不是一个可以单独成立的事实 —— 它的前提是 LUT 保持 4 字节地址相位。
因此这两件事被绑在一起：

| 机制 | 位置 | 检查什么 |
|---|---|---|
| 构建期断言 | `cargo xtask check-image` | 链接好的镜像里 FCB 偏移 `0x80` 的 LUT：读 `0xEC`/擦 `0x21`/写 `0x34`、地址相位 `0x20` |
| 编译期断言 | `board-support::config` | `ADDRESSABLE_BYTES == flash_layout::XIP_WINDOW` |
| 单测 | `flash-layout` | 可寻址边界（窗口内为真、窗口处为假）、所有分区都在窗口内、分区数恰好 6 |
| **运行期自检** | 每次启动 | 用 IVT 魔数检测别名（见下） |

运行期自检的含义：`XIP + 0x1000` 必须是 IVT 魔数（否则我们对映像布局的理解已经错了）；
`XIP + 16 MiB + 0x1000` **必须不是** IVT 魔数。两次读、每次启动都跑，启动横幅打印结果 ——
它检查的是**控制器此刻的真实行为**，而不是源码里的意图。

**两条现场操作约束**（都是真机上踩出来的）：

1. **改动分区布局或 FS 磁盘格式后必须全片擦除**（`bash scripts/flash.sh -e chip`）。
   ⚠️ `make flash` **不会**带 `-e chip`（脚本只把多余参数原样透传给 pyocd），
   "改布局后烧一次"**不等于**全片擦除。否则新分区里是**上一版固件的数据**：实测中
   FS 分区里残留着这块板既有 C 固件的内容，文件系统挂载扫描因此跑了 **21 秒**
   （非擦除块要逐字节重同步），看起来像"启动卡死"。（原理与记录见 `AGENTS.md` §5。）
2. **pyocd 目前无法在 16 MiB 以上编程**（目标内存映射只声明到 16 MiB，
   报 `no memory region defined for address 0x61800000`）。这不影响运行期
   （XIP 已验证可访问整片），但将来若要让调试器/产线工具直接写上半区，
   需要修目标映射或改走固件自己的擦写路径。
