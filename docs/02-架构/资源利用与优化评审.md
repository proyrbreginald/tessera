## 2. P0：MPU + 缓存（已实施）

### 2.1 做了什么

`crates/board-support/src/mpu.rs`：配置 8 个 MPU 区域，再打开 I-cache 与 D-cache；
由固件在 `board::init()` **之前**调用一次。开关 `config::MPU_AND_CACHE_ENABLED`
保留，用于"开/关"对照测量（生产为 `true`）。

### 2.2 依据不是推理，而是本板既有固件的已知正确配置

取自 `winshare/.../bsp/board/board.c` 的 `BOARD_ConfigMPU`（那份固件在这块板上
跑过现场），只改两处以符合**本板事实**：Flash 区域 8 MB → **32 MB**（实装 W25Q256），
SDRAM 32 MB 保持。

| 区域 | 基址 | 大小 | AP | TEX/S/C/B | 含义 |
|---|---|---|---|---|---|
| 0 | `0xC000_0000` | 512 MB | 3 | 2/0/0/0 | 挡住投机预取 |
| 1 | `0x8000_0000` | 1 GB | 3 | 2/0/0/0 | SDRAM 背景（不可缓存） |
| 2 | `0x6000_0000` | **32 MB** | **6（只读）** | 0/0/1/1 | **FlexSPI XIP Flash，只读 + 可缓存** |
| 3 | `0x0000_0000` | 1 GB | 3 | 2/0/0/0 | 片内 RAM/外设背景（不可缓存兜底） |
| 4/5/6 | ITCM/DTCM/OCRAM 可缓存区 | 64K/64K/**64K** | 3 | 0/0/1/1 | 片内可缓存（region6 缩到 64 KB，顶部 64 KB 落回非缓存兜底成为 DMA 池） |
| 7 | `0x8000_0000` | 32 MB | 3 | 0/1/1/1 | SDRAM 写回 + 写分配 + 共享 |

**Flash 标成只读是安全关键**，不只是性能选项：可缓存 + 可写意味着脏行会被**回写进
Flash**，那等于在没有任何命令序列的情况下改写器件内容。标只读后缓存里永远不会有
Flash 的脏行。

### 2.3 起步就抓到一个真 bug（值得记下来）

启动时**回读硬件寄存器并打印**（"报事实，不报意图"），第一次回读就暴露：
8 个区域里 region0 显示的是 region7 的属性、rest 全是 0 —— 说明 **8 次写全落进 region0**。
根因：`RBAR` 的编码写错了 —— **区域号在 `bits[3:0]`、`bit[4]` 才是 VALID**，
而我写成了 `number << 4`（落到 `bits[7:4]`，那属于地址位）。改对后回读与期望逐项一致。
现在这段编码与解码都提取成 [`mpu-regions`](../../crates/mpu-regions/src/lib.rs) 的被测函数
（编译期不变量 + 主机测试），**这类错误在 `cargo test` 里失败，而不是在目标现场失败**。

### 2.4 实测收益与它的天花板

| 场景 | 关缓存 | 开缓存 | 结论 |
|---|---|---|---|
| Flash 流式读（1 MiB） | 46.6 MiB/s | **51.8 MiB/s** | +11%，且**已贴近总线线速** |
| SDRAM 流式自检（32 MiB） | ~3.0 s | ~3.0 s | 基本无变化 |

两条都值得解释，否则会误判"缓存没用"：

- **Flash 读已到总线天花板**：FlexSPI 串行时钟 100 MHz、四线 ⇒ 理论上限约 50 MB/s，
  实测已压在线上。所以要再快，只有提串行时钟（但 **dummy 周期必须同步重算**，
  见 `flash.rs` 顶部警告），缓存解决不了总线带宽。
- **SDRAM 流式访问没有复用**，而 region7 是**写回 + 写分配**：写一个 32 字节行会先
  **读入**该行，对流式写是净开销。所以这份配置（与既有固件一致）适合"有复用的数据"，
  不适合"一次性搬运"。将来若真的出现大块流式搬运，可以为其单独划一段
  **non-allocate** 属性区域 —— 但**先用真实负载测**再改，现在没有这种负载，改了只是猜。
- **一条反面对照**：把 FlexSPI 控制器复位（ROM `clear_cache`）放进每个 32 B 块的内层
  循环后，同一份基准从 3,401,993 KiB/s 掉到 48,473 KiB/s（**70 倍**量级）。
  前者是预取缓冲命中，后者才是诚实带宽 —— 这也是"控制器复位每次编程/擦除只做一次"
  这条规则的来源（见 [Flash 用途划分 §8.2](Flash布局与用途划分.md)）。

### 2.5 给后续工作留下的硬约束

**Flash 写入必须在编程/擦除后失效对应范围的 D-cache 行** —— 该路径已于 2026-10-13
落地（`crate::cache` 用 `SCB.DCIMVAC`；决定性对照实验：D-Cache 关掉后自证全过）。
**新增的 DMA 代码**同样适用：缓冲区放非缓存 DMA 池（OCRAM 顶部 64 KiB）或传输前后
显式维护缓存 —— 顺序反了会引入一类极难复现的数据损坏。

## 3. 片内 RAM 与 SDRAM 的分工（现状 + 原则）

### 3.1 现状与空闲量（2026-10-16 链接产物）

| 存储 | 容量 | 现在放什么 | 空闲 |
|---|---|---|---|
| ITCM | 64 KiB | 全部 `.text`（52,896 B） | 按用户要求取消 8 KiB 预留，全量 64 KiB 可用 |
| DTCM | 64 KiB | 栈（48 KiB）+ 向量表（632 B） | ~15 KiB |
| OCRAM | 128 KiB | 可缓存区 64 KiB：`.rodata`/`.data`/`.bss`/`.uninit`（合计 53,172 B）；**DMA 池 64 KiB 独立非缓存** | 可缓存区余 ≈12.1 KiB |
| SDRAM | 32 MiB | 两段固定块池 4 MiB；其余空闲 | ≈28 MiB |

结论：**整体没有容量压力**，优化目标不是"省内存"，而是"把对的东西放到对的地方"。
真正要盯的是 OCRAM 可缓存区：`check-memory` 会在任何段侵入 DMA 池时给出可读的失败
信息，处置是把大块数据移去 SDRAM，而不是动池的边界（池的 64+64 切法是 MPU 区域
大小约束下唯一的切法）。

### 3.2 分工原则（并写成门禁）

| 存储 | 该放什么 | 为什么 |
|---|---|---|
| ITCM | 全部代码 + ISR 热路径 | 零等待取指 |
| DTCM | 栈、向量表、**最热的小数据结构**（当前状态与队列） | 单周期访问、不受总线仲裁影响 |
| OCRAM | 常驻工作区（文件系统索引、终端缓冲、诊断缓冲） | 与 CPU 同频，容量最大 |
| OCRAM 非缓存池 | DMA 描述符与缓冲 | 在地址上就不可缓存，少一处维护点 |
| SDRAM | 大缓冲、可缓存的工作集（有复用的数据）、固定块池 | 32 MiB，但**流式访问无缓存收益**（§2.4） |

**已实施的门禁**（把上面的原则变成可失败的检查）：

| 门禁 | 状态 |
|---|---|
| `.text` 必须落在 ITCM 且 ≤ 64 KiB（取消 8 KiB 预留） | ✅ `cargo xtask check-memory`（从链接产物读真实地址；判据常量来自 `memory-layout`；余量与预算的算术关系由编译期断言钉住） |
| `.stack` 大小与声明值一致、`.vector_table` 在 DTCM | ✅ 同上 |
| OCRAM 各段不得侵入非缓存 DMA 池 | ✅ 同上（链接脚本并不知道池被征用，只有门禁能抓） |
| **栈余量 ≥ 30%** | ✅ `cargo xtask bench` 按真机自报峰值判定（与基线无关）；`MIN_STACK_HEADROOM_PERCENT` 是阈值 |
| 启动后 cache/MPU 状态等于期望 | ✅ 启动时回读并调用纯逻辑 `mpu_regions::check_state` 判定（含"非全开即报错"的穷举测试）；**刻意不 panic**：现场设备停在启动阶段比降级运行更糟 |
| MPU 区域表不变量（基址对齐、Flash 只读、SDRAM 最高编号） | ✅ `mpu-regions` 的编译期断言 + 主机测试（含当年 `RBAR` bug 的回归测试） |
| 文档数字与代码一致 | ✅ `cargo xtask check-docs`（人工审计曾查出 27 处漂移，现在关键数字是机器判据） |
| 主机侧行覆盖率 | ✅ `cargo xtask coverage`，阈值 90%（95% 量级；前一次实测 94.4%；精确值以命令输出为准） |
| 真机基准回归 | ✅ `cargo xtask bench`：Flash 读吞吐 / 文件系统挂载 / SDRAM 自检耗时，百分比与绝对量**同时**超限才判回归；另含硬下限判据（§1 的栈余量、`rt=ok`、`txdrop=0`）；`--from-file` 可离线验证解析逻辑 |

## 3.3 capsule 化对资源预算的含义

- **ITCM 是 core kernel 的稀缺资源**：业务 capsule 的代码默认应落 `.xip`，不得挤占
  Flash 驱动/热路径的 ITCM 预算；当前 ITCM 仅余约 1.2 KiB（以 `check-memory` 为准）。
- **业务增长主要消耗 Flash 与 SDRAM 池**：整包映像仍受 `check-size`（<1 MiB）与
  `slot_run`（2 MiB）约束；每个 capsule 的静态缓冲/文件配额必须在接入时声明。
- **没有 per-capsule 地址空间**：capsule 共享 kernel 映射与 MPU 区域；MPU 仍按
  “Flash 只读 / ITCM / DTCM / OCRAM / SDRAM / DMA 池”分区，不按 capsule 分区。
- **实时预算按 capsule 计量**（目标形态）：否则“业务变多”会把 `shell-input` /
  `idle-step` 等全局 span 顶爆，而无法指出是谁。

当前这些都还没有 capsule 级实现；在目标形态落地前，不要按“每个 capsule 独立内存域”
做资源规划。

## 4. 文件系统（filesystem）优化现状与清单

现状：日志结构 + 记录级 CRC + 版本完整性 + GC + 磨损分散 + **写队列**（生产者投递、
`idle` 属主执行；满则拒绝而非覆盖）；挂载走内存索引（基线 **0 ms**）；读路径走 XIP
（开缓存可达 ~52 MiB/s）。以下逐条对照。

| # | 条目 | 状态 / 收益与代价 |
|---|---|---|
| F1 | 退役过渡期原始偏移存储 | ✅ **已实施**：持久化只有一个属主（文件系统）；未接线的持久化端口用 `NullStore` 明确说"不可用"。曾有的"三张表与文件系统块 0 物理重叠"双属主事故由 `check-flash-map` 的几何判据保证不可能重新引入 |
| F2 | **给每个文件加块指针链**（littlefs 式 CTZ skip-list 或简单链） | 建议：`read_file` 不再需要扫描；`resolve` 的"全盘下探"路径基本消失。代价：结构变更 ⇒ 必须重做掉电穷举测试（现有掉电注入与版式测试是资产，口径见 [模块分解](模块分解.md)） |
| F3 | **区分"冷挂载"与"热刷新"**：`mount` 只扫块头，记录级扫描推迟到首次访问某文件 | 建议：挂载更稳（现在 0 ms 已足够，但分区更大时仍是 O(全片)） |
| F4 | GC 与磨损统计接入终端 | ✅ 已实施（2026-10-12）：终端 `fs`（别名 `df`）打印容量 / 可写入量 / 文件数 / 索引溢出 / 擦除计数 min·max·total；不可用时**不打印误导性的 0**。⚠️ 首版在 `with_fs`（**关中断**）里调用会扫描介质的 `stats()`：主机实测接近写满时一次读 **28.3 MB 介质 / 44.5 万次 `read`**，真机折算 0.5–2 s —— **已改**为 `stats_index_only()`（**0 次**介质读），`live`/`dead` 显示"需扫描，未计算"（快照新增 `liveness_scanned` 位，绝不把 0 当实测值）。第二轮（2026-10-12，趁格式尚未落盘）：擦除计数 `u16`→`u32`（到顶会**静默饱和**，系统将永远无法表达"这块已写废"）+ 格式版本字节；`gc_runs` 拆成显式/自动两个计数；`try_stats()` 如实返回扫描错误。⚠️ 块头格式变更要求**全片擦除重刷**（`bash scripts/flash.sh -e chip`） |
| F5 | **异常掉电标记**：`boot_meta` 里加"上次未正常关机"位，触发一次全扫自检 | 建议（与 P4 的 `boot_meta` 结构一起做） |
| F6 | 索引放哪 | 现状 13,752 B 常驻 OCRAM（合适）；若将来索引变大，可移 SDRAM（有复用时更快）—— 需注意缓存一致性（无 DMA 时简单） |
| F7 | **把 `report_fs()` 的全盘读挪出关中断** | 待办：`read_file(CONFIG)` 走 `resolve()/copy_into()`，**都是全盘扫描**（文件存在时 1485 次读 / 51 KiB / 约 6 ms，与文件大小无关）。现在写入通道已通，这条会随启动路径的真实文件而常态化 —— 把这两步挪出 `with_fs` 的临界区（或移进 `idle` 的属主任务） |

**不建议做的**：把文件系统换成 littlefs/SPIFFS 之类的现成实现。现有实现是**零通用堆、
无外部依赖**、且掉电点穷举测试覆盖到位；换成外部 crate 会引入依赖（离线环境不可得）
并丢掉这些测试资产。

## 4.5 ⚠️ 一条实测出来的硬约束：**不要在关中断里做全盘扫描**

2026-10-12 的实测（主机 mock 介质、446 块 × 64 KiB 全尺寸、带读计数）：

| 负载 | 操作 | 介质读次数 | 读字节 | 设备耗时估计（按 XIP 实测 51.8 MiB/s） |
|---|---|---|---|---|
| 空分区 | `mount()` | 892 | 14 KiB | 0.27 ms（真机实测 0 ms，用于校准） |
| 空分区 | `stats()` | 892 | 14 KiB | ≈ 3.3 ms（含每次访问固定开销） |
| **接近写满**（live 18 MiB / dead 9 MiB） | `stats()` | **444,574** | **28.3 MB（96.9% 分区）** | **0.52 s（纯字节）～ 2.0 s（含每次访问开销）** |
| 任意 | `stats_index_only()` | **0** | **0** | 0 |

**为什么这是硬约束**：这块 LPUART 的接收 FIFO **只有 1 字节深**（115200 8N1 ≈ 87 µs/字节），
而 `board_support::fs::with_fs` 是 `critical_section::with` —— **整个闭包关中断**。
关中断 0.5–2 s 意味着串口可到达的 6000–23000 字节全丢，串行/CAN 的实时预算更无从谈起。
**更要紧的是代价会随数据增长**：空分区只要 3.3 ms，看着无害；数据真写进去之后才变成
秒级 —— 属于"上线时看不见、写入后才爆"的那类问题。因此：**能读内存索引得出的量，
就别扫介质**；扫描类长活一律挪到 `idle`（F7 就是这条的待办）。

## 5. 实时架构（RTIC v2）现状与清单

现状：2 个硬件任务且**同为优先级 1**（`LPUART1` / `PIT`），终端、文件系统写队列属主、
诊断输出全在 `idle`；控制台发送**已中断驱动 + 8,192 B 环形队列**，`idle` 不再被长输出
拖住（**平台需求 DB-2 / RT-3**）。

| # | 条目 | 现状 / 为什么 |
|---|---|---|
| R1 | **按实时预算拆任务优先级**：`serial_rx=2`、`can_tx=3`、`can_rx=4`（常量与断言已在 `primitives::budget`） | 等 P2 落地；届时任务若都塞进 `idle`，实时性就无从谈起 |
| R2 | **控制台 TX 中断驱动 + 环形缓冲** | ✅ 已实施并真机验证（2026-10-12）：`make bytecheck` **8/8 逐字节一致**、4096 字节可计数图案 **4160/4160**。⚠️ 实施中确立一条硬约束：**`DATA` 只能有一个写入者** —— 队满时若退回"直写寄存器"，会与中断里的排空互相覆盖、**整行整行地丢**；队满时按 `PRIMASK` 分流（中断开着才自旋，关中断时丢弃并计数 `txdrop`） |
| R3 | **`#[init]` 长活继续外移** | 时基/控制台/MPU 已就绪；`boot-init` 仍是**故意超标**的启动期 span（RTIC 用 `interrupt::disable()` 夹住整个 `init`），搬完之前它会一直红在台账里 |
| R4 | **最坏执行时间（WCET）测量** | ✅ 已实施：DWT 周期计数器 + `realtime` 的 8 个 span 统计；心跳（`beat on`）带 `rt=ok\|VIOLATION\|none`；`cargo xtask bench` 把 `rt=ok` 当硬判据（详见 [并发与实时预算](并发与实时预算.md)） |
| R5 | **看门狗按"最后一步"接入**，喂狗条件由健康门控决定 | 决策与健康门控已就绪（`all_healthy` 纯函数、`wdg_ok=` 已上报），**硬件看门狗未启用**（P5 缺口：外部 SGM706 的 `WDG_CTR` 驱动源未确认，贸然生效只能断电恢复） |

## 6. OTP / eFuse 的利用

**现在就能做、且零风险**：读 OCOTP 的 **`CFG0`/`CFG1`** 两个影子字
（本板实测 `0x613803da` / `0x0e3539d7`，已接入启动报告与终端 `status`）。
用途：设备身份 / 日志归属 —— 省掉"把序列号烧进 Flash 再读回来"的整条链路。

> ⚠️ **置信等级 🟡：能读出稳定值 ≠ 它就是"官方唯一 ID"。**
> `MIMXRT1021.h` 把这两个字注释为 "Bank0 Word1/Word2 (Configuration and
> Manufacturing Info.)"。**在拿到参考手册 OCOTP 章节确认、或用第二块板对照之前，
> 不能把它当作"唯一"使用** —— 万一它其实是批次/晶圆信息，两台设备会拿到同一个 ID，
> 那会污染任何以它为键的持久数据。因此代码与输出里都明确标注为"候选"。
> 另外：RAL 的 `ocotp` 寄存器块布局与手册不一致（`LOCK` 在 `0x38` vs 手册 `0x400`），
> 所以这里按手册偏移直读 —— 与 SEMC 那次是同一类问题。

**熔丝（不可逆）必须分阶段**：

| 阶段 | 烧什么 | 前置条件 |
|---|---|---|
| 现在 | **什么都不烧** | — |
| 产品定型 | `BOOT_CFG`（固化启动器件与配置，避免引脚被误改） | 启动链验证通过 |
| 需要签名时 | HAB 的 SRK 哈希 | 密钥基础设施 + 认证方要求明确 |
| 产线 | MAC 地址（若用片上以太网） | 产线流程确定 |

纪律建议：把"当前熔丝影子寄存器状态"做成 `xtask` 的一个只读命令（`fuse-status`），
在**任何**烧写动作前后各跑一次并留档 —— 熔丝是一次性的，没有"回滚"。

## 2026-10-20 补充：ITCM 不是“代码默认位置”

真机验证：RTIC `init` 迁到 `.xip` 后启动/日志/自检全部正常，`.text` 从
57,324 B 降到 52,896 B。ITCM 只保留：Flash 驱动与擦写轮询、擦写期间必须执行的
代码、高频 ISR 与确有实测收益的热路径；其余冷代码（启动报告、idle、终端读路径、
日志管理）可以放 Flash XIP。放 XIP 的代价是 QSPI 取指延迟与 Flash 忙时停等，
所以 `check-code-placement` 仍要求白名单 + 真机验证。

## 2026-10-20 补充：终端命令层迁 XIP

`shell` 目标端命令处理函数（`cmd_*`）加 `.xip` 放置属性；主机仍
`forbid(unsafe_code)`，目标端才允许 `unsafe(link_section)` 属性（不新增 unsafe 块）。
ITCM 从 53,024 B 降到 45,520 B。命令只在 idle 冷路径运行，Flash 驱动/擦写轮询
仍在 ITCM，`.xip` 白名单允许 `shell8commands`，并保留真机 selftest 验证。
