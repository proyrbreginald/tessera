# 产品组合根外提设计

> **状态**：设计已冻结，S1（组合根外提）已落地并随 `0.1.0.0` 上机验证
> （`bytecheck` / `test-target` / `bench` 全过，证据记录在提交信息与 `tmp/`）；
> S2（上下文能力对象化）与 S3（基础 capsule 外提 + 插件模板）**未实现**。
> 本文写"为什么这么切、契约是什么、每一步的判据"，不把规划写成现状。
>
> 决策记录：[ADR-0010](../adr/0010-产品组合根外提.md)。
> 架构方向：[`微内核与capsule架构`](微内核与capsule架构.md)、[ADR-0008](../adr/0008-静态capsule化内核.md)。

## 1. 问题：组合根为什么搬不动

现状事实（改动前，S1 之前）：

| # | 事实 | 证据 |
|---|---|---|
| 1 | 六个基础服务（terminal/fs/log/rotate/health/maintenance）全部定义在 **bin crate `firmware`** 内，且 `firmware` 只有 `[[bin]]`、没有 lib target | `crates/firmware/Cargo.toml`；`crates/firmware/src/capsules.rs` |
| 2 | capsule 集合、容量与注册顺序写死在 `firmware::composition` | 原 `crates/firmware/src/composition.rs`（仅有 `CAPSULE_COUNT = 6` 与一次 `build`） |
| 3 | 六个服务共享的上下文 `TerminalStepContext` 是 `pub(crate)`，字段为裸指针 | `crates/firmware/src/capsules.rs`（`struct TerminalStepContext`） |
| 4 | `sdk::Capsule<C>` 的 `C` 是泛型参数，`CapsuleSet` 只借入 `&'a mut dyn Capsule<C>` | `crates/sdk/src/lib.rs` |

由 1–4 直接得到三个后果：

- **仓库外业务 capsule 无法命名上下文**：要同集注册只能写
  `impl sdk::Capsule<firmware::capsules::TerminalStepContext>`，而该类型不可见；
- **组合根不可复用**：`register` 只能在持有 `Product` 的 `firmware` 内调用；
- **循环依赖**：如果直接把 `composition.rs` 搬到新 crate `product` 并让它构造
  `FsService` 等类型，就变成 `product → firmware`，而 `firmware` 又要 `→ product` 调用它。

三条"看起来能绕开"的路都已被否决：

| 方案 | 为什么不行 |
|---|---|
| `product` 依赖 `firmware` | Cargo 直接拒绝环形依赖；即便拆出 lib 也只是把循环藏在两个 crate 之间 |
| `product` 依赖 `board-support` 自己造服务 | 组合根变成第二个硬件入口，纯逻辑层出现硬件依赖，业务产品无法主机测试 |
| 把服务实例做成全局 `static` 供 `product` 取 | 与 `firmware` 的静态量重新耦合，生命周期/别名问题没有消失，只是从类型系统挪到运行期 |

## 2. 解法：依赖倒置 + 服务注入

目标依赖图（箭头 = 依赖）：

```text
firmware ──▶ product ──▶ sdk ──▶ ports ──▶ primitives
    │
    └──▶ board-support ──▶（imxrt-* / cortex-m*）
```

不变量：

1. `product` **只依赖 `sdk`**：不依赖 `firmware`、不依赖 `board-support`、不认识任何具体服务类型；
2. `firmware` 实现 `product::Platform`，把服务实例以 `&mut dyn sdk::Capsule<C>` 借出；
3. `C`（step 上下文）对组合根是**不透明泛型参数** —— 组合根把它原样传回 capsule；
4. 组合根是"产品包含哪些 capsule、什么顺序、多大容量"的唯一决定处；`firmware` 不再决定。

## 3. 契约（S1 已实现）

代码：`crates/product/src/lib.rs`。

```rust
pub const PRODUCT_NAME: &str = "tessera";
pub const BASE_CAPSULES: usize = 6;
pub const BUSINESS_SLOTS: usize = 2;
pub const CAPSULE_SLOTS: usize = BASE_CAPSULES + BUSINESS_SLOTS;

pub struct PlatformServices<'a, C> {
    pub terminal: &'a mut dyn Capsule<C>,   // Input
    pub fs: &'a mut dyn Capsule<C>,         // Maintenance
    pub log: &'a mut dyn Capsule<C>,        // Maintenance
    pub rotate: &'a mut dyn Capsule<C>,     // Maintenance
    pub health: &'a mut dyn Capsule<C>,     // Health
    pub maintenance: &'a mut dyn Capsule<C>,// Maintenance
}

pub trait Platform {
    type Context;
    fn services(&mut self) -> PlatformServices<'_, Self::Context>;
}

pub fn build<'a, P: Platform, const N: usize>(
    platform: &'a mut P,
) -> Result<sdk::Product<'a, P::Context, N>, BuildError>;
```

设计取舍：

| 决定 | 理由 |
|---|---|
| 六个**具名槽**，而不是 `Vec`/注册表 | 固定容量、零分配；槽名是平台服务契约的一部分。用分布式注册表等于把 ADR-0008 否决过的 `linkme` 换一种写法 |
| `build` 返回 `Result`，容量不足/重名即失败 | "少注册几个也能跑"是**假装完成**；启动期必须显式上报 `build_failed=` |
| 注册顺序固定在 `product` | 跨阶段顺序由 `CapsulePhase` 决定；固定同阶段顺序让"终端输入优先于后台维护"可读、可测 |
| `product` 预留 2 个业务槽 | 默认产品给业务留位；业务产品可以自己给 `build` 传更大的 `N`，容量是产品决定 |
| `build` / `build_named` 只注册、不初始化 | 实例归调用方所有，初始化失败必须由调用方上报；`build` 文档明说"不调 `init_all` 会 step 未初始化对象" |
| 失败回退等于放弃全部内置服务 | 容量不足/重名是启动期缺陷；回退成空产品只保留"设备可被调试器访问"，必须显式打印 `build_failed=` |
| 不新增静态门禁 | 判据已经是**依赖图本身**（`check-layering` + `check-capsules`）与 product 单测；再加一条"检查文件名"的门禁只会制造维护成本 |

### 3.1 扩展边界（S1 的实际能力）

S1 只外提**组合策略**（集合、顺序、容量、产品名），**不是**完整的业务接入通路：

- `sdk::Product` 借用 capsule（`&'a mut dyn Capsule<C>`），不拥有它。业务 capsule 实例
  必须由调用方持有并活过组合根；在 `my-product::build` 里构造局部实例再 `register`
  会因生命周期不足直接编译失败（E0597）。
- `C` 仍是不透明泛型，`sdk` 没有能力句柄层，仓库外 capsule 只能写无能力的
  `impl<C> Capsule<C>`。
- 六个基础 capsule 仍物理位于 `firmware`。

所以"业务方新建产品 crate、`firmware` 源码不变即可接入"是 **S3 的目标**，不是 S1 的现状。
S1 真正可做的扩展是：替换默认产品的顺序/容量/产品名，或在调用方持有实例的前提下
用它组装平台六槽并追加 capsule。

`firmware` 侧的接缝只有 `crates/firmware/src/platform.rs`：

```rust
pub(crate) struct PlatformImpl<'a> { /* 六个 &'a mut Service */ }
impl product::Platform for PlatformImpl<'_> {
    type Context = TerminalStepContext;
    fn services(&mut self) -> product::PlatformServices<'_, Self::Context> { /* 借出 */ }
}
```

## 4. 上下文边界：S1 能走多远，S2 缺什么

S1 之后，`product` 仍对 `C` 一无所知。这带来两个**尚未解决**的事实：

1. 仓库外业务 capsule 只能写 `impl<C> sdk::Capsule<C> for MyCapsule`（泛型实现，
   因为 `Capsule` trait 对 `C` 没有 bound）。类型上能注册，但**拿不到任何能力**：
   `sdk` 不提供句柄层，`prelude` 只重导出 5 个 `ports` trait，`C` 也没有可调用的方法。
2. 六个基础 capsule 仍物理在 `firmware`，因为它们的 `step` 直接调用
   `board_support::{fs, timer, console, rt}` 与 `firmware` 内部函数。

因此 S2 的目标是：

```rust
// sdk：业务可见的能力对象（对象安全、无裸指针）
pub trait CapsuleContext {
    fn clock(&mut self) -> &mut dyn ports::clock::Clock;
    fn log(&mut self) -> &mut dyn ports::log::LogSink;
    fn bus(&mut self) -> Option<&mut dyn ports::bus::Bus>;   // GAP(P2) 期间返回 None
    fn store(&mut self) -> Option<&mut dyn ports::store::Store>;
    fn health(&self) -> HealthSnapshot;                     // 只读
    fn capsule_failures(&self) -> u32;                      // 只读
}
```

并进一步把 `Capsule<C>` 收敛为 `Capsule` + `step(&mut self, ctx: &mut dyn CapsuleContext)`，
使仓库外 crate 可以直接 `impl Capsule for MyCapsule`。

**为什么 S2 不能顺手做**（审计结论，见 §7）：平台 capsule 的能力面远大于业务面 ——
`TerminalService` 的真实能力在 `ShellContext` 的 50 个方法里（直接调
`board_support::{fs,rt,flexcan,config,...}`），`MaintenanceService` 通过模块级原子量与
`firmware` 内部函数通信。把这些塞进 `CapsuleContext` 会把 `board-support` 的细节泄漏到
稳定门面，反而破坏"业务只依赖 sdk"的边界。S2 必须先定义**能力子 trait**（`ConsoleIo`、
`FsMaintenance`、`LogControl`、`HealthQuery`……）并逐个迁移，不能一步到位。

### 4.1 别名这一关（S2 的硬点）

`TerminalStepContext` 用裸指针的根本原因不是"懒得改"，而是别名：

- 上下文构造之后，`idle` 仍直接使用 `clock`（心跳、稳定计时）；
- 如果把字段改成 `&'a mut PitClock`，`idle` 对 `clock` 的借用会在整个循环期间被独占。

两条可行路线（S2 选一，实施前先写判据）：

| 路线 | 做法 | 风险 |
|---|---|---|
| A. 能力按值传入（首选） | `PitClock` 是 `Copy` 的零大小句柄，`now()` 只取 `&self`；上下文存 `PitClock` 值而不是引用 | 需要对每个能力确认"按值安全"；`Sdram` 这类非 `Copy` 能力仍需借用拆分 |
| B. 借用拆分 | `idle` 不再直接持有 `clock`，所有时间读取都经上下文 | 改动面更大，但能彻底消掉 `unsafe` |

无论哪条，判据都是：`check-unsafe` 的块数**只减不增**，且 `capsules.rs` 的裸指针
解引用点从 1 处变 0 处。

## 5. 分阶段落地与判据

| 阶段 | 内容 | 判据（先失败、后实现） | 状态 |
|---|---|---|---|
| **S1** | 外提 `product` crate；`Platform` 注入；`firmware` 只实现平台 | `check-layering`（product 闭包无硬件）、`check-capsules`（product 不依赖 firmware/board-support）、product 单测（顺序/容量/重名/产品名）、真机 `bytecheck` + `test-target` + `bench` | **已落地（0.1.0.0）**：verify 全绿、450 主机测试、bytecheck 全项通过、target-test 5/5、bench `rt=ok`/`txdrop=0` |
| **S2** | `sdk::CapsuleContext` 能力对象；`Capsule` 非泛型化；上下文去裸指针 | 新增 sdk 能力契约单测；`check-unsafe` 块数下降；真机 `bench` 的 `rt=ok`/`txdrop=0` 不退化 | 未实现 |
| **S3** | 基础 capsule 迁到 `capsule-platform`（纯逻辑，依赖 sdk + 能力 trait）；`product` 构造它们；仓库外业务 capsule 示例 + 插件门禁覆盖仓库外 | 业务示例 crate 只依赖 `sdk` + `simulator` 即可主机测试；`check-capsules` 对仓库外工作区给出同等约束；真机验证 | 未实现 |
| **S4** | A/B 整包更新（P4） | 按 P4 单独设计 | 未实现，暂缓 |

每一阶段都遵守同一条顺序：**先让判据失败**（门禁/负例测试），再实现让判据通过。
S1 的"先失败"证据：**保留** `sdk` 依赖并新增 `board-support` 依赖（这样它仍在
`check-capsules` 的扫描范围内），会让 `check-layering`（纯逻辑闭包出现硬件 crate）
与 `check-capsules`（插件直接依赖硬件）同时失败。

## 6. 风险与未决问题

| # | 风险 | 处置 |
|---|---|---|
| 1 | `PlatformServices` 的六个具名槽把"平台服务拓扑"写进了 `product` | 这是组合根的职责；换服务集就是换产品。真正的问题在 S3：基础 capsule 外提后，槽位应变成"能力"而不是"服务" |
| 2 | `Product` 的失败/隔离语义不完整（累计失败即永久隔离、`init` 不可重试、没有 per-capsule 预算承载点） | S2/S3 之前必须先冻结语义；否则业务 capsule 进入同一健康体系时行为不可解释 |
| 3 | `build_failed=` 回退目前不可达，但**不是永远**：容量 8 ≥ 6 只排除了 `Full`，重名（例如把 `rotate` 的 `name()` 改成 `log`）仍会触发。触发后设备会以 0 个 capsule 继续跑：无终端/无日志/无健康，只剩一行 E 日志 | 保持"失败必须显式"；负例判据是 product 单测的重名用例。若将来扩容或改名字，需真机验证这条路径的可见性 |
| 4 | `.xip` 是正向白名单，业务 crate 无法把符号放进 Flash 原地执行 | S3 决定：业务 capsule 默认放 ITCM，或由产品方显式扩充白名单并给出理由 |
| 5 | 上下文能力对象化会改变 `capsules.rs` 的所有 `step` 签名 | 分服务迁移，每次一个服务 + 一次 `verify`；不要一次重写 |

## 7. 依据（只读审计记录）

S1 设计前做过两份只读审计，事实清单在 `tmp/`（不入库，可重跑）：

- `tmp/audit-capsule-surface.md`：六个服务的逐项能力面、`TerminalStepContext` 解剖、
  `sdk` 的 12 条限制、仓库外注册失败的完整类型链；
- `tmp/audit-docs-gates.md`：capsule 相关文档的陈旧断言、新增 crate 对门禁清单的影响面、
  `check-docs` 会强制失败的文档清单。

其中直接影响本设计的结论：

1. 上下文类型 `pub(crate)` + 私有模块是第一道硬墙（S2 解决）；
2. 能力面远不止 `sdk`，`shell::ShellContext` 有约 50 个方法直接打 `board-support`（S3 解决）；
3. 注册只能走"产品 crate 显式依赖业务 crate 的编译期列表"（`linkme` 已被 ADR-0008 否决）；
4. 失败/隔离/预算语义必须先定，否则外提只是搬代码，没有可解释的运行语义。
