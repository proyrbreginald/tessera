# 架构总览

> 回答：为什么这样分层、一次数据流怎么走、底座与业务的分界在哪里。

## 1. 底座的位置

```text
┌────────────────────────────────────────────────────────────────────┐
│ 业务 capsule crate（仓库之外，独立编译）                              │
│   - 领域类型 / 状态机 / 业务决策（纯逻辑，可在主机测试）               │
│   - 只依赖 capsule SDK / ports；禁止 unsafe / 寄存器 / RTIC 任务  │
└───────────────▲────────────────────────────────────────────────────┘
                │ capability 句柄 + 事件（Bus / Clock / Store / LogSink）
┌───────────────┴────────────────────────────────────────────────────┐
│ 本仓库 = core kernel + 基础 capsule                                 │
│   基础 capsule / kernel-support（18 个纯逻辑 crate）：                │
│      终端、文件系统、日志、协议、存储策略、实时仪表、Flash 纪律……    │
│   core kernel：board-support（唯一碰寄存器）→ firmware（平台注入）     │
│   产品组合根：product（只依赖 sdk）——S1 已外提                       │
│   工具：xtask（门禁）、scripts（真机）、simulator（主机替身）          │
└────────────────────────────────────────────────────────────────────┘
```

三条承诺：

1. **业务能在主机上完整重放**：业务 capsule 只认识端口/句柄；`simulator` 提供
   脚本化总线、手动时钟、可注入掉电的介质、捕获日志。超时、乱序、掉电这些
   现场难以复现的时序，在主机上是普通测试。
2. **不可测的部分尽可能薄**：真实寄存器/中断/电气只出现在 `board-support` 与 `firmware`，
   且被"回读打印 + 产物断言 + 上机脚本"三重手段约束。
3. **组合在编译期完成**：业务是独立 crate，与底座一起链接成整包固件；不做运行期
   加载/热替换。接口不兼容在编译期失败；safe capsule 不等于安全隔离（见
   [ADR-0008](../adr/0008-静态capsule化内核.md)）。

## 2. 一次数据流（通用形态）

以"应用从一条总线上收一帧、校验、落盘并上报"为例（具体语义由接入方定义）：

```text
①  业务 capsule 的 step（由组合根在固定上下文调用；`on_event` 事件分发尚未实现）
      │  link.transact(&request, &mut rx)        ← ports::bus::Link 类型状态机
      ▼
②  Bus::recv(deadline)                          ← 端口契约；超时由驱动层实现
      │        （主机：simulator::MockBus 按脚本回帧 / 超时）
      ▼
③  wire-format 的解码与结构校验                   ← 零拷贝，帧借入接收缓冲
      │
      ▼
④  业务 capsule 自己的领域逻辑（纯函数式）          ← 可在主机穷举
      │
      ├─▶ ⑤ LogSink（控制台/日志环）             ← ISR 只拷贝 16 B 定长记录
      └─▶ ⑥ Store / 写队列 → idle 属主 → 文件系统  ← 长操作绝不进关中断
```

关键约束（全部有机器判据）：

- **③ 之前不分配**：帧借入调用方缓冲，容量是编译期常量（无通用堆）；
- **⑤ 的日志不格式化**：热路径只拷贝定长记录，人话渲染留给终端/落盘层；
- **⑥ 的写入不在中断里**：写请求入队（可能被拒，拒绝可见），由 `idle` 属主执行。

## 3. 为什么这样分层

### 3.1 "纯逻辑 / 硬件"二分，而不是按功能切

按功能切（"协议层/业务层/驱动层"）会让每一层都沾一点硬件；按**可测性**切则不同：
凡是能用主机测试证明的，都下沉到 18 个纯逻辑 crate；凡是不能的，全部集中到两个
硬件 crate。这样"哪里需要格外小心"是一个**编译期可判**的事实。

### 3.2 端口的形状由"不可测的部分"决定

每个端口都刻意压到很少的方法：

| 端口 | 方法数 | 为什么这么少 |
|---|---|---|
| `Bus` | 2（send/recv）+ 类型状态机 | 时序不可测，但"顺序"可以用类型表达 |
| `Store` | 2（read/write_atomic） | 掉电原子性只能证明，不能类型化 |
| `Clock` | 1（now） | 时间必须可注入（`ManualClock`） |
| `LogSink` | 1（record） | 丢弃必须计数，不许阻塞 |
| `RawMedium` | 3（read/erase/program） | 介质的全部不可测行为只有这三件 |

### 3.3 门禁是架构的一部分

架构里每一条"不变量"都尽量变成一个机器判据，而不是一句文档承诺：
分层（`check-layering`）、unsafe 预算（`check-unsafe`）、关中断纪律（`check-critical`）、
故障向量真实性（`check-fault-handlers`）、映像布局（`check-image`/`check-memory`）、
文档一致性（`check-docs`）、需求覆盖（`trace`）。
"能被机械检查的约束，就不要靠人记"——详见 [`门禁手册`](../04-开发/门禁手册.md)。

## 4. 与常见方案的取舍（为什么不用它们）

| 方案 | 为什么不用 |
|---|---|
| 裸机超级循环 + 手写中断 | 优先级与资源借用没有编译期检查；本项目用 RTIC v2 的静态优先级与无锁资源借用 |
| 单执行器 async（Embassy 等） | 无抢占 ⇒ 硬实时不可论证；且现场故障恰恰没有调试器 |
| `defmt` + 调试器解析 | 现场只有串口；日志必须是"设备自己能打出来"的（[ADR-0004](../adr/0004-日志方案不使用defmt.md)） |
| 通用堆 / `Vec`/`String` | 内存用量必须静态可知；固定块池 + `heapless` 把"耗尽"变成可观测的值（[ADR-0003](../adr/0003-不使用alloc与async.md)） |
| 三方 RTOS + C 驱动 | 语言边界与构建系统会引入不可离线复现的依赖；本项目 100% Rust、可完全离线构建 |
| 运行期 ELF 加载 / 热替换 capsule | 需要重定位、符号解析与堆；与固定内存、零分配、A/B 整包更新冲突 |
| 每个 capsule 一个 MPU 地址空间 | 需要进程/特权级切换与独立栈堆；会推翻当前 RTIC/固定内存模型，收益不匹配 |

### 3.4 capsule 化是分层的进一步表达

“纯逻辑 / 硬件”二分回答的是**可测性**；“core kernel / 基础 capsule / 业务 capsule”
回答的是**组合与演进**：业务不修改底座源码即可参与编译，底座内部重构不外溢。

`sdk`（`Capsule<C>`/`CapsuleSet`/`Product`）与产品组合根 `product`（S1）已落地：
`firmware` 只实现 `product::Platform` 把服务借出，组合策略在 `product`。
**尚未实现**：S2 上下文能力对象化（能力句柄）、S3 基础 capsule 外提与仓库外插件门禁；
仓库外业务 capsule 目前只能写无能力的 `impl<C> Capsule<C>`，业务接入仍按
[`业务接入指南`](业务接入指南.md) 的方式工作。
方向、契约与信任边界见 [`微内核与capsule架构`](微内核与capsule架构.md)；分阶段判据见
[`产品组合根外提设计`](产品组合根外提设计.md)。

更完整的分层规则见 [`分层与依赖规则`](分层与依赖规则.md)；逐模块实现状态见
[`模块分解`](模块分解.md)。
