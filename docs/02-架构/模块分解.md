## 为什么"未实现"要显式可见

三种做法对比：

| 做法 | 后果 |
|------|------|
| `todo!()` / `unimplemented!()` | **panic**：未实现变成运行期崩溃，且 panic 在 ISR 里可能表现为静默挂死 |
| 假装实现（返回成功） | 上层把不可用能力当成可用，做出错误的实时性假设；这是最危险的 |
| **返回明确的错误变体 + `GAP(Px)` 标记** | 未实现是**可观测的运行时事实**，同时被门禁清点 |

本项目选第三种。`BusError::NotImplemented`、`StoreError::NotImplemented`、
`StoreError::Rejected` 三个变体就是这个策略的类型化形式。

## 里程碑与依赖顺序

| 里程碑 | 内容 | 状态 |
|---|---|---|
| P1 | 平台可用：启动链、控制台、64 位时基、SDRAM、MPU/cache、栈测量、文件系统、终端、故障解码 | ✅ 2026-10-13 真机验证关闭 |
| P2 | 总线：CAN 驱动（探针/写序列已有）、串行端口驱动 | 部分（`GAP(P2)`） |
| P3 | 持久化与日志：FS 可写、文本日志全链路 | ✅ 已完成 |
| P4 | 升级：A/B 双槽 + 引导程序 + 回滚 | 未开始（`GAP(P4)`） |
| P5 | 现场可靠性：看门狗、黑匣子落盘 | 未开始（`GAP(P5)`） |

实现顺序不能随意交换，原因写在依赖里：

```text
P1（平台可用） → P2（总线可用） → P3（持久化） → P4（升级）
```

- 平台不可用时，任何"超时/重试/截止时刻"都失去意义；
- 持久化必须晚于总线：先确认"能收能发"，再决定"要存什么"；
- 升级必须晚于持久化：双区切换的正确性依赖存储的原子性；
- P5 的看门狗必须在健康门控就绪**之后**才允许生效（否则触发即断电恢复）。
