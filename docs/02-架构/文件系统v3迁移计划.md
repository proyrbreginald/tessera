> **历史说明**：本文件记录的是**旧仓库时期**的 v3 迁移计划，迁移已全部完成；
> **本仓库起点已包含 v3 生产路径**（旧仓库时期完成）。以下正文按历史顺序保留，
> 其中的步骤状态与"当前"措辞指的是**迁移进行时**，不再按旧版本号追溯。

- 状态：**已完成**（旧仓库时期完成；本仓库起点即 v3 生产）
- 依据：[ADR-0009](../adr/0009-文件系统v3-inode目录硬链接.md)
- 迁移前生产：v2 路径模型
- 迁移完成后：v3 卷层接入固件，成为唯一生产路径

## 1. 为什么不能直接替换

v3 已具备：

- inode/目录项/硬链接；
- rename intent/commit；
- 分块内容读写；
- 命名空间 checkpoint + clean 脏回退；
- 墓碑块与旧版本数据块 GC；
- read_dir/rmdir。

但固件接线仍缺：

1. 已提供区间流式读取与逐块流式写入；单 inode 上限 64 KiB（512×128 B）；
2. 索引快照容量按测试块（4 KiB）设计，生产 64 KiB 块需重新核算；
3. 没有活记录搬移式 GC（稀疏块压缩）；
4. 没有终端命令与 BSP 适配；
5. 没有掉电注入测试覆盖 v3 新格式；
6. 没有真机格式迁移验证。

因此直接切换会让现有 `config` / `/log` / 归档路径失效，不能作为旧版维护分支的补丁发布。

## 2. 首个生产适配提交（进行中）

在切换介质格式前，先完成一个**不破坏既有 v2 行为的适配层**：

1. ✅ `filesystem` 增加 `path_fs`（路径 → v3 inode 调用）；
2. ✅ `board-support::fs_v3` 增加 `FlashMedium`、`Fs` 与 `FsBackend`（默认 `V2`）；
3. 终端命令通过门面转发，v2 行为不变；
4. 主机测试同时跑 v2/v3 后端；
5. 只有全部门禁通过后，才把默认切到 `V3` 并全片擦除。

## 3. 迁移顺序（硬门禁）

### 2.1 主机层收尾

- 内容上限改为按块容量计算，支持多块文件；
- v3 索引容量在 64 KiB 块下验证；
- 活记录搬移式 GC 或明确保留“只回收整块”的边界；
- v3 掉电注入：每个记录边界、rename intent/commit 前后。

### 2.2 适配层

- `board-support::fs` 增加 v3 卷适配（或新建 `fs_v3` 模块），不直接替换 v2；
- 在编译期 feature 选择 v2/v3，默认仍 v2；
- 终端命令先只读（`ls`/`fstat`/`cat`）接 v3，写命令后接。

### 2.3 迁移与回退

- 更新固件必须 `bash scripts/flash.sh -e chip`；
- 首次 v3 启动全盘扫描，不读旧 v2 记录；
- 旧 v2 数据视为不可迁移（测试板数据可丢弃）；现场数据必须另行导出；
- 回退靠重新烧录 v2 时代的镜像（旧仓库 tag 不再在本仓库保留）。

### 2.4 真机门禁

```text
cargo xtask verify
make test-target
make bytecheck
cargo xtask bench --record
make release-check
```

并额外验证：

- `mkdir/rmdir/rename/ln/unlink` 跨复位；
- `/log` 归档仍可写、可读；
- 掉电/复位后索引 dirty 回退；
- 索引 checkpoint 后挂载走快照。
