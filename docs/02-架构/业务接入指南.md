# 业务接入指南

> 面向**接入方**：你的业务逻辑建在仓库之外，作为**业务 capsule** 参与编译期组合；
> 底座提供 core kernel、基础 capsule、端口、替身与门禁。
> 本文回答三件事：**怎么写**、**怎么脱离目标机测试**、**怎么上机**。
>
> 架构方向见 [`微内核与capsule架构`](微内核与capsule架构.md) 与
> [ADR-0008](../adr/0008-静态capsule化内核.md)。`sdk`（`Capsule<C>`/`CapsuleSet`/`Product`）
> 与产品组合根 `product`（S1）已落地；S1 只外提**组合策略**（集合/顺序/容量/产品名），
> 不含“仓库外业务 capsule 直接参与”的所有权通路（那是 S3 目标）。S2 上下文能力对象化、
> S3 基础 capsule 外提与仓库外插件门禁**未实现**。本文同时标注“当前可用”与“目标形态”。

## 1. 目标与分界

| 谁 | 负责什么 | 在哪里 |
|---|---|---|
| 底座（本仓库） | 启动链、外设驱动、存储、日志、实时仪表、故障解码、终端、门禁、主机替身 | 本仓库的 capsule / kernel-support crate |
| 接入方业务 | 领域类型、状态机、对外协议语义、业务决策 | **另一个 crate**（可独立仓库），即“业务 capsule” |

硬性边界（由 `check-layering` / `check-capsules` 的机制保证）：

- 业务 crate **不得**依赖 `imxrt-*`/`cortex-m*`/`rtic`——它只认识 `sdk` 与 `ports`；
- 若业务 crate 放进本仓库，`cargo xtask check-capsules` 会检查：依赖 `sdk` 的 crate
  **不得**直接依赖 `board-support`/`firmware`/`rtic`/`imxrt-*`（只扫仓库内 `crates/`）；
- 业务 crate **不得**出现 `unsafe` 与寄存器访问（那些只在 `board-support`/`firmware`）；
- 业务的时间从 `Clock` 端口来，I/O 从 `Bus`/`Store` 端口来 —— 因此**可以被完整重放**。

## 2. 推荐结构

```text
your-app/                     ← 接入方的仓库（或本仓库之外的目录）
  app-core/                   ← 纯逻辑：领域类型 + 状态机（依赖 primitives/ports）
  app-wire/                   ← 若需自定义协议：帧/语义（依赖 wire-format 或自研纯逻辑）
  app-tests/                  ← 主机测试：用 simulator 的替身重放全部时序
  app-capsule/                ← 只依赖 sdk：impl<C> Capsule<C>，类型上可注册进 Product
```

`app-capsule/` 在类型上可编译（S1）：只依赖 `sdk`，写 `impl<C> Capsule<C>` 即可。但
`Product` **借用** capsule（`&'a mut dyn Capsule<C>`）而不是拥有它，实例必须由调用方
持有并活过组合根；在仓库外产品 crate 的 `build` 里构造局部实例再 `register` 会因
生命周期不足直接编译失败（E0597）。当前也拿不到能力：`C` 是不透明泛型，`sdk::prelude`
只重导出 `ports` 的 5 个 trait；需要时钟/总线/存储句柄要等 S2。

主机测试的骨架（这就是"脱离目标机"的全部代价）：

```rust
use ports::bus::{Bus, Link, Idle};
use simulator::{MockBus, ManualClock, CapturingLog};

let mut bus = MockBus::new();
bus.push_response(b"...");            // 脚本化应答
let mut clock = ManualClock::new();
let mut link = Link::<_, Idle>::new(bus);
// 你的状态机只认识端口；超时、乱序、掉电都是普通的主机测试。
```

三种最有价值的测试（底座已经用它们抓过真 bug）：

| 测试 | 手法 | 为什么值钱 |
|---|---|---|
| **掉电原子性** | 对每个可写字节位置各注入一次掉电（`simulator::MemMedium` + 双份策略） | "半写"是现场最难复现的失效 |
| **超时/乱序** | `ManualClock` 手动推进 + `MockBus` 按脚本回帧/不回帧 | 时序类缺陷只在特定对齐下出现 |
| **回绕** | 把时间推到计数器回绕点 | `Timepoint` 不实现 `PartialOrd` 就是为此 |

## 3. 目标侧接线

### 3.1 当前可用（两种方式）

1. **加进本工作区**：把业务 crate 放进 `crates/`，并加进 `xtask` 的 `PURE_CRATES`
   （若它是纯逻辑）——它立刻获得 `test-host`/`lint-host`/`coverage` 的全部覆盖；
   然后在 `firmware` 里接线（S1 尚未提供“仓库外产品 crate 直接替换 firmware 组合根”的
   通路，业务 capsule 实例仍由 `firmware` 持有）。
2. **独立组合根**：业务 crate 作为路径依赖引入，自己写一个 RTIC bin
   （照 `firmware` 的结构：`#[init]` 做板级初始化、任务按 `primitives::budget::prio` 分优先级、
   健康位用 `primitives::safety` 聚合）。

### 3.2 组合根扩展能力（S1 的实际边界）

`crates/sdk/src/lib.rs` 是稳定门面；当前实际契约：

```rust
use sdk::prelude::*;

struct MyCapsule { /* 业务状态 */ }

impl<C> Capsule<C> for MyCapsule {
    fn name(&self) -> &'static str { "my-capsule" }
    fn phase(&self) -> CapsulePhase { CapsulePhase::Maintenance }
    fn init(&mut self) -> Result<(), CapsuleError> { Ok(()) }
    fn step(&mut self, _ctx: &mut C) -> CapsuleStep { CapsuleStep::Idle }
}
```

S1 真正可做的扩展（**不是**完整业务接入通路）：

```text
my-product（接入方产品 crate，依赖 sdk 与 product）
  ├─ 用 product::build / product::build_named 替换默认产品的顺序/容量/产品名
  └─ 在调用方持有实例的前提下，用 Product::register 追加 capsule
```

三条硬约束（决定它仍不是“仓库外业务接入”）：

- `Product` 借用 capsule，不拥有它；业务 capsule 实例必须由**调用方**（如 `firmware`）
  构造并活过组合根。在 `my-product::build` 里构造局部实例再 `register` 会因生命周期
  不足直接编译失败（E0597）；`product` 是 `forbid(unsafe_code)` 且无 alloc 的纯 crate，
  也不能用 `static mut` 或泄漏来自持实例。
- `C` 仍是不透明泛型，仓库外 crate 无法命名 `firmware` 的 `pub(crate)` 上下文类型，
  所以只能写泛型实现 `impl<C> Capsule<C>`，且拿不到任何能力（S2 才提供
  `CapsuleContext` / 能力句柄）。
- `build` / `build_named` **只注册、不初始化**；调用方必须在注册后立刻 `init_all`，
  否则 capsule 会在未 init 的状态下被 `step`（`CapsuleSet` 不会替你发现这一点）。

因此“业务方新建产品 crate、`firmware` 源码不变即可接入”是 **S3 的目标**，不是 S1 的现状；
S1 只外提了组合策略（集合、顺序、容量、产品名）。当前仓库外业务 capsule 只能先写
“无能力”的领域状态机（纯逻辑在 `app-core/` 用 `simulator` 测试），能力面等 S2。

`cargo xtask check-capsules` 的覆盖边界：只检查仓库内 `crates/`，仓库外业务工作区
需要接入方自己跑同等约束（S3 才提供仓库外插件门禁与模板）。

### 3.3 目标形态（尚未实现）

产品组合根在编译期选择业务 capsule：

```text
product-fw（组合根）
  ├─ core kernel：board::init / 中断 / 调度 / 预算
  ├─ 基础 capsule：console / fs / log / shell / diagnostics
  └─ 业务 capsule：motor / io / ...
```

组合根是唯一知道“产品包含哪些 capsule”的地方；业务 crate 不修改底座源码即可参与组合。
这是 **S3 的目标形态**：S1 只落地了组合策略外提，以及在调用方持有实例前提下的同作用域注册。
**尚未实现**：业务 capsule 的所有权通路（仓库外产品 crate 自持实例）、capability 句柄、
事件分发与仓库外插件门禁，见 [`产品组合根外提设计`](产品组合根外提设计.md) §5。

无论哪种方式，**上机实测复用底座脚本**：

```bash
make check-bench                  # 台架门禁
bash scripts/flash.sh -e chip     # 全片擦除后重烧（改了分区/格式必须）
make monitor                      # 抓串口，校验时基漂移 ±2%
make bytecheck                    # 控制台逐字节校验
cargo xtask bench --record        # 记录你关心的性能基线
```

## 4. 复用底座的"免检"能力（不要重造）

| 需求 | 直接用 | 不要 |
|---|---|---|
| 定长日志 | `log`（记录 + 环 + 压缩） | 自己写 `println` 风格日志 |
| 持久化文件 | `filesystem` 的文件语义 + 写队列 | 自己在 Flash 上划偏移 |
| 时间/超时 | `primitives::time`（回绕安全） | `now >= deadline` 的裸比较 |
| 校验 | `primitives::crc`（CRC-16/32 双算法） | 各处各写一份 CRC |
| 健康/安全状态 | `primitives::safety` | 自己发明"降级"布尔量 |
| 终端诊断 | `shell` 的命令表 + `ShellContext` | 手写 `match` 分发 |
| 配置/分区 | `flash-layout`（唯一事实来源） | 硬编码偏移 |

## 5. 质量门禁（接入方必须满足的底线）

- **纯逻辑可主机测试**：业务逻辑里不出现寄存器/I/O 直调；
- **未实现显式**：`todo!()`/假装成功一律禁止；用明确错误变体 + 缺口清单；
- **异常与超时可解释**：错误计数要能区分"对端拒绝"与"通信故障"这类不同处置；
- **回绕安全**：时间比较只走 `has_reached` 这类替换；
- **改动前后跑门禁**：业务 crate 若在本工作区，`cargo xtask verify` 必须全绿。

## 6. 常见问题

**Q：业务状态机为什么不能直接拿 `filesystem` 的句柄？**
A：写路径可能花几十毫秒（擦一个 64 KiB 块）。业务只应投递写请求（入队，可能被拒），
由 `idle` 属主执行 —— 这样"业务处理不被擦写阻塞"是由调度保证的。

**Q：没有目标板能不能开发？**
A：可以。主机测试覆盖纯逻辑；`simulator` 覆盖时序/掉电；上机只是"把同一份逻辑接到真实端口"。

**Q：业务需要一个新的外部设备端口怎么办？**
A：在业务侧定义一个小 trait（照 `ports` 的形状：方法少、无时间/无 I/O 副作用），
主机替身与真机实现各一份；**不要**把硬件细节漏进纯逻辑层。

**Q：业务 capsule 可以来自不可信第三方吗？**
A：当前架构**不支持**。capsule 与 kernel 共享地址空间；`forbid(unsafe_code)` 只排除
UB，不防 panic、死循环、资源耗尽或数据泄露。本架构的定位是“可信业务插件”。
要运行不可信第三方代码，需要 userspace/MPU 进程模型，那是另一套架构，
见 [ADR-0008](../adr/0008-静态capsule化内核.md)。

**Q：业务 capsule 能自己创建 RTIC 任务或注册中断吗？**
A：**不能**。中断与调度归 core kernel；`sdk::Capsule<C>` 只暴露 `name`/`phase`/`init`/`step`
等被动入口，由组合根在固定上下文调用（`on_event` 事件分发尚未实现）。这样实时预算与
优先级不会被业务拆散。
