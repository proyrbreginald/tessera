# ADR-0008：静态 capsule 化内核（编译期插件架构）

- 状态：已采纳（2026-10-21）
- 决策者：平台维护者
- 相关文档：[微内核与 capsule 架构](../02-架构/微内核与capsule架构.md)、
  [分层与依赖规则](../02-架构/分层与依赖规则.md)、
  [业务接入指南](../02-架构/业务接入指南.md)

## 背景

平台已经具备“与应用无关”的基础设施，但业务接入仍有两种形态：

1. 业务 crate 放进本仓库，直接修改 `firmware` 的 RTIC 任务表；
2. 业务自己写一个 RTIC bin，把 `board-support` 当库用。

这两种形态都能工作，但“底座”和“业务”的边界仍靠约定，而不是靠架构表达：

- 业务能看到过多内部 crate，底座升级容易破坏业务；
- 业务可以自己挂中断/任务，实时性论证被拆散；
- 没有一个明确的 capsule 生命周期、预算与健康口径；
- “可无缝更新”容易被误解为运行期热替换。

Tock 的 core kernel + capsules 分层提供了一个好参照：capsules 是独立的 Rust crate，
只通过受控 API 使用内核能力，可以按需组合。但需要明确：Tock 的 capsules 仍然运行在
内核态、与 kernel 共享地址空间；`forbid(unsafe_code)` 是代码纪律，不是安全隔离边界。
真正的隔离在 userspace process + MPU，那是另一套模型。

## 决策

平台采用**静态 capsule 化内核**，不引入运行期加载或热替换。

### 1. 三层职责

| 层 | 职责 | 是否允许 unsafe / 硬件依赖 |
|---|---|---|
| core kernel | 启动、时钟、中断、MPU/cache、Flash 原语、调度/事件循环、内存与故障处理 | 允许；只限 `board-support` / `firmware` 的既有边界 |
| 基础 capsule / 系统服务 | 终端、文件系统、日志、gzip、协议编解码等平台服务 | 纯逻辑 crate 禁止 unsafe；不直接碰寄存器 |
| 业务 capsule | 领域状态机、业务协议语义、业务决策 | 禁止 unsafe；禁止硬件/RTIC 依赖 |

业务 capsule 建在仓库之外，只依赖稳定的 capsule SDK 门面；当前仓库内的纯逻辑 crate
是未来基础 capsule 的候选，但**不宣称已经完成物理拆分**。

### 2. capsule 契约

- capsule 是**被动状态机**：core kernel 在固定上下文调用 `init` / `on_event` / `step`；
- capsule **不注册中断、不创建 RTIC 任务、不阻塞**；
- capsule 只能通过 capability 句柄访问总线、存储、时钟、日志；
- capsule 的代码必须可被 `simulator` 在主机上重放；
- 组合在编译期完成（泛型列表或等价静态组合），运行期零加载、零分配注册表。

### 3. 安全边界

- safe Rust + capsule API 纪律解决“内存安全/类型契约”，**不解决**恶意 capsule 的
  CPU 占用、panic、数据泄露或资源耗尽；
- 因此本架构只承诺“**可信业务插件**”的隔离级别；
- 若要运行不可信第三方代码，必须另做 MPU userspace / 进程模型，本 ADR 明确不采用。

### 4. 更新语义

“无缝更新”只指**源码/编译期解耦**：业务 crate 独立编译、与底座一起链接成整包固件。
不承诺运行期热替换。现场整包更新仍依赖 A/B 槽与 Bootloader（P4，当前未实现），
本 ADR 不把 P4 纳入 capsule 化的前置条件。

## 后果

### 正面

- 业务 crate 只依赖稳定门面，底座内部重构不外溢；
- 中断/实时预算仍由 core kernel 统一拥有，论证不被业务拆散；
- 编译期组合，零运行期加载开销；接口不兼容在编译期失败；
- 复用现有 `ports` / `simulator` / `check-layering` 资产。

### 代价

- 需要新增 capsule 生命周期、事件分发、capability 句柄、每 capsule 预算/健康；
- `firmware` 当时是单体组合根，需要外提产品组合根，业务才能不改底座接线（后续已由
  [ADR-0010](0010-产品组合根外提.md) 的 S1 落地）；
- 需要新的插件门禁与模板，仓库外业务 crate 才能获得与仓库内同等的质量约束；
- 同地址空间意味着一个 capsule panic/死循环仍可影响整机；这是与 Tock capsules
  相同的边界，不应被宣传成安全隔离。

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 运行期 ELF 动态加载 capsule | 需要重定位/符号解析/堆；与零分配、静态内存、A/B 整包模型冲突 |
| 每个 capsule 一个 MPU 独立地址空间 | 需要进程/特权级切换、系统调用、独立栈与堆；当前 RTIC/固定内存模型会被推翻，收益不匹配 |
| 每个 capsule 一个 RTIC 任务/中断 | 优先级与关中断预算被业务切碎，实时性无法统一论证 |
| `linkme`/分布式静态注册表 | 依赖链接器段落魔法；组合根不可见，替代方案（编译期泛型列表）已足够 |
| 把 safe capsule 宣称为“不可信隔离” | safe Rust 不防 DoS/资源耗尽/panic；会制造错误安全预期 |

## 实施边界

本 ADR 只冻结**架构方向与边界**，不等于以下能力已实现：

- `sdk` 门面；
- `Capsule` trait 与编译期组合列表；
- 产品组合根外提；
- 插件门禁与模板；
- 每 capsule 预算/健康/配额；
- A/B 整包更新。

这些必须按独立任务推进，并在实现前保持“未实现”的诚实口径。
