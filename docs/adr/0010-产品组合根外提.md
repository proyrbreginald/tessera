# ADR-0010：产品组合根外提（依赖倒置 + 服务注入）

- 状态：已采纳（2026-10-23）
- 决策者：平台维护者
- 相关文档：[产品组合根外提设计](../02-架构/产品组合根外提设计.md)、
  [微内核与 capsule 架构](../02-架构/微内核与capsule架构.md)、
  [ADR-0008](0008-静态capsule化内核.md)、[业务接入指南](../02-架构/业务接入指南.md)

## 背景

ADR-0008 冻结了"静态 capsule 化内核"方向，`sdk` crate 随后落地了
`Capsule` trait、固定容量 `CapsuleSet` 与 `Product` 模板，`firmware` 也已把六个内置
服务接成 capsule 生命周期。但组合根仍物理位于 `firmware`：

- capsule 集合、容量与注册顺序写在 `firmware::composition`；
- 六个服务定义在 bin crate `firmware` 内，仓库外 crate 无法依赖/命名；
- 六个服务共享的 step 上下文是 `pub(crate)` 类型。

后果是"业务不改底座源码即可参与组合"仍然做不到，与 ADR-0008 的目标形态有差距。
直接搬运会形成 `firmware → product → firmware` 的循环依赖。

## 决策

采用**依赖倒置 + 服务注入**外提产品组合根：

1. 新增纯逻辑 crate `product`，只依赖 `sdk`；它定义 `Platform`（平台服务注入契约）、
   `PlatformServices`（六个具名服务槽）与 `build`（固定注册顺序、容量/重名显式失败）；
2. `firmware` 新增 `platform` 模块实现 `product::Platform`，把已构造的服务实例以
   `&mut dyn sdk::Capsule<C>` 借出；
3. step 上下文类型 `C` 对组合根是**不透明泛型参数**，组合根不命名、不解释它；
4. `product` 为业务 capsule 预留槽位；但 capsule 实例归**调用方**所有（`Product` 只借用）。
   因此 S1 只外提组合策略；"仓库外业务 crate 接入、`firmware` 源码不变"需要 S3
   解决实例所有权（详见设计与 §后果·代价）。

本 ADR 只决定"组合根放在哪里、如何拿到服务"，**不**决定：

- 上下文的公开形态与能力句柄（S2）；
- 基础 capsule 是否物理迁移（S3）；
- 失败/隔离/预算语义的最终形态。

## 后果

### 正面

- 消除循环依赖：依赖方向单向 `firmware → product → sdk`；
- 组合策略（集合、顺序、容量、产品名）从底座移到独立 crate，业务产品可替换；
- `product` 可主机测试（纯逻辑），组合顺序/容量/重名成为普通单测；
- 依赖图本身成为判据：`check-layering` 与 `check-capsules` 强制 `product` 不碰硬件。

### 代价

- `firmware` 仍需构造六个服务实例（它们要经 `board-support` 接触硬件），
  "服务实例也搬走"要等 S3；
- `PlatformServices` 的六个具名槽把平台服务拓扑写进 `product`，换服务集需改产品 crate；
- capsule 实例仍归调用方所有（`Product` 借用），仓库外业务 crate 无法在自己的
  `build` 里构造实例再返回组合根（生命周期不足）；
- 业务 capsule 目前只能写无能力的泛型实现（`impl<C> Capsule<C>`），
  拿到时钟/总线/存储要等 S2 的上下文能力对象化；
- 组合根构建失败路径（容量不足/重名）在当前容量与服务命名下不可达，但重名/扩容后
  是真实路径；失败会回退成 0 个 capsule（无终端/日志/健康），需要负例测试看住它。

### 未决问题

1. 失败/隔离语义：累计失败即永久隔离、`init` 不可重试、无 per-capsule 预算承载点；
2. 上下文别名的安全化路线（按值传入 `Copy` 句柄 vs 借用拆分）；
3. `.xip` 正向白名单如何让仓库外 capsule 参与代码放置。

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| `product` 直接依赖 `firmware`（先把服务抽成 lib） | 环形依赖；即使 Cargo 允许通过拆 crate 绕过，也让组合根无法独立于底座演进 |
| `product` 依赖 `board-support` 自己造服务 | 组合根变成第二个硬件入口；纯逻辑层出现硬件依赖；业务产品无法主机测试 |
| 服务实例做成全局 `static` | 与 `firmware` 静态量重新耦合，生命周期与别名问题从类型系统挪到运行期 |
| 分布式自注册（`linkme`/`ctor`） | ADR-0008 已否决：依赖链接器段落魔法，组合根不可见 |
| 把 `CapsuleSet` 换成运行期注册表 | 需要堆与动态派发；与固定内存、静态可论证的目标冲突 |

## 实施

S1（本 ADR 落地范围）：`crates/product` + `firmware::platform` + 依赖接线 +
主机单测 + 真机验证。

S2/S3 见 [产品组合根外提设计](../02-架构/产品组合根外提设计.md) §5，按"先失败判据、
后实现"的顺序推进。
