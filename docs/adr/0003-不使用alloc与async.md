# ADR-0003：不使用 alloc，也不使用 async

## 状态

已采纳（决策）；`alloc` 部分已按文末**修订**改为"受限引入"。

## 决策

全部容器用 `heapless` 固定容量类型；**不使用 `alloc`**；**不使用 async/await**。

## 理由

- **零分配**：内存用量静态可知，是安全论证的一部分（不存在内存耗尽、碎片导致的
  非确定性）。本项目所有集合都有自然上界（定长帧缓冲、队列、表），容量是编译期常量。
- **不用 async**：见 [ADR-0001](0001-运行时选型rtic-v2.md) —— 单执行器无抢占，
  硬实时不可论证。

## 后果

- **正面**：`bss`/`data` 用量在链接期完全确定；无分配器意味着不需要论证分配器。
- **代价**：所有集合要有编译期容量上界；容量估错会导致 `TableFull` 而不是"自动扩容"。
  缓解：容量做成 const generic，启动时打印用量，并按 ≥2× 预留
  （见 [内存与Flash布局](../02-架构/内存与Flash布局.md)）。
- **重新评估的触发条件**：实时要求都放宽到软实时，**且** IO 并发路数 ≥ 4。

---

## 修订（2026-10-12；后续扩为两段池）：**受限**引入 alloc —— SDRAM 固定块静态池

### 背景

原决策的理由是"内存用量静态可知、不存在耗尽/碎片导致的非确定性"。后来出现一个具体
需求：**运行期按需持有变长对象**（终端/诊断路径的排版、gzip 压缩器状态）。

### 决定

**引入 `alloc`，但把它约束成"不破坏原论证"的形态**：

| 原论证 | 新实现如何保住它 |
|---|---|
| 内存用量静态可知 | 池 = SDRAM 里**两段**常量地址 + 常量大小的区域（小块池 1 KiB × 2048 块 + 大块池 128 KiB × 32 块（4 MiB）），编译期断言把两段都钉在 SDRAM 窗口内、**首尾相接且不重叠**（[`memory-layout`](../../crates/memory-layout/src/lib.rs)）。"堆能长到多大"这个问题不存在 |
| 无碎片 | **两个池各自都是固定块大小** ⇒ 不存在"总空闲够、但没有连续块"。**不做跨池拼块、不做块内切分**；单次请求超过 64 KiB 直接失败，这个代价是**故意**的 |
| 失败可处置、不 panic | `alloc` 失败返回空指针；`dealloc` 的重复释放/越界**只计数、不改位图、不 panic** —— 策略在纯逻辑 crate [`block-pool`](../../crates/block-pool/src/lib.rs)（`forbid(unsafe_code)`，主机测试覆盖耗尽/重复释放/越界/高水位） |
| 控制路径的确定性 | **控制路径（总线收发、状态机、存储）一律不使用 `alloc`** —— 仍用编译期定容的 `heapless` 容器。`alloc` 只服务终端/诊断与压缩器状态 |

### 明确不做的事

- **不引入通用堆**（可变块、可合并、可增长）—— 那正是原决策否决的东西；
- **不用 `alloc` 传输控制帧**，也不把"分配失败"当作可接受的控制路径行为；
- 需要"一大块"内存时**声明静态区**，不走分配器。

### 仍然否决 async

原决策中关于 `async` 的部分**不变**（理由见 [ADR-0001](0001-运行时选型rtic-v2.md)）。

### 重新评估

若将来需要"变长块 + 合并"，必须重新走一遍本 ADR 的论证（碎片与耗尽的非确定性会回来），
而不是顺手把块大小改成可变的。
