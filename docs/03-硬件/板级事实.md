# 板级事实与证据链

> 依据：`docs/manual/IMXRT1020IEC.pdf`（NXP《i.MX RT1020 Crossover Processors for
> Industrial Products》Rev 3.1, 03/2022，**数据手册，非参考手册**）与
> `docs/manual/PJ0007_TF2_SCH-A10-20250427-主控板.pdf`（主控板原理图，13 页图框）。

## 1. MCU 与存储器

| 项目 | 取值 | 依据 |
|------|------|------|
| 订购型号 | `MIMXRT1021CAG4A` | 原理图 p3/p4（`U1`）；数据手册封面 |
| 内核/频率 | Cortex-M7，最高 **396 MHz** | 数据手册 §1 |
| 封装 | 144-LQFP，20×20 mm，0.5 mm 间距 | 数据手册 §6.1.1 |
| 片上 RAM | 256 KB（FlexRAM：ITCM/DTCM/OCRAM 可分配） | 数据手册 §1 |
| Boot ROM | 96 KB，出厂固化 | 数据手册 |
| **内部程序 Flash** | **无**（型号里的 `4` 是主频位，不是 4 MB SIP Flash） | 数据手册 §1.2 |
| 外部程序 Flash | Winbond `W25Q256JVEQ`，32 MiB，3 V，quad-SPI ≤133 MHz | ✅ 原理图 p13（`U2`）；实板确认 |
| 外部 SDRAM | `W9825G6KH-6I`（TSSOP-54，`U20`），**32 MB** @`0x8000_0000` | 原理图 p13；**已由固件初始化并全片自检通过（2026-10-10）** |
| 晶振 | `Y1` **24 MHz**，负载电容 11 pF | 原理图 p4 |

🟡 SDRAM 容量在资料内自相矛盾：原理图 p3 框图写「32MB」，而 p13 设计注记按
`8M×16×4 = 512 Mb = 64 MB` 推算。**固件已按 32 MB 初始化并全片自检通过（2026-10-10，
`pattern_test` 覆盖 32768 KiB、0 错误）**，所以这个矛盾不影响当前固件；实做前仍建议核实。

## 2. 引脚（只列本固件使用或明确相关的）

### 2.1 启动 Flash（FlexSPI1-A，ALT1）

| 信号 | 焊盘 | 球号 | 接到 |
|------|------|------|------|
| `SPI_SS0` | `GPIO_SD_B1_11` | 19 | `U2` pin1 CS |
| `SPI_CLK` | `GPIO_SD_B1_07` | 24 | `U2` pin6 CLK |
| `SPI_DATA0..3` | `GPIO_SD_B1_08/10/09/06` | 23/21/22/25 | `U2` pin5/2/3/7 |

> 原理图注记：「QSPI 时钟包地，整组包地」「等长误差 ≤100 mil」。

### 2.2 调试串口 LPUART1 ✅

| 信号 | 焊盘 | 球号 | ALT | 接到 |
|------|------|------|-----|------|
| `UART1_TXD` | `GPIO_AD_B0_06` | 105 | **2** | 22R → `J7` pin11 |
| `UART1_RXD` | `GPIO_AD_B0_07` | 101 | **2** | 22R → `J7` pin12 |

115200 8N1 **是工程约定**，数据手册与原理图都没有规定控制台波特率。
UART 功能时钟取 **24 MHz 晶振**（`UART_CLK_SEL=1`、`UART_CLK_PODF=1` → 115384 Hz，
误差 +0.16%），而不是 PLL3/6（误差 0.006%）：理由是**不依赖 PLL3 是否锁定**，
时钟树配错时控制台仍能出字。

### 2.3 SWD ✅

`SWDIO = GPIO_AD_B0_00`（球 111）、`SWCLK = GPIO_AD_B0_01`（球 110），都在 `J7`
（`300-2S-16P/2X8PIN-2MM`，标注「调试接口」）。

### 2.4 CAN（`CAN2` + `TJA1044T`，驱动已落地、接收路径未通）

> 板上有 CAN 收发器 `U13`（`TJA1044T`）；控制器是 **FlexCAN2**
> （`MCR` 复位值 `0x5980_000F` 与 `[RM 40.9.1]` 逐位一致）。

| 信号 | 焊盘 | 球号 | ALT | 接到 |
|------|------|------|-----|------|
| `CAN2_TX` | `GPIO_AD_B1_00` | 92 | **2** | `U13`(TJA1044T) pin1 TXD |
| `CAN2_RX` | `GPIO_AD_B1_01` | 91 | **2** | `U13` pin4 RXD（输入选择 daisy = **3**） |

端接 120 Ω（`R185`/`R186`），共模电感 `L13`，TVS 保护；连接器 `J12`/`J13`
各带 CANH/CANL 与 120 Ω 端接。

**ALT 与 daisy 的依据**（这一项曾在旧文档里是"未知"，2026-10-13 关闭）：
- 官方 `fsl_iomuxc.h:502`：`IOMUXC_GPIO_AD_B1_00_FLEXCAN2_TX` 的 mux 值 = `0x2`；
- 官方 `fsl_iomuxc.h:511`：`IOMUXC_GPIO_AD_B1_01_FLEXCAN2_RX` 的 mux 值 = `0x2`、
  输入选择寄存器 `0x401F8324`、daisy 值 = **`0x3`**；
- 本板既有固件 `pin_mux.c:262/265`（`BSP_USING_CAN2` 分支）用的是同一对焊盘；
- ⚠️ 对照：第一版误用了 `GPIO_AD_B0_14/15`（那是 ENET 焊盘、ALT=1）—— 已修正并
  把 ENET 焊盘恢复成 ALT0。**ALT 是 2、RX 的 daisy 是 3，这两项都不可能靠猜得到。**

**驱动现状**（`crates/board-support/src/flexcan.rs`）：
- **焊盘手配**：`imxrt-iomuxc` 只有 imxrt1060 的 `flexcan::Pin`（1020/1021 没有，
  orphan rule 使下游无法补实现），因此 CAN 焊盘由 BSP 自己按上面的 mux/daisy 值写；
- **只读探针**：常开、零副作用，回读 `MCR`/`CTRL1`/`ECR`/`ESR1`/`IFLAG1` 与 PE 时钟；
- **写序列 + loopback 自证**（`config::CAN_LOOPBACK_SELFTEST`，默认开）：覆盖
  "时钟门控 → 复位 → 位时序 → 邮箱 → 发送 → 接收"整条通路；
- **PE 时钟真机实测 12 MHz**（由 `CCM_CSCMR2[CAN_CLK_PODF]` 决定，**不是假定的 24 MHz**；
  位时序按官方公式反解，目标 **1 Mbps**）；
- **当前真机结论（2026-10-19）：内部 loopback `PASS`** —— TX 完成、RX 逐字节一致。
  它证明控制器/邮箱路径，**不证明** TJA1044T 之后的 CANH/CANL 电气与对端设备；
  外部总线接收仍未通，在接通第二块板/示波器之前**不靠改序列去猜**，
  缺口留作 `GAP(P2)`（见 [`模块分解`](../02-架构/模块分解.md)）。

### 2.5 看门狗（外部 SGM706）

器件 `SGM706-SYS8G`，原理图 p4 的 **`U5`**（不是某些资料里写的 `Z1`）。
`WDG_CTR` 极性：**高电平禁用看门狗**（原理图 p4 注记 + 二极管方向推导一致）。
`WDI` 为独立网络。🟡 `WDG_CTR` 的驱动源未逐线确认（疑为按键板或 IO 扩展器）；
这一项是开放问题 **Q-I**（见 [`需求规格`](../01-需求/需求规格.md)），
也是看门狗未启用的原因（`GAP(P5)`，见 [`模块分解`](../02-架构/模块分解.md)）。

### 2.6 板上的串行/总线收发器（事实陈述）

对原理图全 13 页检索 `485` / `SP3485` / `MAX485` / `SN65` / `ADM485` / `75176`：
**零命中**，也没有任何 RS-485 收发器器件。

板上唯一的板载总线收发器是 CAN 的 `U13`（`TJA1044T`，见 §2.4）。
**若上层需要串行总线（如 RS-485），须由外部转换器或另一条链路提供** ——
这条路径不在本底座当前的验证边界内，因此固件不装配任何相应驱动，
也不会"假装它能用"。

## 3. 时钟与启动

- 24 MHz 晶振 → PLL → 各总线频率。🟡 **PLL1/PLL2/PLL3 与 AHB/IPG 分频无资料记录**，
  当前由 `imxrt-hal` 的默认 `ccm` 配置决定；实测频率待用 DWT 或 CLKO 标定。
- 启动链：Boot ROM 读 FCB → 配 FlexSPI → 读 IVT/boot data → 跳到 Flash 复位向量
  → `Reset`（设栈指针、搬 `.data` 与向量表）→ `__pre_init`（关 RTWDOG、配 FlexRAM、搬段）
  → `main`。
- **ISP/串行下载模式**：`BOOT_MODE0/1` = `GPIO_EMC_16/17`（球 142/141），
  `BT_CFG[0..9]` = `GPIO_EMC_18..27`，默认 100 K 下拉。🟡 本板把这些焊盘**与 SDRAM
  地址线共用**，实际上电电平无记录；要进 ISP 必须先实测。
- FlexSPI 串行时钟 100 MHz（器件允许 133 MHz）。⚠️ **dummy 周期与时钟绑定**：
  当前 6 个 dummy 只对 100 MHz 正确；只改时钟不重算 dummy 会读到垃圾数据，
  表现为**启动即崩溃**。

## 5. 本固件**不依赖**的板级事实

以太网 PHY、USB、4G/LoRa/UWB 模组、各类传感器、RTC、IO 扩展器、LED 驱动源
—— 均未初始化、未使用。把它们写在这里是为了明确**当前验证的边界**：
本固件当前有真机证据的路径是 LPUART1 + PIT 时基 + FlexSPI 只读（含 FCB 启动）
+ **SEMC/SDRAM 初始化与自检** + **MPU/cache** + **文件系统只读挂载**
+ **FlexCAN2 只读探针与写序列**（内部 loopback **PASS**，外部总线接收未通）。

修复项与实测判据（全部在本板实测）：

### 2026-10-19（S1 续 2）：`0.21.7.0` 故障注入入口

- 终端新增 `fault udf`：执行 `UDF` 触发 UsageFault（本平台刻意不打开 `SHCSR.USGFAULTENA`，
  因此升级为 HardFault），走真实故障路径。
- 真机结果：串口打印 `!!! FAULT HardFault`、`frame : PC/LR/SP/xPSR/R0-R3`、
  `CFSR=0x00010000`（UsageFault：非法指令），随后复位；证明"故障现场可解释"链路有输入。
- **已闭环（0.21.8.0）**：复位后启动报告 `last crash: 见下方`，`crash` 行的
  PC/LR/SP/CFSR/HFSR 与故障帧逐项一致（PC=0x000038dc、CFSR=0x00010000）。
  根因：`clean_dcache_by_address` 的 `num_lines` 按传入 size 从**对齐后起点**计算，
  未对齐的 CRASH（0x...d59c，48 B）末尾 8 B 所在第三行没被 clean；改为先把起点
  对齐、长度补上起点偏移后，记录完整写回 SRAM。

### 2026-10-12：控制台**逐字节**校验（`make bytecheck`）与丢字节真因

**背景**：控制台发送在 2026-10-10 改成中断驱动 + 2 KB 环形队列之后，长输出的
**后半段会被整行整行地丢掉**（前几行完好，肉眼极易漏判）。

**判据（可复现）**：让固件在启动时打印 4096 字节**可计数图案**（64 行 × 65 字节），
再用 `scripts/console-bytecheck.py` 逐字节比对 —— 中文文本难以量化"丢了多少、从哪开始"，
图案可以精确对齐。单变量 A/B：

| 构造 | 结果 |
|---|---|
| 纯阻塞发送（单一 `DATA` 写入者） | **4160/4160 逐字节一致** |
| 环形队列 8 KB（突发期间**不满**） | **4160/4160 逐字节一致** |
| 环形队列 2 KB（突发期间**会满**） | **只到 53/64 行**（丢约 715 字节） |
| 环形队列 + 阻塞写混用 | 彻底乱（计数器一行都到不了） |

**真因**：队列化路径在"队列满且中断关着"时退回**按字节直写 `DATA`**，与中断里的排空
**同时写同一个寄存器**、互相覆盖。修法：该路径**只入队、绝不直写**；关中断上下文要输出
走 `write_bytes_blocking`。**先前归因的"陈旧 `TDRE`/连写"不是真因**。

**修复后验收**：`make bytecheck` **8/8 条期望文本逐字节一致**（连跑两次），
图案 **4160/4160**。命令与判据见 [`../04-开发/门禁手册.md`](../04-开发/门禁手册.md)
与 `scripts/bytecheck.sh`；提交 `39ff36a`，版本 → 0.3.1.0。

横幅现在会**回读并打印 PIT 寄存器**（`pit regs : ...`）——
"时基是链式的"这句话必须能被寄存器证实，而不是自我声明。这条习惯直接来自本次踩坑。

**本次修掉的四个时基缺陷**（串口只有横幅、之后永久静默；三处都在 `board-support`）：

1. `PitClock::ticks()` 每次读时间都调 `hal::pit::Pit::new()` —— 而 `Pit::new()` 会
   把四个通道的 `TCTRL` **清零**，即"读时间把定时器关掉"。现在读路径只用 RAL 读寄存器。
2. `enable_chaining(Chan0)` 被 HAL 直接拒绝（低位通道不能成链），返回值被丢弃
   → **64 位链从未建立**。改为链 `Chan1`，失败即 panic。
3. `now()` 把"刻度→微秒"写成 `ticks / TIMEBASE_HZ`（24e6）—— 那是把 1 秒折算成
   **1 微秒**，时间慢 100 万倍。正确换算是除以"每微秒刻度数"（24）。
4. ISR 清标志后未清 NVIC 挂起位，存在重入竞态 → 中断频率实测 1493 Hz（设计 1000 Hz）。
   显式 `NVIC::unpend(PIT)` 后回到 996.5 Hz。

| 项 | 实测 | 判据 |
|---|---|---|
| SEMC 时钟 | 62.5 MHz（PLL_SYS 528 MHz → PFD2 500.2 MHz → PODF /8） | 与既有 C 固件 `clock_config.c` 记录的 62.5 MHz 一致 |

1. **`MCR[DQSMD] = 0`（内部回环）**：C 固件用"从 DQS 焊盘回环"，但**本板原理图没有

3. **焊盘电气配置沿用 Boot ROM DCD 的 `0xE1`**（SRE=1、DSE=7、SPEED=200 MHz、无上下拉）。

**串口终端（仿 Fedora 风格）已上机**：彩色提示符 `[root@tessera ~]# `、逐字符回显与重绘、
方向键/Home/End/Delete/Ctrl-A/E/U/K/L/C、Tab 补全、上下翻历史、错误红字与 ERR 状态行。
命令：`help/status/memtest/fs/wq/mem/rt/free/uptime/version/uname/whoami/hostname/history/echo/colors/clear/gaps/reboot`
以及 `can`（**只读探针**）；未实现的能力明确报错、给出 `GAP` 指针，不假装成功。
（命令表是唯一数据源，`help` 与补全自动跟上 —— 完整清单以 `shell` 的 `COMMANDS` 为准。）

**接收路径的一处硬约束**：这块 LPUART 的**接收 FIFO 只有 1 字节深**（`FIFO[RXFIFOSIZE]=1`）。
因此发送路径**绝不能关中断**：早期 `with_console` 用 `core::sync::critical_section` 包住整段
阻塞发送（一行 60 字节 ≈ 5.2 ms），这期间到达的输入全部溢出丢失 —— 现场症状是
"终端提示符与回显都正常，但每次只收到两个字符"。

**现在的做法**（2026-10-10）：接收走 `LPUART1` 中断 + 256 字节环形队列；
发送也改成**中断驱动 + 2048 字节 `heapless::Deque`**，入队只短暂进一次临界区拷一个字节，
CPU 不等待寄存器。⚠️ 两个真机坑：①ISR 里**一次中断只写一个字节**就返回（第一版在 ISR 里
`loop` 连写，长输出后半段丢约 40% 字节、汉字整段错位）；②**同一条通道只能有一个 TX 实现**
（曾同时存在 HAL 阻塞写与环形队列两份，二者抢 `DATA`）。队满时的处置按中断是否开着区分：
中断开着就等 ISR 腾位置，关中断（panic/临界区）则按字节直写，否则会死等。
⚠️ **这条队满分流策略后来被修正**（2026-10-12）：关中断时**不再直写**，改为**丢弃并计数**
（`txdrop=`），队列也按实测定容到 **8192 B** —— 见上一条记录与
[`台架准备与排障`](../04-开发/台架准备与排障.md)。

### 2026-10-10：文件系统上机 + 栈余量实测

> ⚠️ 本节是当天**较早**的一次快照（文件系统 190 块 / 栈 32 KiB）。同日晚些时候启用
> 整片 32 MiB 后，文件系统扩到 **446 块**、栈提到 **48 KiB**，见下一节「（续）」。
> **当前值以「（续）」为准**（最后一次上机镜像的启动横幅：栈峰值 **29,860 B / 余量 39%**）。

**文件系统分区已可挂载（读路径真机可用）**：

```
fs       : mounted, 190 blocks x 64 KiB = 12160 KiB, 0 个文件
fs       : config.bin 尚未写入（首次上电的正常状态）
```

- 190 块 × 64 KiB = 11.88 MiB，与分区表一致（`FILESYSTEM_SIZE / BLOCK`）；
- 挂载只做 XIP 读（扫描块头），因此**不需要擦写驱动**即可工作 —— 这也意味着
  "把文件内容整段读出来做校验/搬运"这件事当时就能做；
- 擦除与页编程当时仍依赖 FlexSPI IP 命令驱动（当时的旧缺口口径），写入会**明确失败**
  而不是静默丢数据。（2026-10-12 之后擦写已走 Boot ROM API 落地；文件系统的
  **写入路径**仍未接线，现为 `GAP(P3)` —— 见 [`模块分解`](../02-架构/模块分解.md)。）

**上机抓到的两个真问题**（都属于"只有真机才会暴露"）：

| 现象 | 根因 | 处置 |
|---|---|---|
| 启动后串口**一行都不出** | `fs::mount()` 的 ~7 KiB 实例 + 搬进静态的副本同时在 16 KiB 栈上 → `CFSR=0x400`(STKERR)、`SP=0x1FFFF838`（越过 DTCM 下界）、`HFSR=0x40000000`(FORCED) | 栈 16 KiB → 32 KiB；并加栈涂抹测量（见下） |
| 读 `"/config.bin"` 返回 `BadName` | 扁平命名空间不允许 `/`（路径分隔符），而文件名是按 POSIX 习惯写的 | 文件名改为 `config.bin` 等（不带前导斜杠） |

**栈余量现在有实测数字**（不再是"估计一个够大的值"）：

```
stack    : 峰值 19336 B / 32 KiB，余量 13432 B (40%)
```

两次被栈打穿的对照：8 KiB（2026-10-09，SP 到 `0x1FFFE7F0`）、16 KiB（2026-10-10，
SP 到 `0x1FFFF838`）—— 而实测峰值 19336 B 正好落在 16 KiB 之外、32 KiB 之内。

### 2026-10-10（续）：启用整片 32 MiB 与两处现场操作约束

**4 字节寻址已启用并验证**：FCB 的 LUT 改用专用 4 字节操作码（读 `0xEC`、页编程 `0x34`、
扇区擦除 `0x21`，地址相位 `0x20`），依据是**本板既有固件的已知正确配置**
（`bsp/board/imx_nor_flash/nor/flexspi_romapi.c`）。刻意**不用** `EN4B(0xB7)` 模式切换：
后者会把器件留在非上电默认状态，序列没生效就变砖。验证见
[Flash布局与用途划分 §8.6](../02-架构/Flash布局与用途划分.md)。

**顺带修掉的一处隐患**：原先"偏移是否可访问"的判据是器件容量（32 MiB），
而 3 字节模式下越过 16 MiB 的访问**不报错、会别名到低 16 MiB**。

**两处只有真机才会暴露的事**：

| 现象 | 根因 | 处置 |
|---|---|---|
| 启动后 21 秒才出字，最后"卡住" | 新分区里是**上一版 C 固件的数据**（能读出旧固件遗留的字符串）；非擦除块要逐字节重同步 | 改布局后**必须全片擦除**（`pyocd load ... -e chip`）；擦除后挂载 3 ms |
| 启动后串口全哑 + SWD 连不上 | 文件系统扩到 446 块后常驻索引 7 → 12 KiB，构造时"临时量 + 静态副本"同时在栈上，顶穿 32 KiB 栈 → lockup | 栈 32 → 48 KiB；文件表 16 → 8；当时实测峰值 28,812 B / 余量 41%；**最后一次上机镜像的启动横幅实测 29,860 B / 48 KiB，余量 39%** |

**XIP 读改为批量拷贝**：原先逐字节 `read_volatile`（每字节一次 `checked_add`），
使挂载扫描 27.88 MiB 慢到几十秒 —— 表现同样像"死机"。用调试器连续采样 PC
（在动 vs 不动）才把它与"真卡死"区分开。
